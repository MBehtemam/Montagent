# The project schema is closed everywhere, and there is no in-band escape hatch

> **Amended by [ADR-0156](0156-four-named-effects-join-the-effects-list-and-a-code-drawn-piece-enters-as-pre-rendered-footage.md)**: reaffirmed, not reopened. An open shader or script file
> stays refused, and a code-drawn look enters as pre-rendered footage instead.

[#75](https://github.com/MBehtemam/Montagent/issues/75). ADR-0016 spends the format's entire
forward-compatibility budget on the unknown-key error, and states plainly that its mechanism
"does not exist" unless the schema is closed to unknown keys — but no accepted document had
taken that decision. This ADR takes it, at three levels: base policy, scope, and escape hatch.

## Base policy: closed, at `error` severity

Any key the schema does not define is a schema validation **error**, not a `note` and not a
`warn-and-proceed`, and it blocks `render`. This was tested to a three-model jury (Opus,
Sonnet, Haiku) and returned unanimous, for two converging reasons that were independently
named by all three jurors:

- **ADR-0016's mechanism requires it structurally.** With no version number in the file, the
  unknown-key error is the *only* signal an old binary has that a file was authored against a
  newer schema revision. A permissive policy — open or warn-and-proceed — makes that signal
  optional, and an optional signal is indistinguishable from no signal: the same failure this
  project already rejected once, in ADR-0006, as "an omitted check is indistinguishable from a
  decision not to check."
- **The typo case is the load-bearing scenario, not the edge case.** [#48](https://github.com/MBehtemam/Montagent/issues/48)
  measured agents systematically mistyping fields copied from examples (`"gravty"` for
  `"gravity"`). Under an open or warn-and-proceed schema, that typo is silently accepted and
  the video renders wrong with no signal — worse than a blocked render, because a blocked
  render is at least noticed. A `note`-level finding fares no better: ADR-0016's own error text
  ("do not delete the key to make the file validate") only means anything if the file will not
  render either way, and a warning that doesn't block gets skimmed past by exactly the agent
  that made the typo in the first place.

## Scope: closed uniformly, at every object level

The closed-schema policy applies to **every object shape the schema defines** — the project
top-level object, track, element (per discriminated type), run, keyframe, and font-table
entry — not only the levels most exposed to revision skew (project and element types).

Tested to the same three-model jury, 2–1 for uniform closure. The majority argument: neither
typo risk nor skew risk correlates with nesting depth. A `run` object misspelling a style key,
or a `keyframe` misspelling `ease`, is exactly the silent-drift failure the policy exists to
catch — and these shapes are authored in the highest multiplicity per file, so if anything they
are *more* exposed to copy-paste typos than the project header, not less. Schema growth in a
video editor also lands disproportionately in nested shapes (a new easing parameter, a new
run-level style field), so an old binary needs the same tripwire there to catch skew; leaving
nested objects open just relocates the exact blind spot closure was adopted to close. The
dissent (localizing typo risk to "high-level copy-paste" and treating keyframes as
"algorithmically generated") did not survive that counterpoint: keyframes and runs in this
format are hand-authored by an LLM agent, not generated by tooling, at least as often as
top-level structure is.

## Escape hatch: none — third-party annotation lives in a sidecar

The schema reserves **no namespaced prefix** (no `x-` or equivalent) exempted from closure on
any object. Third-party annotation — a review comment, a tracking id, an experimental field a
different tool wants to read — belongs in a **separate sidecar file** in the same git repo,
never in the project file.

Tested to the same jury, 2–1 against an `x-`-style hatch, reversing this ADR's original
working recommendation. The majority argument: an escape hatch does not add a side channel
next to the schema's strictness, it puts a hole *in* the property that makes the unknown-key
error legible as a version-skew signal at all. Once any key pattern is exempt, "unknown key"
stops meaning "something is definitely wrong" and starts meaning "something is wrong, unless
it happens to match the reserved pattern" — and a typo that happens to collide with the
pattern (`"x-gravity"` for `"gravity"`) now validates silently, which is the exact failure mode
closure exists to prevent. The majority also re-read ADR-0002's inline-source precedent more
narrowly than the ticket's framing suggested: ADR-0002 kept media source paths inline because
they are state the *authoring agent* must edit in lockstep with the element that owns them —
splitting them would force the agent to track two files to make one correct change.
Third-party annotation is the opposite case: it is not input to rendering, the authoring agent
does not need it to edit correctly, and nothing breaks if it drifts out of sync. Co-location
was never a principle for its own sake in ADR-0002; it was a principle about state the editing
agent owns, and that reasoning argues for a sidecar here, not against one.

The dissent (industry precedent in OpenAPI/JSON Schema, one-file convenience) is recorded
because it is not baseless — those formats do use `x-` successfully. But they are consumed by
tolerant parsers and carry explicit version fields, so they do not lean on unknown-key
detection as their only versioning signal the way this format does. The convention does not
transfer to a versionless, hand-typo-prone format.

## Consequences

- **Adding an optional key to the schema is a breaking change for older readers.** A file
  written against a schema revision that adds any new key — at any level, including a `run` or
  `keyframe` — fails validation on an older binary that predates that revision. This is the
  intended behavior, not a defect: it is the exact mechanism ADR-0016 relies on to catch
  revision skew, since no version number exists to catch it any other way. It does **not**
  oblige a rewrite of existing, already-valid files — only new files carrying the new key are
  affected on old binaries.
- **Every nested object shape (`run`, `keyframe`, font-table entry) must be fully and
  correctly enumerated in the schema**, with `additionalProperties: false` (or the schema
  language's equivalent) at every level, not only at `project` and each element `type`.
- **No reserved namespace exists for third-party or tooling annotation.** A convention for a
  sidecar file (naming, how it references elements — most plausibly by element id) is not
  specified by this ADR and is left open.
- **`validate` and `render` enforce this uniformly.** An unknown key anywhere in the document —
  regardless of nesting level — is reported and blocks render exactly as ADR-0016's example
  message describes, with the newer-revision/retired-key distinction from ADR-0016 and
  [#78](https://github.com/MBehtemam/Montagent/issues/78) applying equally at every level.

## Not settled here

- **The sidecar file's format and element-reference convention.** Left open; a future ticket if
  third-party annotation becomes a real need rather than a hypothetical one.
- **[#78](https://github.com/MBehtemam/Montagent/issues/78)** — the message-text distinction
  between a newer-revision key and a retired key — is unaffected by this ADR and proceeds on
  ADR-0016's terms.

## Evidence

Grilled per [#75](https://github.com/MBehtemam/Montagent/issues/75); all three sub-decisions
(base policy, scope, escape hatch) were each put to an independent three-model jury (Claude
Opus, Sonnet, Haiku), jurors blocked from seeing each other's ballots. Base policy: unanimous
for closed/error. Scope: 2–1 for uniform closure. Escape hatch: 2–1 against a reserved prefix,
reversing the ticket's own working recommendation.
