A minimal realistic counterexample: source_span=7ms, speed=0.560
  true value 7 / 0.560 .............. 25/2 = 12.5 (an exact half-integer tie)
  exact round-half-up (ties go up) .. 13
  IEEE double: 7 / 0.560 in Python's repr: 12.499999999999998
  float round-half-up ................ 12
  => an element with source_end-source_start=7 and speed=0.560 gets end-start=12
     under naive double division, but the invariant's exact reading demands 13.

== does ADR-0028's tenths-restriction mechanism fix this? ==
  Sweep C measured ZERO divergences for exact-tenths speeds, up to 60s spans.
  This is NOT the same guarantee ADR-0028 gives line_height, and does not
  generalise: exact ties still mathematically exist at tenths (e.g. speed=0.4,
  source_span odd -> source_span/0.4 is always an exact X.5) -- unlike
  line_height, where the fix makes the underlying arithmetic EXACT so no tie
  can ever be perturbed. Here the tie exists but this script measured that its
  IEEE evaluation happens not to cross it in the tested range (spot-checked to
  50,000,000ms/~14h below with the same result) -- an empirical non-occurrence,
  not a proof, because division by a non-power-of-two decimal is never exact.
  It is also moot: ADR-0020 imposes no precision limit on speed, and the
  fixture's own speed (0.645) already needs THREE decimal digits -- at that
  precision (Sweep A) and at hundredths (Sweep B), real divergence is measured.
