# parley silently drops a mandatory `\n` inside Thai, Khmer and Lao

Evidence for [#28](https://github.com/MBehtemam/Montaget/issues/28). Regenerated by
`./run.sh` into `results/hard-breaks.txt`; the two frames are in `frames/`.

**This inverts [#27](https://github.com/MBehtemam/Montaget/issues/27)'s ranking.**

## Why it is the whole ballgame

[ADR-0007](../../../adr/0007-text-runs-literal-size-declared-fonts.md) makes `\n`
**the only line-break mechanism in the format**: *"A run boundary is style-only; a
line break is `\n` inside a run's text,"* under *"No fit-to-box. No automatic
wrapping."* UAX #14 gives U+000A class `BK` — a **mandatory** break, unconditional.

So a stack that drops one is not *worse at Thai*. It cannot render the format.

## The measurement

Laid out with **no box at all**, so only mandatory breaks can apply. Expected line
count is `count('\n') + 1`.

| case | cosmic-text 0.19 | parley 0.11, flag off | parley 0.11, flag on |
| --- | --- | --- | --- |
| latin `AAA\nBBB` | ok | ok | ok |
| **thai** | ok | **DROPPED** | **DROPPED** |
| **thai (2nd string)** | ok | **DROPPED** | **DROPPED** |
| thai font, latin text | ok | ok | ok |
| **thai then latin** | ok | **DROPPED** | **DROPPED** |
| latin then thai | ok | ok | ok |
| **khmer** | ok | **DROPPED** | **DROPPED** |
| **lao** | ok | **DROPPED** | **DROPPED** |
| japanese | ok | ok | ok |
| thai with `\r\n` | ok | ok | ok |
| **thai, two `\n`** | ok | **DROPPED** | **DROPPED** |
| **dropped** | **0 of 11** | **6 of 11** | **6 of 11** |

The `complex-scripts` feature makes **no difference** — this is a second, separate
defect from the one #27 measured, and the 3.82 MB dictionary does not fix it.

The trigger is the character **before** the `\n`: `latin-then-thai` survives,
`thai-then-latin` does not. `\r\n` survives, because CR carries class `CR`
independently.

## It is parley's bug, not ICU4X's

`results/hard-breaks.txt` ends with `icu_segmenter` queried directly, same strings:

    thai     LF at byte  51  boundary at 52? YES   breaks [0, 9, 24, 33, 51, 52, 61, …]
    khmer    LF at byte  36  boundary at 37? YES   breaks [0, 9, 36, 37, 55, 73]

**ICU4X reports the mandatory boundary correctly in all six cases**, including both
the dictionary boundary at 51 and the mandatory one at 52. parley is handed a
correct boundary set and loses the mandatory break on the way to its line breaker.
Not diagnosed further than that — the defect reproduces from parley's public API and
that is enough to act on.

## The frames

Identical string, identical `\n`, identical font, size and box.

**cosmic-text — two lines, as authored:**
![](frames/hardbreak-cosmic-thai.png)

parley renders the same input as **one line 813 px wide**, the `\n` gone with no
error, no warning and no glyph. In a video frame that is a caption that silently
grew past its card.

## What it does to #27

#27 ranked parley above cosmic-text because parley (with `complex-scripts`) offers
Thai break opportunities and cosmic-text offers none. That ranking assumed the
renderer needs break opportunities. Under ADR-0007 it does not — it needs `\n` to
work.

On the capability the format **actually uses**:

- **cosmic-text: correct.** Its zero Thai break opportunities are never consulted,
  because nothing ever wraps.
- **parley: broken**, with or without the 3.82 MB dictionary.

#27's measurements stand. Its *weighting* does not survive #28.

## Not settled here

- Whether parley exposes a supported way to force the break (feeding one paragraph
  per `\n` was not tried, and would be a workaround, not a fix).
- Whether the defect is present in parley versions other than 0.11.1.
- Not reported upstream at the time of writing.
