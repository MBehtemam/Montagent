# parley drops a mandatory `\n` inside Thai, Khmer and Lao — in its default wrap mode

Evidence for [#28](https://github.com/MBehtemam/Montaget/issues/28). Regenerated by
`./run.sh` into `results/hard-breaks.txt` and `results/falsify.txt`.

> **Correction.** The first version of this file concluded *"parley cannot render the
> format"* and that this inverts [#27](https://github.com/MBehtemam/Montaget/issues/27)'s
> ranking. **That was wrong, and the falsification pass below is what caught it.**
> `TextWrapMode::NoWrap` — which is exactly the mode this format calls for — makes
> parley honour the newline correctly. The bug is real; the disqualification was not.
> The original text is in this file's git history.

## Why a dropped `\n` would matter

[ADR-0007](../../../adr/0007-text-runs-literal-size-declared-fonts.md) makes `\n`
**the only line-break mechanism in the format**: *"A run boundary is style-only; a
line break is `\n` inside a run's text,"* under *"No fit-to-box. No automatic
wrapping."* UAX #14 gives U+000A class `BK` — a **mandatory** break. A stack that
drops one silently merges two authored lines into one overflowing caption.

## The measurement

Laid out with **no box**, so only mandatory breaks can apply. Expected line count is
`count('\n') + 1`.

| case | cosmic-text 0.19 | parley 0.11, flag off | parley 0.11, flag on |
| --- | --- | --- | --- |
| latin `AAA\nBBB` | ok | ok | ok |
| **thai** (2 strings) | ok | **DROPPED** | **DROPPED** |
| thai font, latin text | ok | ok | ok |
| **thai then latin** | ok | **DROPPED** | **DROPPED** |
| latin then thai | ok | ok | ok |
| **khmer**, **lao** | ok | **DROPPED** | **DROPPED** |
| japanese | ok | ok | ok |
| thai with `\r\n` | ok | ok | ok |
| **thai, two `\n`** | ok | **DROPPED** | **DROPPED** |
| **dropped** | **0 of 11** | **6 of 11** | **6 of 11** |

The `complex-scripts` feature makes **no difference** — a second, separate defect
from the one #27 measured, which the 3.82 MB dictionary does not fix. `\r\n`
survives, because CR carries class `CR` independently.

### The trigger, corrected

An earlier draft of this file said *"the trigger is the character before the `\n`."*
**Minimal-pair testing falsified that**, and the real condition was not pinned down:

| input | char before LF | result |
| --- | --- | --- |
| `"AB\nC"` | Latin | ok |
| `"กกA\nB"` | Latin | ok |
| `"Aก\nB"` | **Thai** | **ok** |
| `"กก\nกก"` | **Thai** | **DROPPED** |
| `"ฉันแขวน\nBBB"` | **Thai** | **DROPPED** |
| `"กก \nกก"` | space | ok |
| `"\nกก"` | *(LF first)* | ok |

Thai immediately before the LF is **necessary but not sufficient** — a single Thai
character does not trigger it, a longer run does. Whatever the exact condition is, it
was not determined here and the report should say so rather than guess.

**Minimal repro, 13 bytes:** `"กก\nกก"` → parley returns **1 line**, expected 2.

## It is parley's bug, not ICU4X's

`icu_segmenter` 2.x queried directly on the same strings reports the mandatory
boundary immediately after the LF **correctly in all six cases** — for the Thai
string the boundary set contains both 51 (dictionary) and 52 (mandatory). parley is
handed a correct boundary set and loses the mandatory break before its line breaker.
`Line::break_reason()` returns `None`, not `Explicit`, so the boundary is lost rather
than deprioritised.

It is an **untested path upstream**: parley's own mandatory-break tests
(`test_mandatory_break_in_text`, `test_newline`, `test_two_newlines` in
`src/tests/test_analysis.rs`) use `"ABC DEF\nG"` and bare newlines. Nothing exercises
`\n` inside a complex-script run.

## The falsification pass — and what it overturned

`results/falsify.txt`. Every plausible way the harness could be wrong:

| variant | result |
| --- | --- |
| Latin control, same harness | ok — the harness is not simply broken |
| `break_all_lines(None)` / `f32::MAX` / `10000` / `984` | **DROPPED** in all — not a width artefact |
| fonts Ayuthaya / Thonburi / Helvetica / Arial Unicode MS | **DROPPED** in all — not a font artefact |
| `OverflowWrap::Anywhere`, `WordBreak::KeepAll`, `TextWrapMode::Wrap` | **DROPPED** |
| **`TextWrapMode::NoWrap`** | **ok** — 2 lines, `Explicit`, split at the authored `\n` |
| **`WordBreak::BreakAll`** | **ok** — same |

### The jury's strongest objection, answered

Three subagents on three models were asked what would falsify this. Their sharpest
point: *both parley columns are identical, including with the dictionary off — which
is the signature of a harness that built the same configuration twice.*

Answered behaviourally rather than by inspecting build flags. An unspaced Thai
paragraph in a finite 420 px box can only wrap if the dictionary is live:

    complex-scripts=false  ->  1 line   (overflowing; no opportunities exist)
    complex-scripts=true   ->  5 lines  (segmenting)

The two columns are genuinely different builds. The identical hard-break result is a
finding, not a duplicated measurement.

Also cleared from their lists: the input is a literal `0x0A` at byte 51 with no
U+2028 (byte-dumped); the failure survives every finite and infinite width; it is
font-independent across four faces; and cosmic-text is an independent harness over
the same strings that passes all 11.

**`TextWrapMode::NoWrap` is the mode this format wants.** ADR-0007 forbids automatic
wrapping outright, so a Montaget renderer built on parley would set `NoWrap` and never
meet the bug.

## What it actually does to #27 and #7

**It does not invert the ranking, and it does not disqualify parley.** Both stacks can
render the format's Thai correctly. What it adds is a **silent footgun**: parley's
*default* wrap mode discards an authored line break in exactly the four scripts #27
was about, with no error, and upstream has no test that would catch a regression.

The live question for [#7](https://github.com/MBehtemam/Montaget/issues/7) is
unchanged and is #28's answer: under "no automatic wrapping" the renderer never
consults a break *opportunity*, so #27's `complex-scripts` discriminator belongs to
`measure` and authoring-time tooling, not to the renderer choice.

## Not settled here

- Whether the defect is present in parley versions other than 0.11.1.
- Whether `NoWrap` is the *intended* fix or coincidentally masks the bug — it is
  correct output either way, but the mechanism was not diagnosed.
- Whether cosmic-text has an equivalent footgun in some other mode; it was correct in
  all 11 cases in `Wrap::None` and was not swept across its other wrap modes here.
- Not reported upstream at the time of writing.
