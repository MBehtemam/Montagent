# Proxy-resolution preview savings at 4K/8K

Prototype for [#87](https://github.com/MBehtemam/Montagent/issues/87), graduated from
[ADR-0021](../../../adr/0021-preview-budget-and-graceful-degradation.md), part of the map
[#2](https://github.com/MBehtemam/Montagent/issues/2). **Throwaway.** Nothing here is a
proposed design; the scene JSONs are this ticket's fixtures, not a candidate project format.

## Verdict

**A fixed proxy target recovers the < 5 s scrub-preview budget, and #34's "resample
scales with output pixels" finding holds — but only up to a point.** The dominant open
question was whether bilinear resampling cost tracks output pixel count (a fixed target
recovers budget cleanly) or source-decode size/scale ratio (it doesn't). **Both are true,
in different regimes:** resample cost tracks output pixels as the theory predicted, but
**decode cost tracks source size independently of the output target**, and at 8K it grows
large enough to change the answer.

**1080p is not a safe single target.** It recovers budget at 4K (**4.28 s**, 14 % under
budget, `skia-safe`) but **misses it at 8K (5.79 s, 16 % over budget)** — the same target,
the same backend, only the source got bigger. This is exactly the failure mode ADR-0021
declined to guess at: 1080p was the "obvious" number and it is wrong at 8K.

**720p is the smallest single target that clears < 5 s at both sizes, on the load-bearing
backend:** **2.68 s at 4K, 3.78 s at 8K** (`skia-safe`). Below 720p the wall-clock keeps
falling but the *reason* changes: resample cost keeps shrinking with the output, while
decode cost — driven by source size, not target size — stops shrinking and starts to
dominate. At 8K/360p, **decode is 53 % of the frame**, up from 22 % at 8K/native; the same
sweep at 4K only moves decode's share from 15 % to 23 %. **8K's saving ratio does not hold
the way 4K's does** — the ratio is bigger (native is so much slower that any proxy looks
like a huge win), but the *floor under further downscaling* is higher, because the decoder
is chewing on 8K source frames no matter how small the destination is.

**The savings curve justifies at most two tiers below native, not four.** At both sizes,
essentially all the recoverable time is bought by the *first* step (native -> the first
target that clears budget); each further step buys single-digit percent of what's left.
4K: native->1080p saves 11.6 s, 1080p->720p saves only 1.6 s, and the last two steps combined
save under 1 s. 8K: native->720p (the first clearing target) saves 78.6 s; 720p->540p->360p
combined save 1.06 s. A ladder past one degradation step is measurable but not
load-bearing; going all the way to 360p is not worth what it costs the raster budget, and
it costs a lot visually -- see the floor discussion below.

## Method

**All synthetic, explicitly.** No 4K/8K source media exists in this repo (checked: the
`en-halloween-decorating` fixtures are 1536x2720 stills and a 1080x1920 video). Every
still and video source used below is generated by `ffmpeg`'s `testsrc2` filter -- **not
real footage** -- via `generate-media.sh`, run on demand rather than committed (the 8K
video alone is ~80 MB; see "What's committed vs regenerated" below).

Reuses [#34](https://github.com/MBehtemam/Montagent/issues/34)'s compiled `rast-bench`
binary by relative path (`../rust-rasterizer/target/release/rast-bench`) -- **zero Rust
source changes**. The binary's existing `--scale=k` flag already separates the two
variables this ticket needs apart: still-image sampling reads the Ken Burns crop window
in the source file's own native pixel space (untouched by `k`), and only the *destination*
rect scales with `k`; a video clip's decode target (`dw*k, dh*k`) is handed straight to
FFmpeg's own `-vf scale=W:H`, so `--scale=1.0` against a scene whose declared resolution
*is* 4K/8K, with a genuinely 4K/8K source file behind it, is a real decode-at-native,
resample-to-target pipeline -- exactly how a real proxy-resolution preview would work.

### Scenes

Two new scenes, `scene-4k.json` (2160x3840 canvas, 2160x2600 card) and `scene-8k.json`
(4320x7680 canvas, 4320x5200 card) -- true 4K/8K portrait canvases, not `scene-video.json`
upscaled by `--scale=2` (that is what ADR-0021's own 4K pass did, and it's exactly the gap
this ticket exists to close: that pass's video source was still native 1080p). Each scene
carries:

- A full-duration Ken Burns still, generated at exactly the card's native pixel
  dimensions (`testsrc2`, no real photograph exists at this size).
- A video clip from t=5s to t=25s (source entered at 5s into its own file), decoded from
  a genuinely 4K/2160x3840 or 8K/4320x7680 synthetic source -- matching #34's mid-clip-seek
  methodology, scaled down.
- The same title-card/subtitle-box text and rect overlay block #34 measured (`scene-video.json`'s
  t=30.6-42.76s block), kept because on-screen captions are part of the real preview
  workload and #34's own measured block is the most realistic overlay available -- window
  shifted to t=5-20.76s and every coordinate/size scaled x2 (4K) or x4 (8K) from its
  1080x1920 origin.
- 25 s total duration, so the measured window (`--from=10 --to=20`) opens the decoder
  mid-clip, matching #34's t=40 methodology.
- No audio tracks (the source scene's `amix` filter graph divides by the audio count and
  panics on zero inputs; every render below passes `--noaudio`, which does not touch the
  decode/raster/pipe path being measured).

### Scale-fraction precision (a real gotcha, worth recording)

The target resolutions are 1080p/720p/540p/360p, expressed as `--scale` fractions of each
scene's native height (`4K: 1080p=0.5, 720p=1/3, 540p=0.25, 360p=1/6`; `8K` halved again).
**A 6-decimal fraction is not precise enough**: `main.rs` computes `(width as f64 * k) as
u32`, which *truncates*, and `2160 * 0.333333` floors to **719** -- an odd width, which
`ffmpeg -pix_fmt yuv420p` cannot encode, and the encoder dies on a broken pipe. Each
fraction actually used below was hand-verified (`float(s) * w` and `float(s) * h` in
Python, matching Rust's `f64::parse` + cast) to floor to the exact even target on both
dimensions: `0.500000, 0.333334, 0.250000, 0.166667` (4K) and `0.250000, 0.166667,
0.125000, 0.083334` (8K). This is a harness footgun, not a finding about the product.

### Correctness before timing (the #6/#34 ground rule)

| | mean delta/255 | max delta | px differing > 8 |
| --- | --- | --- | --- |
| skia-safe vs tiny-skia @ 4K, t=10 (with video) | 0.018 | 68 | 0.09 % |
| skia-safe vs tiny-skia @ 8K, t=10 (with video) | 0.010 | 70 | 0.04 % |

Consistent with #34's own cross-backend diff magnitudes (0.05-0.07 mean, <0.4% of pixels)
-- both arms render the same scene, frames in `frames/`.

## Results

### 1. The 10 s scrub preview (budget < 5 s), `skia-safe`, at `--from=10 --to=20`

| Target | 4K wall | 4K decode | 4K decode % | 8K wall | 8K decode | 8K decode % |
| --- | --- | --- | --- | --- | --- | --- |
| **native** (no proxy) | 15.88 s | 2.32 s | 14.6 % | 82.40 s | 18.55 s | 22.5 % |
| **1080p** | **4.28 s** (met) | 0.70 s | 16.4 % | **5.79 s** (missed) | 1.05 s | 18.1 % |
| **720p** | 2.68 s (met) | 0.43 s | 16.0 % | 3.78 s (met) | 0.91 s | 24.1 % |
| **540p** | 1.63 s (met) | 0.34 s | 20.9 % | 3.07 s (met) | 1.20 s | 39.1 % |
| **360p** | 1.16 s (met) | 0.27 s | 23.3 % | 2.72 s (met) | 1.44 s | 52.9 % |

Both sizes miss badly at native (**3.2x over budget at 4K, 16.5x at 8K**) -- the mechanism
is needed at both. **1080p is the ADR-0021-cited "obvious" number and it only works at
4K.** At 8K it misses by 16 %.

### 2. Sanity check: `tiny-skia`, same matrix (does the axis change the conclusion?)

| Target | 4K wall | 8K wall |
| --- | --- | --- |
| native | 28.09 s | 118.29 s |
| 1080p | 7.46 s (missed) | 7.58 s (missed) |
| 720p | 4.56 s (met) | 4.91 s (met, 1.8% margin) |
| 540p | 2.22 s (met) | 2.83 s (met) |
| 360p | 1.51 s (met) | 2.41 s (met) |

**No** -- the axis doesn't change which target is the recommended one, but it does narrow
the margin: `tiny-skia` needs 720p at *both* sizes (matching #34's original conclusion
that `tiny-skia` is consistently ~1.7-2x slower and closer to the line), and at 8K/720p
its margin over budget is only 1.8 % (4.91 s vs 5 s) -- too thin to certify as safe without
more samples. `skia-safe` remains the load-bearing backend (per ADR-0009/#34); this
confirms it still is, at these sizes.

### 3. Resident per-frame ablations -- does #34's ~93 % resample finding hold as output shrinks?

`--bench=60`, resident (no process/encoder churn), full frame vs `--notext` vs `--noimage`
vs both, at `t=10` (mid-clip, so a video frame is present in every measurement below --
this scene composites a Ken Burns still **and** a video clip in the same card every
frame, unlike #34's still-only ablation, so the "image resample" line below isolates the
*still's* bilinear resample; the video frame arrives pre-scaled to its dest rect by
FFmpeg's own decode-time `-vf scale`, so its blit cost is comparatively small and mostly
pixel-count-driven memcpy/colour-convert, not resampling):

| | 4K native | 4K/1080p | 4K/360p | 8K native | 8K/1080p | 8K/360p |
| --- | --- | --- | --- | --- | --- | --- |
| full frame | 40.75 ms | 11.02 ms | 2.55 ms | 170.30 ms | 13.05 ms | 6.16 ms |
| ...without text | 41.22 ms | 10.50 ms | 2.41 ms | 166.13 ms | 12.62 ms | 6.10 ms |
| ...without the still | 18.36 ms | 5.39 ms | 2.26 ms | 71.84 ms | 10.83 ms | 5.91 ms |
| ...neither (video+rects only) | 17.08 ms | 5.01 ms | 2.38 ms | 71.28 ms | 10.67 ms | ~5.9 ms (noise) |
| **still's resample, % of frame** | **55.0 %** | **51.1 %** | **11.4 %** | **57.8 %** | **17.0 %** | **4.1 %** |

**#34's finding holds directionally and gets a sharper edge.** At native and at 1080p, the
still's bilinear resample is still roughly half the frame (55%/51% at 4K, 57.8% at 8K
native) -- consistent with #34's ~93% figure once you account for this scene splitting
that cost between a still *and* a pre-scaled video blit (#34's scene had no video in its
ablation). **But the resample share collapses as the target shrinks** -- 11.4% at 4K/360p,
4.1% at 8K/1080p and 8K/360p -- because resample cost scales down with output pixels while
a roughly *fixed* per-frame floor (buffer setup, the pre-scaled video blit, background
fill) does not shrink nearly as fast. Text is confirmed cheap throughout (+/-1-2% noise,
matching #34's 5% finding). **The practical read: at small proxy targets, the bottleneck
stops being "which pixels get resampled" and becomes fixed per-frame overhead plus
whatever the source decode is still costing** -- which is exactly what section 1's
decode-percentage numbers show growing at 8K.

## What this does not settle

- **The floor is a wall-clock proxy, not a legibility measurement.** 360p clears budget
  at both sizes with room to spare (1.16 s / 2.72 s), but this harness only measured time,
  not whether the scene's overlay text (sized for a 1080p-equivalent card, e.g. the 57-80px
  subtitle text here, scaled down to a ~19-27px card at 360p) is still readable. The
  *time* floor and the *visual* floor are different questions; only the time floor is
  answered here. Given how little wall-clock the last two steps (540p, 360p) buy -- under
  a second combined, at either size -- the visual floor is very likely the binding one in
  practice, but that needs a human-legibility pass this ticket didn't run.
- **One clip, one still, one overlay block -- not a heavy composite stack.** ADR-0021's
  degradation trigger includes "a heavy composite stack"; this harness measured one video
  clip over one Ken Burns still with one overlay block, at the two sizes. Multiple
  simultaneous clips/effects would raise the raster (not decode) side of the budget
  further and were out of scope here.
- **Single run, one machine, no repeats.** Matches #34's own practice (wall clock, single
  runs) but variance was not characterized -- the tiny-skia 8K/720p 1.8% margin in
  particular should not be read as reliably safe without more samples.
- **GPU rasterization remains untouched**, as ADR-0021 already notes; nothing here bears
  on it.
- **What's committed vs regenerated:** `scene-4k.json`, `scene-8k.json`, `gen_scenes.py`,
  `generate-media.sh`, `run.sh`, this file, and the correctness-check frames in `frames/`
  are committed. The synthetic `media/` assets (4K/8K stills and video, ~100 MB total,
  dominated by an ~80 MB 8K video) are **not committed** -- `generate-media.sh` (called by
  `run.sh`) regenerates them from `ffmpeg testsrc2` on demand, deterministically enough
  for this harness's purposes (same command, same synthetic pattern; not byte-identical
  across ffmpeg versions, which does not matter for wall-clock measurement).

## Machine and versions

Apple **M1 Pro**, 10 cores, 16 GB, macOS **26.5.2** (Darwin 27.0.0). `rustc` **1.95.0**,
`ffmpeg`/`ffprobe` **8.0.1**. `skia-safe` **0.153.2**, `tiny-skia` **0.12.0** -- same
`Cargo.lock` as #34, unchanged. Same machine as #6, the FFmpeg baseline, and #34. Wall
clock, single runs, matching #34's own stated practice.

## Reproducing

```
./run.sh          # every number above, ~10-12 min (dominated by the two native-8K renders)
```

Or by hand, after `./generate-media.sh` and `cargo build --release` in `../rust-rasterizer/`:

```
../rust-rasterizer/target/release/rast-bench --backend=skia --scene=scene-4k.json \
  --scale=0.5 --from=10 --to=20 --noaudio --out=out/skia-4k-1080p.mp4
```
