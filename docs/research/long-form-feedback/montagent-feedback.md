# Montagent feedback from a long-form production (montagent 0.2.0)

For the Montagent developer and for their coding agent. Everything here comes from one real production run (a 49-minute 1080p video, 88,722 frames) and from measurements taken afterwards. Numbers were measured, not estimated, unless marked **(E)**. A machine-readable copy is in `montagent-feedback.json`; a reproduction kit is in `montagent-repro/` (15 MB, runs in about 3 minutes).

## 0. How to use this document
1. Read section 2 (the one-paragraph result) and section 5 (the user stories, each with acceptance criteria).
2. Run `cd montagent-repro && python3 profile.py` and `python3 video_presence_test.py` to see the same numbers on your machine.
3. Each user story has a measurable acceptance test, written so that an agent can implement it, run the kit, and report pass or fail.
4. Section 7 lists questions only the Montagent developer can answer.

## 1. Who we are and what we build
A small team (one person + an AI coding agent) producing language-learning videos for six YouTube channels. The current product is a calm, hour-long video of a classic story read in a book on a wooden table: Danish text with karaoke highlighting, English explanations, hand-drawn marks (highlighters, circles, arrows, braces, numbers), looping pencil illustrations, animated stickers and channel branding. Montagent is the renderer. The project JSON is generated by Python scripts.

## 2. The result in one paragraph
Rendering Part 1 (2,957 s, 88,722 frames, 1,386 tracks) took 3.24 hours of render time at 7.6 frames per second on a 10-core Apple M1 Pro, using on average **1.2 cores (118% CPU)** and 0.6 GB. In a typical page frame **about 75% of the time is spent on two full-frame, never-changing images** (a table plate and a book plate with a feathered mask); text, marks and shapes together cost 10-15%; masks and shadows cost about 40%. **A single video element anywhere in the project, even one that is not on screen in the rendered range, makes every frame about 4 times slower** (0.026 to 0.12 s/frame in the kit), which suggests that the static-layer shortcut is switched off for the whole project once any video exists. Baking the two background images into one picture ourselves made the same slice **5 times faster** (6.2 to about 32 fps) with a visually identical result. Four renders of different ranges run side by side were only about 15% slower each (3.3x aggregate), so a single render leaves most of the machine idle.

## 4. What works well (please keep it)
- `--progress-file`: one JSON per render with state, phase, frames, fps, ETA, rewritten about once a second. We poll it, build an overall percent across chunks and get a notification per chunk.
- `render --from/--to --output`: exact frame counts; chunks join with stream copy and invisible seams (frame difference across a join about 0.5/255, audio silent).
- `validate`: 3 seconds on a 1,386-track project; the review classes found real problems.
- `frame --full`: we use it to inspect pages and, below, to bake a background.
- Text with `highlight` runs (karaoke), `measure`, `trim_end` on paths, `swivel`/`perspective`, rect/circle `mask`, `blend: multiply`, `overrun: loop`.

## 5. Findings and user stories
Priority: P0 = would change our render times by a large factor; P1 = clear benefit; P2 = quality of life; P3 = to discuss.

### Finding table (3-second slice of a normal page, 90 frames, 0.134 s/frame as built)
| Variant | s/frame | Saves |
|---|---|---|
| drop the table plate | 0.095 | 29% |
| drop the book plate (feathered mask) | 0.054 | 60% |
| drop both plates | 0.021 | 85% |
| drop the picture loop (the only active video) | 0.029 | 78% |
| drop the 2 stickers | 0.131 | 2% |
| picture loop without blend | 0.126 | 6% |
| drop the full-frame fade rectangle | 0.129 | 4% |
| drop all marks (text, rects, paths) | 0.128 | 4% |
| drop karaoke text blocks | 0.130 | 3% |
| strip every effect (masks, shadows) | 0.079 | 41% |
| strip every blend | 0.121 | 9% |
| **baked background (the 2 plates as 1 picture; video still present)** | **0.023** | **83%** |
The kit's `evidence/` folder holds the reference logs. Savings are not additive.
Decisive test (`video_presence_test.py`): picture loop removed (no video left): 0.026-0.031 s/frame. Add one small video element at 2,000 s, outside the rendered 1,500-1,503 s: **0.120-0.125**. Add one small image there instead: 0.027. In the full project (many videos elsewhere in the film) removing the picture loop still leaves 0.126. Audio elements make no difference.

---
### US-1 (P0) Cache static layers across frames
**As** a producer of long videos with a fixed background, **I want** layers that do not change between frames to be rendered once and reused, **so that** a frame costs only what changes.
- Evidence: two never-changing full-frame images cost 75% of every frame; baking them into one picture is 5x faster with an identical result (mean difference 1.5/255, no pixel off by more than 24 levels, which is re-encoding noise).
- Options: (a) automatic: a layer whose pixels do not depend on time (no keyframes on transform/opacity/effects, static source) is composited once together with the static layers below the first changing layer; (b) explicit hint, see US-4.
- Acceptance: on the kit with the unbaked background, `profile.py` "everything" is at most 1.25x the time of the manually baked variant (reference machine: at most 0.030 s/frame, versus 0.134 today); output differs from the current renderer by a mean of at most 2/255 and no pixel by more than 24 (or is bit-identical when caching is off); a layer that has an opacity keyframe is never wrongly cached (frames equal with caching on and off at 20 random times).

### US-2 (P0) The fast path must not depend on whether a video exists in the project
**As** a producer, **I want** static layers cached even when a video (or sticker) is present, **so that** a small picture loop does not make the whole frame expensive.
- Evidence: one small video element anywhere in the project (even at 2,000 s, outside the rendered range) makes every frame 4-4.5x slower; an image does not. Dropping the only active video leaves the slice at 0.026-0.031 s/frame. (Our reading: when no video exists the static layers are reused; any video disables it. Please confirm or correct.)
- Options: composite cached static background + only the layers (or dirty rectangles) that change each frame (the picture loop 740x416, a sticker, the line being read).
- Acceptance: `video_presence_test.py` reports the same time (within 15%) with and without the extra video element; with the picture loop and 2 sticker videos active the kit slice is at most 0.045 s/frame; time grows with the area of the changing layers (a test with the loop at half the area is faster).

### US-3 (P1) Cheap feathered masks and shadows
**As** a producer, **I want** a rect mask with feather (and a drop shadow) on a static element to cost almost nothing per frame, **so that** soft edges do not dominate the render.
- Evidence: effects (masks, shadows) are 41% of the frame; the table plate (no mask) costs 29%, the book plate (mask feather 26) 60%.
- Options: compute the mask alpha once per element and reuse it; cache the masked, shadowed bitmap; separable blur.
- Acceptance: the kit with the unbaked book plate (mask kept) is within 10% of the same slice with the plate baked; a micro-benchmark of 20 shadowed stickers shows the shadow cost per frame at least 5x lower than today.

### US-4 (P1) A "static / cache" hint and group elements
**As** a producer who writes projects with a script, **I want** to mark an element or a group as static (`"cache": true`) and to group elements that share a transform, **so that** I can help the renderer and stop creating one track per mark.
- Evidence: 1,060 marks are 1,060 tracks, layer bands are used to avoid `E-LAYER-TIE`, and every mark gets its own fade keyframes.
- Acceptance: the schema accepts `cache` and a `group` element; a group with opacity keyframes renders the same pixels as the same members with per-element keyframes (mean difference at most 1/255); the 1,060-mark project can be written with at most 40 tracks.

### US-5 (P1) A per-element render profile
**As** a producer, **I want** `montagent render --profile` (or a `profile` verb) to report the time spent per element id, per element type and per effect, plus cache hits, **so that** I do not need 14 test renders to find what costs time.
- Evidence: this analysis needed 14 renders of the same slice.
- Acceptance: JSON output; the listed costs add up to at least 90% of the render time; element ids are the ones in the project file; includes "frames drawn from scratch / frames reused".

### US-6 (P1) Use more than one core inside a render
**As** a producer, **I want** one render to use the machine, **so that** I do not have to split the film into chunks by hand.
- Evidence: one render uses 1.2 of 10 cores; four renders of different ranges ran side by side at 52-54 s each instead of 45 s alone (aggregate 3.3x, memory 0.6 GB each); the intro scene alone runs at 5.8 fps and pages at 7.9 fps.
- Options: `--jobs N` that renders disjoint frame ranges in parallel and feeds one ordered encoder (or concatenates), compositing and encoding on separate threads.
- Acceptance: `--jobs 4` renders the kit slice (and a 60-second range) at least 3x faster than `--jobs 1`; output is identical to `--jobs 1` within the tolerance of US-1; no visible seam (frame difference across a chunk boundary at most 1/255 on average).

### US-7 (P2) A better progress file
**As** a producer who polls it, **I want** a windowed fps (last 10-30 s), a smoothed ETA, and a stall indicator, **so that** estimates stop jumping and a paused machine is visible.
- Evidence: our ETA changed from 3.8 h to 5.2 h to 4.5 h to 3.4 h (actual 3.24 h) because `fps` follows the current scene. The Mac went to sleep during one render: `started_at` and `updated_at` were 9 hours apart while `elapsed_s` was 1,250 s, with nothing in the file saying so. Timestamps are UTC while the machine's clock is local (easy to misread as stale).
- Acceptance: new fields `fps_window`, `wall_clock_gap_ms` (or `state: "paused"` after a `SIGSTOP`/`SIGCONT` or sleep test), `elements_drawn`, `frames_reused` documented and covered by a test that suspends the process for 10 s.

### US-8 (P2) Review noise control
**As** a producer, **I want** to silence or aggregate a review class per project, **so that** real findings stay visible.
- Evidence: `R-KEYFRAME-UNREACHED` 1,470 and `R-EASE-INERT` 1,163 on a project where every mark fades in and out; the one real finding (`R-HIGHLIGHT-UNPAINTED`, a 17 ms karaoke word) is a needle in a haystack.
- Acceptance: a `suppress` list (class, optional element-id pattern) in the project; `validate` prints at most 20 lines for the final project and a count of suppressed findings.

### US-9 (P2) Batch `measure`
**As** a script author, **I want** to measure many texts in one call, **so that** building a project is fast.
- Evidence: our builder calls `montagent measure` thousands of times; building 64 units takes 63 s, almost all of it process starts.
- Acceptance: `measure --batch file.json` (or a daemon/library mode) measures 1,000 texts in under 2 s with results identical to single calls.

### US-10 (P2) Stabilise video clips
**As** a producer using AI-generated clips, **I want** an effect that locks a clip to a reference frame, **so that** drift and slow zoom do not have to be removed outside Montagent.
- Evidence: Veo clips of "a still drawing, camera does not move" drift 2-15% in centre and size (measured: size 205 to 237 px in 4 s). We measure the drawing's ink centre and spread per frame in Python, fit a cubic, re-place each frame with sub-pixel transforms, play forward and back, slow it with frame blending and bake a new mp4. Driving the same correction with keyframed `scale`/`source_time` made the render 3.7x slower.
- Acceptance: an effect `stabilize` (reference: first frame; optional `loop: ping-pong`; `fill: paper|edge`) reduces residual size drift of the test clip from 15% to below 1% with no black edges.

### US-11 (P1 for hosting) Linux, container and hosted rendering
**As** a producer who wants to render in the cloud, **I want** official Linux (x86-64 and ARM64) builds, a container image, clear server-use licence terms and a way to feed many workers, **so that** chunks can render in parallel on GCP or Azure.
- Evidence: one render uses 1.2 cores and 0.6 GB, so a 16-core machine can run about 10 jobs (E); the whole project is about 12 hours of serial rendering today.
- Needs: no GUI dependencies; ffmpeg dependency documented; a content-addressed asset cache (345 MB of assets per part); progress to stdout or a URL; documented tolerance of pixel differences between architectures (same chunk-seam test as US-6).
- Acceptance: the container renders the kit slice on linux/amd64 and linux/arm64 with a mean frame difference to the macOS output below the stated tolerance.

### US-12 (P3) GPU drawing back-end
- Evidence: `ioreg` renderer utilisation averaged 0.3% (max 8%) during a render; the binary has no GPU frameworks linked but contains the strings `webgpu`, `metal`, `vulkan`, `sksl_gpu`.
- Question and acceptance: is a GPU back-end planned or hidden behind a flag? If so, document it; it must be opt-in and pixel-compatible; a useful result is at least 2x on the kit, or an explanation of why not (our cost is redundant per-frame work, see US-1/2, not raw drawing speed).

### US-13 (P3) Encoder options
- Evidence: libx264 `medium` is fixed; the encoder is about 15% of the work (about 0.2 core of the 1.2 used).
- Acceptance: `--encoder`, `--preset`, `--crf` documented, default unchanged; `h264_videotoolbox` selectable for drafts.

### US-14 (P3) Clarify output-file behaviour (unverified observation)
- While timing variants we once wrote several different projects to the same `--output` path and saw implausibly fast timings (about 27 fps for a project that normally runs at 6 fps). We did not capture the exit codes, so this may be our mistake. Please confirm that a render never silently skips work because an output file exists, and document what `--output` does when the file belongs to another project or range.

## 6. Workarounds we use today
- Bake the table and book into one picture (`montagent frame --full` on a project that contains only those two elements) and use it as the only background after the book opens (tested; not yet in the production builder).
- Chunk the film at silent page turns (`--from/--to`), one `--progress-file` per chunk, join with ffmpeg; run chunks side by side (tested at 4 jobs).
- Keep the Mac awake with `caffeinate -dimsu -w <pid>`; check `elapsed_s` against the wall clock.
- Layer bands (marks 40-439, text 450+, stickers 700+) to avoid `E-LAYER-TIE`.
- Stabilise video loops in Python before Montagent sees them.

## 7. Questions only the Montagent developer can answer
1. Is the static-layer fast path real, and is it turned off by any video element in the project (as the decisive test suggests)? Is the check per project, per render range or per frame?
2. Is a Linux build available, and what are the licence terms for hosted/server rendering?
3. Is there a GPU back-end (the binary mentions webgpu/metal/vulkan/sksl_gpu) and can it be enabled?
4. Are masks, shadows and `fit: cover` resampling recomputed per frame? Would a pre-scaled image help (we expect so)?
5. Is intra-render parallelism planned? Any constraint that makes frames dependent on each other (so that `--jobs` would not be safe)?
6. What happens when `--output` names a file written by another project (US-14)?
7. Are pixel results guaranteed identical across macOS arm64 and Linux x86-64/ARM64?
