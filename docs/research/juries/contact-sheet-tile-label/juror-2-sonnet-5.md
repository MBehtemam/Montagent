🗳️ **Juror 2** (Claude Sonnet 5) — **VOTE:**
Q1: (a) gutter strip beneath each tile
Q2: (c) both, with visual treatment (border/tint) load-bearing; document-derived tiles defined by absence of a mark
Q3: Delta (first line full, later lines only entered/left)
Q4: Field list may vary — but only by dropping the optional discriminating field, never the mandatory numeric fields
Q5: Yes, a floor around 9-10px; content that doesn't fit at the floor is truncated/omitted from the label (not shrunk further), pushed to the provenance list
Q6: No — the boundary must stay on the label; if space is short, drop the discriminating field instead (see Q4)
Q7: (c) tool vendors its own UI face for chrome
Q8: The element (not group) with the lowest layer order among those whose presence changed at this run's boundary relative to the immediately preceding run in cut-list order; if only departures occurred (nothing entered), use the lowest-layer-order element among those that departed. If no boundary-adjacent change exists (e.g., the sheet's first tile), fall back to lowest-layer-order non-chrome element in the presence set.

**Reasoning:**
Q1: The 11% gutter is already costed into the 180/140px cliffs and is measured to keep labels legible; burning text onto pixels attacks the very defect class (visual/pixel) the feature exists to protect — an occluding label could itself hide a recolored-text-style defect. Never trade sheet content for label space.
Q2: A text prefix costs width exactly when width is already the scarce, load-bearing resource (per the px-per-char law). A border/tint costs zero label characters and is legible at any tile size, including the 92px sizes where labels degrade toward illegibility — meaning register survives even when the label text doesn't. That makes it load-bearing; a text prefix can be redundant backup only if space allows. Defining document-derived tiles by absence of a mark keeps the "silence reads as coverage" hazard confined to a single, deliberately loud exception (marked synthetic tiles), rather than requiring every real tile to spend width announcing "I am real."
Q3: The whole point of moving the presence set off the per-tile label was to kill the 20x character multiplier; repeating the full set on every provenance line partially reintroduces that inflation at range level too. A delta is cheaper and, because the list is sequential and ordered by tile, still reconstructable without ambiguity — same reasoning that already justified moving off fixed-length full-stack printing.
Q4: Fixed arity guarantees every tile carries index+instant+boundary at consistent size, which the measurements show is the safe, always-legible core (17-27px range). Letting one additional discriminating field appear only when it helps, and drop when it would crater legibility, avoids forcing the smallest type onto the busiest tile purely to satisfy a schema. But arity can't be totally free — the three mandatory fields (Q6) never drop.
Q5: The measurements show fitted-to-width alone is not self-limiting — it reaches 1.4px, "fits" by a geometric definition, and is unreadable. That's precisely the silence-reads-as-coverage failure recreated inside the label itself: an agent sees a labelled tile and assumes attribution succeeded. A floor forces the tool to admit when it can't label safely, which must trigger dropping content, not shrinking below legibility.
Q6: The boundary is upstream-mandated for a stated technical reason (the boundary is meaningful data, distinct from the renderable instant). Eliding it under space pressure reopens a decided question through the back door. Since the optional discriminating field is the one field this brief explicitly treats as elastic (Q4), it's the correct thing to sacrifice first.
Q7: The project's declared font may not render digits/ASCII at all (Thai-only, missing files, display-only faces) — using it for tool chrome risks the label itself being unrenderable, which is worse than any licensing cost. A system font is unpredictable across six platform targets (different fallback metrics change the fitted-width math per platform). Vendoring one known face keeps the px-per-char law measured in this brief actually true everywhere the tool ships.
Q8: The rule must be mechanical, range-independent, and use only already-legal tie-breaks (layer order, not array order). Anchoring to boundary-adjacent presence changes (what specifically entered/left at this run's edge) is a document-derived, non-ranking fact — it's not "interesting," it's structural, satisfying the "no verdict" constraint. Layer order supplies a deterministic tie-break when multiple things change at once. The departure-only case is explicitly handled because a run can be defined entirely by something leaving.

**Trade-offs:** Q1 costs sheet real estate (11% per tile) that could have gone to pixels; accepted because overlay labels would actively harm defect detection. Q2 costs rendering complexity for a color/border system instead of "free" text, and a colorblind or color-flattened render would defeat it — I'd keep a minimal ASCII fallback marker despite the brief not requiring one. Q3's delta costs local readability of any single mid-sheet line (can't tell full state without walking back) — acceptable since the list is machine-readable provenance, not a skim target, and the 20x multiplier is a hard measured cost. Q4's variable arity costs predictability for the calling agent — accepted because rigid full-presence-set arity is exactly what produced unreadable 1.4px type. Q5's floor-with-drop costs completeness on busy tiles, pushing more reliance onto the provenance list — acceptable since attribution is a joint obligation, not solely the label's. Q6 costs available width for the discriminating field on tight tiles — acceptable since the boundary is explicitly mandated and the discriminating field is the explicitly elastic one. Q7 costs a real font-licensing/maintenance obligation — accepted over the alternatives, which risk silently unrenderable or platform-inconsistent labels. Q8 costs implementation complexity (must compute the adjacent run's presence set, not just "uniqueness within sheet") — necessary specifically because the brief proves the simpler "unique to this sheet" rule is range-dependent and wrong.
