# Juror 3 — Fable 5.1

Verbatim ballot. Given [`BRIEF.md`](BRIEF.md) cold, blind to the other jurors and to the
author's recommendations.

---

🗳️ **Juror 3** (Fable 5.1) — **VOTE Q1: (a) — add explicit geometry in v1, minimal and per-shape, all-or-none**

**Reasoning:** The ticket exists to decide the parameter set; ratifying param-less-only is declining the ticket, not answering it. The decisive fact on the record is that an off-centre circle, a rounded-corner rect, and an ellipse narrower than its box are inexpressible by any means today, with no composition workaround, and the project's own rule is that the fixture is never evidence a capability is unneeded. A video editor must express a rounded picture-in-picture; that is table stakes, not speculation. The param-less form also has a reading hazard: its meaning silently changes with `width`/`height`, which is at odds with a file that must be understood by reading. The set I would ratify: all integers in element-local pixels (Q2), fixed arity per shape, and all-or-none — either the bare shape (ADR-0068's inscribed rule, unchanged) or the full tuple: `circle{cx, cy, r}`, `ellipse{cx, cy, rx, ry}`, `rect{x, y, width, height, radius}` with `radius` identity 0. ADR-0049's four clauses transfer cleanly to parameters if "documented identity value" is read as "the inscribed default": fixed arity per shape, bounded integers, identity = the element rect, and not reproducible by composing existing members. Bare vs. fully-spelled is not a union in the ADR-0012 sense: `fmt` preserves presence (ADR-0030), so the zero-hits hazard never arises, and the two spellings are two different declarations (derived vs. pinned).

**Trade-offs:** This is a guess made with zero fixture evidence, and ADR-0068 warned the default is not evidence for the explicit form's shape; the mitigation is keeping the set small and refusing partial tuples (no `cx` without `r`), so there are exactly two arities per shape rather than 2^n spellings. Option (b) is cheaper and safer against a wrong guess, but leaves a hole that can only be filled by mutating the element's rect, which moves the picture — that is a worse outcome than a small, revisable parameter set. Soft/feathered masks stay deferred as ADR-0040 said.

🗳️ **Juror 3** (Fable 5.1) — **VOTE Q2: Element-local; (0,0) is the rect's top-left regardless of `origin`; integers in unscaled `width`/`height` units**

**Reasoning:** Frame-absolute is precisely what `clip` already is, and the glossary says the mask is not that concept; giving the mask frame-space numbers would make it a second clip with a shape, and under a keyframed `x`/`y` the mask would stay put while the picture slid out from under it — which is the porthole behaviour `clip` owns. Element-local also matches every other effect parameter: `blur.radius` and text `stroke_width` are element-space quantities. On the origin: `origin` is a placement anchor for `x`/`y` (ADR-0012), nothing more; letting it move the mask's coordinate origin would create nine coordinate frames per element, make a mask unreadable without cross-referencing `origin`, and mean that changing `origin` (a placement edit) silently rewrites the mask geometry. Top-left-of-rect regardless of `origin` is also what the shipped renderer does, so no golden changes.

**Trade-offs:** An agent must compute element-local coordinates rather than reusing frame numbers it already has, but it always knows `width`/`height`, so the arithmetic is local and trivial. The fixture cannot distinguish the candidates, so the ADR must state this rule explicitly and pin it with a test on a non-`top-left` element, not by assertion (ADR-0075 lesson).

🗳️ **Juror 3** (Fable 5.1) — **VOTE Q3: Pre-transform — the mask rides `scale` and `rotation`; indirect animation via transform keyframes is acceptable and should be stated explicitly**

**Reasoning:** The fixed, non-rotating, non-scaling porthole already has a name and a spelling: `clip`. Making the mask a second fixed porthole would be two spellings of one concept, which this project has retired three times. Riding the transform is also the only reading consistent with the rest of the effect model — `blur` radius and `stroke_width` scale with the element — and with what "mask the picture" means to an editor: a rotated badge with a rect mask should paint a rotated rectangle. The two compose cleanly and cover both intents: `clip` for "window the picture moves behind", `mask` for "shape the picture is cut to". On the keyframe question: "no effect parameter is keyframable" is about the parameters, and the mask's parameters stay constant in element space across every frame; the on-screen geometry changes only because the transform does, exactly as a blur's footprint grows under a Ken Burns. That is not a violation, but the ADR must say so in words, because it is the kind of implicit consequence a reader would otherwise have to infer from the renderer.

**Trade-offs:** A fixed shaped porthole (a non-rectangular window a Ken Burns moves behind) becomes inexpressible with `mask` alone; it is reachable by a shape-element overlay, the same route ADR-0040 assigns to vignettes, so a workaround exists. The vote agrees with the shipped code, but should be ratified by measurement — a golden on a rotated and scaled masked element — not by citing the code, given that an unratified renderer reading has been wrong before.

🗳️ **Juror 3** (Fable 5.1) — **VOTE Q4: (b) — a `review` finding for a param-less `circle` on a non-square rect, specific to `circle`; no finding for `ellipse` or `rect`**

**Reasoning:** `min(width, height)` is determinate and must stay (backward compatibility with ADR-0068 and the committed fixture), so (c) an error and (d) a redefinition are both out: an error would fail a legal, documented meaning, and redefining `circle` on a tall rect as anything other than a circle would make the word lie. But silence is wrong too: erasing 832 of 1912 pixels with no edit to the mask member is a large, silent consequence of the derived default, and it is exactly the case where the author's intent is most likely an oval or an off-centre circle. The concern is `circle`-specific: an `ellipse` inscribed in a non-square rect is an ordinary oval and `rect` is the element's own rect, both plainly intended. With Q1(a) the finding can honestly name a repair — switch `shape` to `ellipse`, or pin the circle with explicit `cx, cy, r` — and because presence is content (ADR-0030), the explicit spelling is itself the author's declaration that the inscribed circle is meant, which silences the finding without a suppression mechanism.

**Trade-offs:** Some noise for authors who genuinely want a centred inscribed circle on a tall image; the cost is one explicit tuple. If Q1 resolves to (b) instead, the only nameable repairs are "use `ellipse`" or "make the element square", which is weaker but still honest, so the finding survives either outcome. The square fixture badge triggers nothing.
