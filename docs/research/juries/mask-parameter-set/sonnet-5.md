# Juror 2 — Sonnet 5

Verbatim ballot. Given [`BRIEF.md`](BRIEF.md) cold, blind to the other jurors and to the
author's recommendations. **This is the dissenting ballot on Q1.**

---

🗳️ **Juror 2** (Sonnet 5) — **VOTE Q1: (b) ratify param-less-only; put explicit geometry in "not yet specified" pending a forcing case**

**Reasoning:** The record has zero evidence for any explicit-geometry shape — the only real instance (the badge) is already fully expressed by the param-less form. ADR-0068 was explicit that admitting `mask` at all rode on one observed authoring gesture, and warned twice against extrapolating from it: once that the full parameter surface is "graduated to its own ticket," and once that the param-less default "is not evidence the explicit form should look any particular way." Manufacturing a parameter set now — centre, radius, corner radii, two axes — with no fixture pressure and no consumer violates the same discipline ADR-0049 embodies for colour filters: don't admit a member (or here, a parameter) until something forces it. The silent-redefinition-on-resize property (Q1's third consideration) is a real cost of the param-less form, but it's a cost of what's already ratified, not a reason to add unmotivated geometry today.
**Trade-offs:** This leaves off-centre circles, rounded rects, and narrow ellipses genuinely inexpressible, with no composition workaround — a real capability gap, unlike the vignette/glow cases ADR-0040 could defer onto other mechanisms. It also means this ticket cannot fully "decide the parameter set" as framed; it can only decide the parameter set for the case that exists (none) and record the shape of the decision procedure for later. That's an acceptable trade given the project's stated principle that primitives are shaped by what a video editor must express, not what one project happens to use, is a two-way constraint — it also means not shaping a member's parameters by what one project happens to *lack*. Option (a) is rejected because it would enumerate fields (centre? radius units? corner radii for `rect` only, or also `ellipse`?) from pure speculation, exactly the "guess at now" ADR-0068 forbade.

🗳️ **Juror 2** (Sonnet 5) — **VOTE Q2: Element-local, origin at the rect's top-left regardless of the element's `origin` keyword**

**Reasoning:** Element-local is required by the one thing already settled: the param-less default is defined against "the element's own rect," not the frame — so the coordinate space for any future explicit parameters must be the same space that default already lives in, or the default's meaning would fork from the explicit form's meaning inside one union member. Frame-absolute would also mean a mask's meaning depends on the element's placement on the frame, which contradicts ADR-0012's "exactly one transform per element... never relative to another element" — masks are effect-layer content, not a second placement system, and `clip` already occupies frame-space as the one deliberately frame-anchored, non-rotating aperture (ADR-0025); duplicating that role for `mask` would blur a distinction the glossary went out of its way to draw. On origin: pinning `(0,0)` to top-left regardless of `origin` matches the shipped renderer's actual mechanism (origin-offset translate happens before effect layers open) and, more importantly, is simpler to state and to reason about from the schema alone — a mask parameter set whose origin silently relocates based on an unrelated field (`origin`, which exists to control *placement*, not *effect geometry*) is one more hidden coupling an agent reading the file would have to hold in its head.
**Trade-offs:** Tying the mask's origin to top-left-always means that changing `origin` (say, from `top-left` to `center`) to reposition an element does not reposition the mask relative to the picture the way a naive reader might expect — an author must remember the mask is anchored to the rect's corner, not to the placement anchor. The alternative (origin follows `origin` keyword) would make mask geometry co-vary with a placement field never designed to carry effect semantics, and would require defining what "origin at center" even means for corner-radius or two-axis parameters — more surface, not less. The fixture cannot distinguish these (Q2's note), so this is argued from the model's internal consistency, not from evidence; a future forcing case could still overturn it, same as Q1.

🗳️ **Juror 2** (Sonnet 5) — **VOTE Q3: Post-transform (the mask rides `scale` and `rotation`) — ratify the shipped behaviour, and explicitly accept indirect keyframe animation of mask geometry as compatible with "no effect parameter is keyframable in v1"**

**Reasoning:** This is squarely a case where the shipped renderer's mechanism, unratified, still deserves adoption on its own logic rather than because it's shipped: effects are stated to run "in element space" and the element's box inside effects is "unscaled units" measured after translate/rotate/scale — meaning every other effect (`blur`, `shadow`, colour filters, text `stroke_width`) already rides the transform as a matter of what "element space" means. Making `mask` alone sit in a transform-immune space would require inventing a second, different effect-space just for one member, contradicting the single per-element transform model (ADR-0012) and creating exactly the kind of inconsistency ADR-0025 avoided by keeping `clip` — the one genuinely fixed porthole — a separate, named, differently-behaved concept. If masks needed a fixed porthole, `clip` already is that porthole; a second one would be a union spelling of the same idea in different clothes. On the keyframe question: `scale`/`rotation` moving a mask indirectly is animation *of the transform*, not of an effect parameter — no effect field itself takes a keyframe list, so the letter of "no effect parameter is keyframable in v1" holds; the mask's on-screen motion is a consequence of the transform system it inherits, the same as it is for `blur` radius or `stroke_width`, both cited on the record as already behaving this way without controversy.
**Trade-offs:** This does make a masked Ken Burns behave in a way an author might not expect on first read — the "porthole" mental model (mask as a fixed window) is intuitive and is exactly wrong for this design. It also means the four-clause discipline for any future explicit geometry parameters must specify units as pre-scale (unscaled element-space), which adds a documentation burden. The alternative — a fixed, non-riding mask — would need its own new mechanism, is unmotivated by any fixture evidence, and is arguably just `clip` under another name, which the project has already rejected as a union spelling (ADR-0068's ruling against admitting both a bare `mask` key and `effects`, and the glossary's explicit warning against conflating the two).

🗳️ **Juror 2** (Sonnet 5) — **VOTE Q4: (b) — a `review`-severity finding when a param-less `circle` sits on a non-square rect, but only if Q1 lands on (b) and the repair it names is "convert to `ellipse`" or "add explicit width/height-equalizing guidance," not a repair requiring parameters this ADR didn't ratify; scoped to `circle` only, not `ellipse`**

**Reasoning:** `min(width, height)` on a non-square rect is determinate but plausibly not what an author meant — 832 erased pixels on a 1080x1912 element is a large, silent effect from a compact spelling, which is exactly the kind of thing a `review` finding exists to surface without blocking it (it's legal, documented, and sometimes intended — e.g., someone genuinely wants a badge inscribed in a tall slot). Silence (a) under-serves an author who wrote `circle` meaning "a circle, sized to something," on a rect where that spelling produces heavy cropping; but promoting it to hard error (c) would punish a form ADR-0068 deliberately kept legal as the *only* spelling. The note's own caveat is decisive on scope: `ellipse` inscribed in a non-square rect is an ordinary, unsurprising oval — there's no reading under which an author is likely to be surprised by it — so a finding there would be noise. `circle` is different because "circle" carries a strong shape connotation (round, not "some conic section") that a silent per-axis squash violates in a way `ellipse` never claims to avoid.
**Trade-offs:** This makes the finding's honesty conditional on Q1: if Q1 is (b), the only "repair" this ADR can name is something like "switch to `ellipse`" (no new parameters exist to name), which is a thin repair — it changes the shape, not just its parameters, so a purist could argue that's not a repair but a rewrite, undermining (b)'s claim to be honest. If Q1 later moves to (a), the repair could tighten to "supply an explicit radius/centre," which is a stronger, more satisfying finding — meaning Q4's answer may need revisiting when Q1 is revisited, which is an acceptable and disclosed dependency rather than a defect in this vote. Option (d) — `circle` meaning something other than the inscribed circle on non-square rects — is rejected outright: it would silently fork the meaning of the already-ratified param-less default across geometries, directly violating the backward-compatibility constraint and ADR-0068's fixed reading.
