# Ballots: the master stage

Two courts on [What is the master stage, where does it live, and what does it hold?](https://github.com/MBehtemam/Montagent/issues/801).
Each had three jurors (Opus, Sonnet, Fable), dispatched in parallel. Each juror got the same
packet blind, with none of the Judge's recommendations in it, and was asked to judge from how
agents actually work with Montagent. The packets are [`QUESTION-ROUND-1.md`](QUESTION-ROUND-1.md)
and [`QUESTION-ROUND-2.md`](QUESTION-ROUND-2.md). Votes are exact. Juror 3's ballots are verbatim; Jurors 1 and 2 are lightly condensed from the full ballots, which were reported verbatim to the owner in session. Both times the
owner ruled with the Judge's read. The decision is
[ADR-0171](../../../adr/0171-the-master-stage-is-a-top-level-loudness-target-and-true-peak-ceiling-reached-by-one-measured-gain.md).

## Round 1 (Q1 to Q4)

| | Q1 normalisation | Q2 location | Q3 contents | Q4 absent |
|---|---|---|---|---|
| Juror 1 (Opus) | (a) target, as measured gain + `alimiter` | (a) `master` | `target_lufs` + `ceiling_dbtp` | (a) |
| Juror 2 (Sonnet) | (b) agent-written `gain_db` | (a) `master` | `gain_db` + `ceiling_dbtp` | (a) |
| Juror 3 (Fable) | (a) target | (a) `master` | `target_lufs` + `ceiling_dbtp` | (a) |

🗳️ **Juror 1** (Claude Opus 5.5) — **VOTE: Q1 (a), implemented as measured gain + alimiter, never loudnorm; Q2 (a) `master`; Q3 `target_lufs` + `ceiling_dbtp`; Q4 (a)**

**Reasoning:**
- **Q1:** Agents edit iteratively — swap a TTS line, retime the bed, change a volume. Under (b), every such edit silently invalidates the stored `gain_db`, and nothing in the file signals staleness; the agent must remember to re-run `verify`, re-measure, and rewrite the gain after every change, and if it forgets, the output is quietly wrong. That is exactly the stale-derived-state failure agents handle worst. `target_lufs: -16` is a literal declaration of intent that stays correct across edits, is `validate`-checkable without rendering, and is one exact-replaceable string. Determinism is an implementation concern, not a schema one: pass 1 renders the whole mix audio-only and measures integrated loudness, then the renderer applies a fixed `volume=xdB` followed by `alimiter latency=1` (when a ceiling is set) — never `loudnorm`, whose silent fallback to dynamic mode makes bytes CPU-dependent. Partial renders and `preview` must use the gain derived from the whole-programme measurement, never from the span alone, so a clip sounds the same in preview as in the final render. `verify` should gain integrated-LUFS and true-peak checks against the declared target so the agent can see the result.
- **Q2:** `master` names precisely the one-stage-on-the-final-mix concept the prior court ruled; `mix` collides with the per-element `amix` mixing and with "a mix" in general; (c) breaks every existing document and conflates a file path with audio processing.
- **Q3:** `target_lufs` serves the lead workflow (TTS narration over a music bed); `ceiling_dbtp` is the safety net, since a fixed gain toward −16 can push peaks over 0 dBFS. Both are literal, closed, and statically checkable. Channel layout stays out: stereo is hard-coded throughout the pipeline and nothing has asked for mono. An `audio_effects` list stays out: the prior court already ruled the master stage is a small closed set, not a general bus with an effect chain.
- **Q4:** Absent `master` means today's behaviour, byte-identical for existing documents, with no surprise processing. Opt-in normalisation keeps the rule simple: what the file says is what happens.

**Trade-offs:**
- **Q1:** Costs a full-programme audio pass before every render, including partials and previews — some latency, but audio-only is cheap next to video. The exact final gain is not in the file; acceptable as long as `verify` and the render log report the applied gain, and the result is deterministic. (b) buys full literalness at the price of permanent staleness; (c) automates writing the same stale number and adds a mutating tool.
- **Q2:** `master` borrows a little music-production jargon, which is fine. `mix` is ambiguous; (c) breaks compatibility for nothing.
- **Q3:** No mono output and no whole-mix EQ or compression yet. Either can be added later as its own closed key; a general effect chain could not easily be taken back out.
- **Q4:** Documents without `master` can still clip, as they do today. A default ceiling would avoid that, but it changes every existing render and adds processing nothing in the file mentions.

🗳️ **Juror 2** (Claude Sonnet 5.5) — **VOTE: Q1 (b); Q2 (a); Q3 `target_lufs` + `ceiling_dbtp` rejected as framed — hold `gain_db` + `ceiling_dbtp` only; Q4 (a)**

**Reasoning:**
- **Q1:** (b) is the only option that keeps the standing invariants. The document holds a literal `gain_db` that `validate` can check without painting a frame and the agent can edit by exact-string replace. (a) puts a measured result inside the renderer: the effective gain exists nowhere in the file, so agents can't see it, `validate` can't check it, and partial renders and `preview` wouldn't match the full render. A first-pass measurement depends on the whole mix, but a partial render mixes only `[from, to)`, so a `target_lufs` stage would sound different in a partial than in the final. With (b), the written gain is the same in every render mode. (c) puts a write tool in front of (b): a second authoring path for no gain. The agent already runs `verify`, reads the number and edits a string; if `verify` gains an integrated-LUFS and true-peak finding, that loop is complete and cheap.
- **Q2:** (a) `master`. Additive and optional, so nothing breaks; it matches the prior court's "one master stage on the final mix" and names the thing precisely. `mix` is vague: the mix graph already uses `amix`, and "mix" suggests a bus. (c) breaks every document, and `output` is a plain path string agents edit by exact replace today.
- **Q3:** The closed set should be `gain_db` (the Q1(b) correction) and `ceiling_dbtp` (a deterministic `alimiter` at `latency=1`, no added delay). `target_lufs` should not be in the stage if the stage applies gain by measurement; it could exist only as a declared goal that `verify` checks, never as something the renderer reaches, and a checked-but-inert value invites confusion about whether it acts. Channel layout is hard-coded today and belongs to a separate decision. An `audio_effects` list would turn the stage into the general bus the prior court rejected.
- **Q4:** (a). An absent `master` must mean today's behaviour, byte-identical. A default ceiling would silently change every old document's output and hide clipping that `verify` should report.

**Trade-offs:**
- **Q1:** (b) costs the agent an extra render-and-`verify` round: pass 1 is a full audio render, and the correction is applied by hand. Landing within about 0.1 LU may take two passes, and nothing stops a later edit drifting the loudness until the agent re-verifies. I accept that because it is visible and deterministic. (a) hides a measurement pass, risks `loudnorm`'s dynamic fallback whose output varies by CPU, and breaks partial-render parity. (c) adds a tool path with no new capability.
- **Q2:** `master` is less generic than a bus, which is intended; the cost is one new top-level key.
- **Q3:** Without `target_lufs` the document carries no stated loudness goal; the agent keeps it in its own notes, or `verify` needs another way to flag a mismatch. No channel layout and no effects means mono output and whole-mix EQ or compression need a later decision.
- **Q4:** With no default ceiling, a careless document can still clip, with only `verify` as protection. I chose byte-identical backward compatibility over automatic safety, because the safe ceiling is one explicit line, `master: {ceiling_dbtp: -1}`.

🗳️ **Juror 3** (Fable 5.1) — **VOTE: Q1 (a); Q2 (a) `master`; Q3 `target_lufs` + `ceiling_dbtp` only; Q4 (a)**

**Reasoning:**
- **Q1 (a).** `target_lufs: -16` is the authored intent, written as a literal, closed-vocabulary, exact-string-replaceable value, and `validate` can range-check it from the file alone. The renderer reaching the target (pass 1 measures the full mix audio-only, then `volume=xdB` + `alimiter latency=1`) is deterministic on any CPU per the ffmpeg facts, so it does not break reproducibility the way `loudnorm`'s dynamic fallback would. Options (b)/(c) store a *derived* number: `gain_db` is correct only for the mix as it existed when `verify` was last run, and the agent's actual loop is edit element → re-render, so every element edit silently stales the gain. That turns one authored choice into a chore the agent must remember to redo, and it leaves the document lying about its own loudness. The one implementation requirement for (a): partial render and `preview` must measure the *whole* programme in pass 1 (not just `[from, to)`) so the applied gain is identical across spans, otherwise previews would not match the final render. `verify` should additionally report measured integrated LUFS and true peak so the agent can confirm the target was hit.
- **Q2 (a).** `output` as an object breaks every existing document for no gain; rejected outright. Between `master` and `mix`: `mix` already names the per-element graph and `amix` in the renderer's vocabulary and would be ambiguous in docs and findings; `master` matches the prior court's "one master/output stage" language and the industry term for the final stage. Top-level, optional, sibling of `output`, holding only the small closed set below.
- **Q3 `target_lufs` + `ceiling_dbtp`.** These are exactly the two things the final stage uniquely can do (integrated loudness is a whole-programme property; true-peak is a whole-mix property), they carry ADR-0170 unit suffixes, and both are validate-checkable without painting a frame. An `audio_effects` list on the master is the "general bus with an effect chain" the previous court already ruled out, and EQ/compression on a TTS-over-music mix is better expressed on the elements where the agent can reason about it. Output channel layout is an *output format* property (like sample rate and codec, currently hard-coded), not master processing; if mono ever matters it belongs with the output settings, not here. Both keys should be independently optional; `validate` should warn when `target_lufs` is set without `ceiling_dbtp`, since a gain-up without a limiter can clip.
- **Q4 (a).** Absent `master` means today's graph, byte-identical. An always-on default ceiling would change every existing document's output, would be behaviour not written in the file (violating "every authored choice has its own string"), and would make a `verify` finding about clipping unexplainable from the document. Clipping is already documented renderer behaviour; the fix is for the agent to add `master: { ceiling_dbtp: -1 }`, which is one exact-string insert.

**Trade-offs:**
- **Q1:** (a) costs a full-mix audio-only measurement pass on every render and preview, and the first partial-span preview may feel slower. It also means the exact gain is not visible in the file (though `verify` reports it). I accept this because audio-only ffmpeg passes are cheap next to video encode, and the alternative (b)/(c) puts a stale derived value into a document whose invariants are about authored intent; (c) additionally adds a write tool that must be re-run after every element change, which is precisely the kind of hidden coupling exact-string editing agents get wrong.
- **Q2:** `master` risks being read as a general "mastering" bucket later; mitigated by keeping it a closed set in the schema. `mix` would have been shorter but collides with existing terminology. (c) is strictly worse: a migration for everyone to gain a nesting level.
- **Q3:** Leaving out an `audio_effects` list means a whole-mix compressor is not expressible; that is a deliberate limit per the prior ruling, and element-level effects plus the limiter cover the narrated-over-bed workflow. Leaving out channel layout means mono output is still unsupported; that is a separate output-format capability and should not ride on this one.
- **Q4:** (a) means new agents can ship a clipping mix if they never set `master`; the cost is a `verify` finding (true-peak over 0 dBTP) rather than silent protection. (b) would buy "nothing clips" at the price of changing existing renders and introducing invisible behaviour, which is worse for an agent that debugs by reading the file.

### The Judge's read (round 1)

Q2 and Q4 unanimous. On Q1, Juror 2's partial-render and `loudnorm` objections do not hold
against (a) as Jurors 1 and 3 specified it (whole-programme measurement; measured gain plus
`alimiter`, never `loudnorm`). Its surviving point, that the applied gain is not in the file, is
answered by `render` and `verify` reporting the measured loudness and the gain applied. Read: (a),
`master`, `target_lufs` + `ceiling_dbtp`, absent means today's graph. The owner ruled with it.

## Round 2 (Q5 to Q9)

| | Q5 target without ceiling | Q6 limiter loss | Q7 verify | Q8 near-silent mix | Q9 validate ranges | Q9 review thresholds |
|---|---|---|---|---|---|---|
| Juror 1 (Opus) | (b) | (a) | (b), review | no gain + finding; full gain, finding above +20 dB | target [−40, −5]; ceiling [−9, 0] | target > −9 or < −31; ceiling > −1; ceiling − target < 5 dB |
| Juror 2 (Sonnet) | (b) | (a) | (b), review | (a) + finding when very large (~+20 dB) | target [−40, 0]; ceiling [−20, 0] | target > −9 or < −30; ceiling > −1 |
| Juror 3 (Fable) | (b) | (a) | (b), review | no gain + finding; full gain, finding above +12 dB | target [−40, −5]; ceiling [−12, 0]; error if target ≥ ceiling | target > −14 or < −27; ceiling > −1; ceiling − target < 6 dB |

🗳️ **Juror 1** (Claude Opus 5.5) — **VOTE: Q5 (b); Q6 (a); Q7 (b), review (never error); Q8 (c): undefined loudness → no gain + review finding; defined → full gain + review finding above +20 dB, never capped; Q9 validate target_lufs ∈ [−40, −5], ceiling_dbtp ∈ [−9, 0]; review when target > −9 or < −31, when ceiling > −1, and when target_lufs − ceiling_dbtp > −5 dB (heavy limiting likely)**

**Reasoning:**
- Q5: At `validate` time the renderer has not measured the mix (that is pass 1), so it cannot know whether the gain will be positive. A target with negative gain, or a modest positive gain on a quiet mix, is legitimate; an error would block valid documents. An implicit ceiling (d) breaks ADR-0145: the file would no longer say literally what happens. A review finding fits: the clipping risk is real but not certain, and it points the agent to a one-line fix (`ceiling_dbtp: -1`).
- Q6: One fixed gain is deterministic and explainable: the applied gain is a number `render` reports and the agent can reason about, and partials and `preview` get the same result from the same measurement. A compensation pass turns `target_lufs` from "gain computed to this target" into a closed loop and adds a whole-programme pass to every render. `verify` reporting −14.6 vs −14 tells the agent exactly which knob to turn: ease the ceiling pressure or lower the target.
- Q7: Measurements cost almost nothing, and an agent needs them even without `master` — that is how it learns whether it needs one. Findings only against values the document sets, so nothing is judged against a threshold the author never chose. A miss is review: `verify` runs after the deliverable exists, so an error blocks nothing, AAC can push true peak a little past the ceiling, and the tolerance belongs to the separate ticket.
- Q8: With everything gated out, no gain is the only defined behaviour; a review finding explains why. For defined loudness the target is literal, so apply the full gain. A silent cap (b) quietly misses the target with no trace in the file. Instead, a review finding above +20 dB ("raising noise floor; check the source or lower the target") and the agent decides.
- Q9: Validate ranges cover every real-world target (broadcast −23/−24, streaming −14/−16, podcast −16/−19, cinema-ish −27 to −31) while catching typos and sign errors (`14`, `-140`). Above −5 LUFS or 0 dBTP is nonsensical for delivery. Review thresholds mark legal-but-unusual territory: louder than −9 (brickwalled), quieter than −31, a ceiling above −1 dBTP on lossy AAC (the precedent's guidance), and a target-to-ceiling gap under about 5 dB, which predicts the Q6 shortfall before rendering.

**Trade-offs:**
- Q5: Agents that ignore review findings can still ship clipped audio — accepted, because (a) blocks valid cases, (d) hides behaviour, and (c) wastes a cheap, checkable warning.
- Q6: Delivered loudness can sit below target under heavy limiting — accepted for determinism and one fewer pass. (c) makes render time unbounded and opaque.
- Q7: A loudness analysis per `verify` run is cheap. (a) hides useful data from agents with no `master` yet. An error would contradict the tolerance ticket and fire after the fact anyway.
- Q8: A large gain will raise the noise floor if the agent ignores the finding. A cap makes `target_lufs` mean "target unless the renderer disagrees", against literal values, and would need its own report and threshold debate.
- Q9: The numbers are borrowed conventions, not certainties, which is why they are review rather than errors. Wider validate ranges let typos through; narrower ones refuse legitimate creative or cinema targets.

🗳️ **Juror 2** (Claude Sonnet 5.5) — **VOTE: Q5 (b); Q6 (a); Q7 (b), a miss is a `review` finding, not an error; Q8 (a) with a review finding when the gain is very large; Q9 `target_lufs` −40 to 0 LUFS, `ceiling_dbtp` −20 to 0 dBTP, plus review thresholds**

**Reasoning:**
- **Q5:** A target with no ceiling is legitimate: mixes that are already quiet, or that need attenuation, can't clip. `validate` can't know whether the gain is positive without pass 1, and ADR-0145 says `validate` works from the file and probed assets alone, so it can't be an error. A `review` finding fits: the threshold is borrowed and the call is a judgement. It fires when `target_lufs` is set and `ceiling_dbtp` isn't, and mentions −1 dBTP as the usual lossy-delivery guidance. (c) hides a real clipping risk; (d) is hidden behaviour that breaks literal values and that an agent editing by exact-string replace couldn't see.
- **Q6:** One gain, no compensation: deterministic, cheap, and partials and `preview` stay consistent with the whole-programme gain. `render` and `verify` already report pre-gain loudness and applied gain, so a limiter shortfall is visible, and the agent fixes it by changing `target_lufs`, the ceiling, or the mix. (b) adds a third pass; (c) is harder to predict and breaks the same-sound-in-partials guarantee.
- **Q7:** Always report the deliverable's integrated LUFS and true peak, even with no `master`, as a baseline before the agent picks a target. Findings only against values `master` sets. A miss is a `review` finding, because the tolerance is set elsewhere and the AAC re-encode adds measurement noise. A true-peak overshoot beyond a margin is a stronger finding but still review, since AAC inter-sample peaks can exceed the ceiling slightly and the deliverable remains usable. `verify` inspects the deliverable and can't make the document "wrong".
- **Q8:** Undefined loudness: no gain, plus a `review` finding that loudness couldn't be measured. Defined loudness: full gain. A cap (b) would make the result differ from the literal `target_lufs`. Instead, a `review` finding when the required gain is very large (above about +20 dB) warning that the noise floor will rise; the cap is advisory, not applied.
- **Q9:** `target_lufs` in [−40, 0], `ceiling_dbtp` in [−20, 0]; outside is a `validate` error, since a positive LUFS target or positive true-peak ceiling can't be delivered. Review thresholds: `ceiling_dbtp` above −1 (lossy risk); `target_lufs` above −9 or below −30 (outside broadcast and streaming norms). A target within about 1 LU of −23, −24, −14 or −16 raises nothing, so common cases stay quiet.

**Trade-offs:**
- **Q5:** (b) costs a finding each time the ceiling is deliberately omitted. (a) rules out a valid case and needs data `validate` lacks; (c) is quiet but risky; (d) is surprising.
- **Q6:** (a) can leave delivered loudness slightly short. (b) and (c) cost render time and complexity for a small accuracy gain the agent can already make.
- **Q7:** (b) does some work with no `master`, cheap and useful. (a) hides the baseline. An error would fail a render over a lossy-encode effect the agent can't fully control.
- **Q8:** (a) can produce a loud noise floor if the finding is ignored. (b) silently deviates from the document; a hard cap is a hidden constant agents can't see in the file.
- **Q9:** Generous ranges so real uses (broadcast, streaming, podcast, music) pass; review thresholds are borrowed convention, which fits ADR-0061's definition of a `review` finding.

🗳️ **Juror 3** (Claude Fable 5.1) — **VOTE: Q5 (b); Q6 (a); Q7 (b), review finding; Q8 (c): undefined → no gain + finding, defined → full gain, finding when gain exceeds +12 dB, no cap; Q9 `target_lufs` ∈ [−40, −5], `ceiling_dbtp` ∈ [−12, 0], error if `target_lufs >= ceiling_dbtp`; review when target > −14 or < −27, ceiling > −1, or ceiling − target < 6 dB**

**Reasoning:**
- Q5: The master ruling already made both keys independently optional, so (a) would relitigate it; and `validate` cannot know whether the gain will be positive without pass 1, so an unconditional "target requires ceiling" rule would reject documents that are fine (a −23 target on a hot mix is pure attenuation). (d) is a hidden value, contradicting ADR-0145 (literal values, nothing the agent cannot read from the file). (c) hides the one real hazard, since lossy AAC delivery makes clipping likely once gain is positive. (b) is exactly ADR-0061's shape: a borrowed-threshold judgement call. The finding text should name the fix literally ("add `ceiling_dbtp: -1`") so the agent can apply it by exact-string replace. Combined with Q7(b), the agent then sees the actual true peak after render anyway.
- Q6: One gain is the invariant that makes partial renders and `preview` sound like the final: every span uses the same whole-programme number. A post-limiter correction (b) changes that number after the fact, and (c) makes it a function of iteration count. A miss from heavy limiting is also diagnostic, not a bug to paper over: it says the target/ceiling pair is unrealistic for this material, and the agent should lower `volume` on the loud elements rather than have the renderer push harder into the limiter, which only trades a 0.6 dB miss for more distortion. The miss is visible through `render`/`verify` reports, and the tolerance ticket decides whether it counts.
- Q7: Measurements should always be reported, because an agent authoring without `master` still needs to know what it produced (the typical first iteration is "render, read the LUFS, then decide whether to add a target"). Findings only against values the document actually sets, because a finding needs a stated expectation to compare with. Severity: review finding. The document is not wrong (it validated), a deliverable exists, and even a true-peak miss can arise legitimately from AAC inter-sample peaks after a correctly-applied `alimiter`. An error would make `render` refuse something it already produced.
- Q8: Undefined loudness (all blocks gated) → gain 0, deliverable unchanged, finding "integrated loudness undefined, no gain applied". Defined loudness → apply the full gain; a target is defined as something the renderer reaches, and a silent cap (b) makes the renderer sometimes ignore the document with no literal in the file saying so. Instead flag it: when the applied gain exceeds +12 dB, emit a finding ("gain +36 dB applied; the mix is far below target, raise element `volume` or lower `target_lufs`"). Note both findings are necessarily emitted at render/verify time, not by `review` on the document, since they depend on the pass-1 measurement; the question's "review finding" should be read that way.
- Q9: Validate ranges are wide enough for every known practice (−24 broadcast, −14/−16 streaming, −9 loud masters, −5 as an absolute sanity bound; ceilings from 0 down to −12 for conservative broadcast chains). `target_lufs >= ceiling_dbtp` is a hard error because integrated loudness cannot exceed true peak (a full-scale sine measures about −0.7 LUFS), so the target is unreachable: that is checkable from the file alone. Review thresholds encode the borrowed norms: target louder than −14 is above every platform norm, quieter than −27 is below every broadcast norm (likely a typo or confusion with dBFS); ceiling above −1 dBTP contradicts the lossy-delivery guidance given AAC 160k; headroom under 6 dB between ceiling and target guarantees heavy limiting (mastered material rarely has a peak-to-loudness ratio below that), which is exactly the Q6 miss scenario the agent should be warned about before rendering.

**Trade-offs:**
- Q5: A review finding can be ignored, so some deliverables will clip; the cost is accepted because the alternative (error or implicit value) either breaks the "independently optional" ruling or hides a value. Agents working from findings will add the ceiling on the next edit.
- Q6: Delivered loudness can sit a fraction of a dB under target on heavily limited material. Costs of (b) are a third full audio pass plus a gain that differs between the pass partial renders used and the final; (c) adds unbounded render time and no guarantee of convergence under a limiter.
- Q7: Always measuring adds a loudness/true-peak scan to every `verify` even with no `master`, which is cheap relative to rendering. A finding rather than an error means a missed target does not block delivery; that is intended, since the target is reached by construction and misses come from limiting or encoding.
- Q8: An uncapped gain can raise a noise floor by 30+ dB; the finding plus the reported gain make that visible, and the cure is in the document (`volume`, `target_lufs`), where the agent edits anyway. A cap would need its own literal and would quietly miss the target.
- Q9: Every threshold here is borrowed (platform guidance, broadcast specs), so none belongs in `validate` beyond physical impossibility; keeping them in `review` means a deliberate −9 LUFS or 0 dBTP choice still renders. The cost is a few extra findings an agent must consciously dismiss on unusual projects.

### The Judge's read (round 2)

Q5 (b), Q6 (a) and Q7 (b) with a miss never an error: unanimous. Q8 agrees on everything but
the threshold; read +20 dB (two jurors), since +12 would fire on ordinary quiet TTS mixes.
Juror 3's catch is adopted: Q7's misses and Q8's findings depend on the pass-1 measurement, so
they are `render`/`verify` findings, not document-level `review`; Q5's finding and Q9's
thresholds stay document-level. Q9 read: `target_lufs` ∈ [−40, −5] (two jurors), `ceiling_dbtp`
∈ [−12, 0] (the middle proposal); review when the target is louder than −9 or quieter than −31,
the ceiling is above −1, or headroom (ceiling − target) is under 6 dB. Juror 3's hard error for
target ≥ ceiling is dropped: its premise is shaky (a full-scale sine on both stereo channels
measures about 0 LUFS, not −0.7) and the headroom finding covers the case. The owner ruled
with it.
