🗳️ **Juror** (Claude Sonnet 5) — **Q1 VOTE: (c) a `MUST` that some tool actually checks compliance against**

**Reasoning:** The incident shows exactly why (a) and (b) fail: the convention existed, was even predicted to break by another agent, and still broke — because nothing checked it. Every agent in this system edits by exact-string replace, and that convention is not a style preference, it's a load-bearing precondition for every future edit to succeed. A rule that other tooling structurally depends on but that nothing verifies is a latent outage, not a convention. Folklore (a) already failed once, silently, and was only caught because a human/agent happened to notice the file ballooned from 154 to 1595 lines — a more subtle key-reorder with the same line count would sail through undetected. A documented SHOULD (b) doesn't change that outcome; the offending agent "reported no schema errors" and was correct by the letter of every existing rule, which is precisely the failure mode a SHOULD leaves in place.

**Trade-offs:** Enforcement costs a real implementation and maintenance burden, and it risks becoming the "noisy check that fires on the majority of correct files" the document warns against elsewhere — if built carelessly. But that risk is a reason to design the check well (see Q3), not a reason to leave the requirement unchecked. Option (b) is cheaper to ship but has already been tried in effect (an unenforced expectation) and failed under real use.

🗳️ **Juror** (Claude Sonnet 5) — **Q2 VOTE: a separate canonical order per element `type`**

**Reasoning:** The stated purpose of the key-order rule is narrow and mechanical: make a unique, matchable substring exist so exact-string replace works reliably. A single global order applied to "whatever keys happen to be present" doesn't serve that purpose any better than a per-type order does — but a per-type order serves it *more precisely*, because different element types (image, video, audio, text, rect, ellipse) plausibly have different natural/primary fields (e.g., text likely has a `content` or `text` field with no image analogue; rect/ellipse likely share geometry fields video/audio don't have). Forcing one global sequence onto heterogeneous key sets means either padding the sequence with irrelevant type-specific keys interleaved awkwardly, or having the "effective" order for any given element be an arbitrary-looking subsequence of a list that was never designed with that type in mind — which makes the convention harder to hold in a human or agent's head and easier to violate by accident. A per-type canonical order lets each order be legible on its own terms (e.g., `type, id, track, start, duration, ...type-specific fields...`), which is easier to document, easier to check, and easier for an agent to reproduce correctly when authoring a new element by hand.

**Trade-offs:** Per-type ordering means six schedules to define and maintain instead of one, and a shared-key prefix (id, type, track, start) needs to stay consistent across all six to avoid the schedules feeling arbitrary relative to each other — that's extra design discipline, not extra runtime cost. A single global order is simpler to state and implement (one array, one comparator) but pushes the complexity onto every element that doesn't use all the keys, which is the common case here, not the exception.

🗳️ **Juror** (Claude Sonnet 5) — **Q3 VOTE: both**

**Reasoning:** These two placements answer different questions and neither substitutes for the other. `fmt --check` is opt-in — something "you have to remember to invoke" — and the material explicitly frames unremembered invocation as the failure mode of interest (the incident agent wasn't running a check, it was doing a routine edit that happened to reformat). Placing the check only in `fmt --check` reproduces exactly the gap that caused the incident: the tool that would have caught it is one more thing nothing forces anyone to run. `validate`, by contrast, already runs unconditionally on every file, including ones nobody ran `fmt` on — which is exactly the coverage this needs, since the incident file was never intentionally formatted at all, it was reformatted as a side effect of an unrelated edit. Only `validate` catches that shape of failure. `fmt --check` still earns its place as a fast, local, pre-commit-style tool for an author who wants to confirm before landing a change, and as a mechanism *some* tool needs to actually implement the check both places call into agreeing on the same rule.

**Trade-offs:** Adding the check to `validate` risks making it the "noisy check that fires on the majority of correct files" its own governing principle warns against, *if* most legitimately-produced files don't match the canonical order — that risk has to be managed by making the canonical order match what the standard writing path already produces, not by leaving `validate` blind to key order. Implementing in both places also means keeping the two checks (and their shared rule) in sync, which is a small maintenance cost against the alternative of a known, already-demonstrated gap.

🗳️ **Juror** (Claude Sonnet 5) — **Q4 VOTE: split `fmt` into a non-destructive check mode and a separate rewriting mode**

**Reasoning:** The concern in #61 is concrete and already identified, not hypothetical: a single `fmt` invocation could combine a key-reorder and a default-materialization in one pass, producing a diff whose size and content conflate two independent, separately-justifiable changes. That's a real cost for an agent-authored, exact-string-replace-dependent file format, where the whole discipline of the system depends on changes being legible and minimal — a large diff that mixes unrelated rewrites is exactly what makes review (by a human or another agent) unreliable, and unreviewed changes are how the original incident's category of failure gets normalized rather than caught. A check mode that shows what would change before anything lands costs little to add relative to a rewriting mode that has to exist anyway, and it directly serves the stated purpose of `validate`-adjacent tooling in this document: giving accurate signal without asserting more than is true. This isn't unnecessary caution; the document already flags the compounding-diff problem as a real finding (#61), not a speculative one — the split is the natural mitigation to a documented risk.

**Trade-offs:** Maintaining two modes (or a single tool with a flag that changes its fundamental behavior from read-only to mutating) is more surface area than one mode that always writes, and if the check output isn't kept honestly in sync with what the write mode actually does, the check becomes a false promise that's worse than not having one. It also doesn't fully solve the "two changes at once" problem by itself — an author could still run the rewriting mode and get both changes bundled — so this only helps to the extent authors are expected to use the check mode first, which is a workflow discipline outside what the split itself can guarantee.
