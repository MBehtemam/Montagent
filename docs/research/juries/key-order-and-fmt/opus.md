🗳️ **Juror** (Claude Opus 5) — **Q1 VOTE: (c) a `MUST` that some tool actually checks compliance against**

**Reasoning:** The layout is not cosmetic here — it is the substrate every editing agent depends on. Exact-string replace is the only edit mechanism in play, and it has a hard precondition: a unique, stable matchable substring. A convention that carries a real precondition for correctness but is enforced by nothing is not a convention, it's a shared assumption, and the incident proved exactly how shared assumptions die: an agent did the forbidden thing, reported "no schema errors," and was *right by the letter of every rule*. That is the definitive argument for (c). Options (a) and (b) both leave the same hole open. (b) is strictly worse than (c) and barely better than (a), because a `SHOULD` with no checker gives the reviewer a rule to cite after the damage and gives the writer nothing at the moment it matters. Note also that the failure mode is silent and delayed: the reformat itself looks fine and passes review as "just formatting"; the breakage surfaces later as a zero-hit replace in a different session, where the cause is no longer visible. Silent, delayed, correctness-bearing failures are precisely the class that must be mechanized rather than remembered.

**Trade-offs:** (c) costs a real implementation and it makes some legal JSON rejected — a file that means the right thing can now fail. That is a genuine cost and should be named honestly rather than waved away: the project is choosing to narrow "legal" from "correct JSON" to "correct JSON written the one way agents can edit." The cost is acceptable because the narrowing is deterministic and machine-repairable — a formatter can always produce the compliant form, so the failure is never a dead end, only a "run the formatter" instruction. The other cost is that a `MUST` needs an owner: the rule and the checker must ship together, or you get the worst outcome, a `MUST` nobody verifies, which teaches agents that MUSTs are advisory.

🗳️ **Juror** (Claude Opus 5) — **Q2 VOTE: A separate canonical order per element `type`**

**Reasoning:** The purpose of the canonical order is to make a human- and agent-legible file whose lines are predictable and diff-stable. A per-type order serves that purpose better because element types genuinely differ in what matters: a `text` element's content and typography are its identity, a `video` element's source and in/out points are, a `rect`'s geometry is. A single global sequence must be some compromise ordering over the union of all keys, which means for every individual type the important fields land wherever the union happens to put them. Crucially, the two designs are equally strong on the *mechanical* requirement — determinism — so the tiebreak should go to legibility, and per-type wins that. A global order also has a subtle failure the question's framing hints at: it is "applied to whatever keys happen to be present," which means the order is defined over a set the schema does not close, and adding a key to one type forces a decision that silently reshuffles every other type's lines. Per-type orders localize schema growth to the type that grew. The right structure is a shared prefix that is genuinely universal (`type`, `track`, `start`, `duration` — the fields every element has and by which the file is sorted), then a type-specific tail. That keeps the top of every line uniform for scanning and sorting while letting each type order its own substance.

**Trade-offs:** Per-type costs six orderings to define and maintain instead of one, and it is six places to update rather than one when a common field is added. It also slightly complicates the checker, which must dispatch on `type` before validating order. Against that, the global option's simplicity is partly illusory: one list over a union of heterogeneous keys is simpler to *state* and harder to *justify*, and every future key addition reopens the whole list. A shared prefix plus per-type tail recovers most of the global option's uniformity benefit at small cost. If the project cannot commit to maintaining six lists, a global order is survivable — determinism is the load-bearing property and both deliver it — but per-type is the better design.

🗳️ **Juror** (Claude Opus 5) — **Q3 VOTE: Both — `validate` is the enforcement point, `fmt --check` is the convenience; neither alone is sufficient**

**Reasoning:** The governing principle quoted for `validate` settles this: *an opt-in check is worth nothing.* A `fmt --check`-only design is exactly an opt-in check — it fires only when someone remembers to invoke it, and the agent in the incident would not have invoked it, because it believed it was making a routine edit and had no reason to suspect formatting was at stake. The files most likely to be malformed are precisely the ones nobody ran a formatter over. So the check must live in the thing that runs unconditionally. The second half of the same principle — a noisy check that fires on most correct files is worse than no check — is the standard this must clear, and it does clear it: layout compliance is not a heuristic or a judgment call, it is a deterministic property of the bytes, so it fires on exactly the files that are non-compliant and never on a correct one. Zero false positives is the property that earns a check its place in an unconditional tool. `fmt --check` should still exist, because a check mode is what lets CI and a cautious author ask the question without writing, and because pointing the formatter's own check at the same rule keeps one implementation of the rule rather than two. But its role is ergonomic, not enforcement.

One constraint on the `validate` half: this must be a distinct, clearly-labeled diagnostic class — "layout: not canonical, run `fmt`" — separable from semantic errors, with a message that names the mechanical fix. It must not be reported as a schema error, because it isn't one, and conflating them would make `validate` assert something the document doesn't carry. Note this is a genuine, if modest, widening of `validate`'s stated one question: layout is not "internally legal" in the semantic sense, nor agreement with media on disk. The widening is justified — the file's editability is a real property of the file, and `validate` is the only unconditional gate — but it should be made deliberately and written down as such, not slipped in.

**Trade-offs:** Putting it in `validate` means `validate` can now fail a file that is semantically perfect, which will occasionally annoy someone who hand-edited a file and meant no harm. The fix is one command, which keeps the annoyance bounded. The cost of "both" is two invocation paths over one rule — acceptable only if they share a single implementation; two independently-written checkers that drift apart would be worse than either alone, since agents would get contradictory answers about the same file.

🗳️ **Juror** (Claude Opus 5) — **Q4 VOTE: Split it — a non-destructive check mode separate from the rewriting mode. This is not excess caution.**

**Reasoning:** The finding in #61 describes a tool that would perform two independent, semantically distinct transformations in one silent pass: reordering keys (a pure layout change, meaning-preserving) and materializing defaulted fields (a change to what the document explicitly asserts). Those are not the same kind of edit and should not be indistinguishable in a diff. Default materialization in particular converts "I did not specify this, the system chose" into "I specified this" — the resulting file is still semantically equivalent *today*, but it is no longer equivalent under a future change to a default, and it destroys the author's record of what they actually cared about. A tool that does that invisibly, bundled into what the author thinks is a formatting run, is doing something the author did not ask for. The whole incident in the background is one agent silently reformatting a file and being technically correct; shipping a tool whose default behavior is a large silent rewrite would be institutionalizing that same failure rather than fixing it. A check mode is the cheapest possible remedy: it costs almost nothing to build (the comparison already exists inside the rewriter — write to a buffer, compare, report) and it turns an irreversible surprise into a reviewable proposal. It also happens to be the mode `validate` and CI need, so the split pays for itself twice.

**Trade-offs:** The cost is a slightly larger tool surface — two modes to document, and a decision about which is the default. My view is that check should not be an afterthought flag on a rewriter but a first-class mode, and the safer default is to make the destructive path explicit. The real caution here is not about the split itself, which is obviously cheap, but about scope: the split does not by itself answer whether `fmt` should materialize defaults at all. It shouldn't, in my view — materializing defaults is a separate operation from formatting and belongs behind its own explicit flag if it exists at all — but that question is adjacent to the one asked, and I note it only because the split's value is diminished if the answer is "yes, always, just now with a preview." The split makes the change visible; it does not make an unwanted change wanted.
