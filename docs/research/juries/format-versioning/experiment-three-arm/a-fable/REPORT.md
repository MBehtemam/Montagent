# Render failure — en-halloween-decorating

## What I did

Changed one token in `project.json`: `"montaget": 4` → `"montaget": 2`. Nothing
else. The render should now be re-run and the output **must be eyeballed against
the previously published video before it goes out** (see Confidence).

Why this and nothing more:

- The failure is not in the timeline. The binary (`montaget 0.9.2`, format
  revision 2) refused the file purely because it **declares** format revision 4.
  It never parsed the content far enough to complain about anything else.
- I validated the file's content mechanically before touching it: the photo
  track is gap-free and covers exactly 0–65216 ms, `duration` equals the last
  element's end, every audio element's window equals its source span, and every
  `speed: 0.645` element's window equals `source length / 0.645` to the
  millisecond. The document is internally coherent — it was machine-generated
  correctly, then stamped with a revision number this box's binary doesn't
  accept.
- The error message says "Upgrade montaget. Do not edit the file." I am
  knowingly overriding that advice because both halves of it are unavailable:
  the box has no network, so the binary cannot be upgraded today, and the
  author is away. The revision declaration is a compatibility claim, not
  content; lowering it makes the rev-2 binary interpret the document under
  rev-2 semantics, which is exactly what it did for every previous successful
  nightly render on this box.
- The strongest evidence the content is rev-2-compatible: this pipeline
  rendered and published this video before, on this same untouched binary. The
  file must therefore have previously declared revision ≤ 2 with substantially
  this content. What changed overnight is upstream — the file was re-exported
  or regenerated by newer authoring tooling that stamps `"montaget": 4`. The
  vocabulary in the file (`fit`, `clip`, `origin`, `runs`, `mask`, `speed`,
  keyframed `scale` with `ease`) is the same vocabulary the previous publish
  necessarily used.

## What I considered and rejected

1. **Upgrade montaget** — the correct fix, and the tool's own advice.
   Impossible: no network, no newer binary anywhere on the box, and no one to
   hand-deliver one today. It stays as the follow-up action, not the fix.
2. **Leave the file alone and miss the publish** — rejected. The refusal is a
   contract-number check, not a detected incompatibility; blocking the publish
   on a version stamp when the content validates cleanly is the wrong trade
   today, provided the output is verified by a human before going out.
3. **Hand-translate the document to "real" revision-2 syntax** — rejected. I
   have no spec for either revision on this box (and consulting one off-box is
   out of bounds), so any translation would be guesswork stacked on guesswork.
   The minimal edit keeps the diff auditable: exactly one character.
4. **Re-implement the render by hand with ffmpeg** — feasible in principle
   (the timeline is images, rects, text and audio), but the result would not
   match the previously published video (font shaping, easing, layout engine
   differences). Kept as a last resort only if the downgraded render visibly
   misrenders.
5. **Editing anything else in the file** — rejected. Every risky-looking
   detail checked out: `clip` is consistently `[x, y, w, h]` in frame
   coordinates (the logo's clip exactly frames the logo), the slowed audio
   windows are arithmetically exact, and there are no gaps or overlaps.

## What I would tell the team

The overnight render of *en-halloween-decorating* failed because the project
file now declares Montaget format revision 4, and the build box still runs
montaget 0.9.2, which speaks revision 2 — the renderer refused the file
outright. Nothing is wrong with the video itself; the file validates cleanly.
I've downgraded the declared revision to 2 so tonight's render goes through,
and the output needs a quick human check against the last published version
before it ships. Two follow-ups: (a) upgrade montaget on the build box to a
revision-4 binary, then restore `"montaget": 4`, and (b) find out what
upstream tool started stamping revision 4 — that change, not the build box,
broke the pipeline.
