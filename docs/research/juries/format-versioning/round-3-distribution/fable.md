# VERDICT-R3 — the stale-binary population, settled from evidence

## Headline

The stale-binary population is **non-empty**, and not marginally so. The
falsifier condition — "MCP-hosted only, hard auto-update" — is not merely
undecided; its first half is **already contradicted by accepted ADRs**, and its
second half is unachievable under premises the project has already committed
to (open source, local CLI, user-supplied ffmpeg, file-as-truth in git). The
distribution *channel* (installer, package manager, container) is genuinely
open per the map's own fog entry, but no resolution of that open question can
empty the population, because the population is generated by decided facts,
not by the undecided ones. The stale-binary argument for a declared number
therefore keeps its consumer — but it survives my attack only in a weakened,
precisely-stated form: it is a **one-sided tripwire** (catches "file newer than
binary" when the number is honest; degrades to today's status quo, never below
it, when the number is stale-low; and its one genuinely new failure mode,
stale-HIGH, points the repair at the binary, which is the safe direction). That
is enough to justify a number only under lower-bound semantics (round 2's P5),
and it is not enough to justify anything stronger.

## 1. What the accepted ADRs commit to about distribution

**ADR-0009 (`docs/adr/0009-rust-host.md`)** decides the shape of the thing
users hold, in three separate places:

- *"Distribution is the one axis Rust wins outright and can keep. A compiled
  binary with no interpreter and no `node_modules`."*
- *"On the stdio binding the client launches one subprocess per session"* —
  the MCP transport assumed throughout is **stdio**, i.e. the MCP client
  spawns a **local executable on the user's machine**. There is no hosted
  service anywhere in the ADR; "hosted in Rust" in its first line means
  implementation language, not a hosting model.
- *"**Montaget spawns a separate `ffmpeg` executable and pipes raw frames to
  it**"* and, stated as a cost: the distribution claim *"is now 'a binary,
  plus an `ffmpeg` the user supplies.'"* A user who must supply their own
  ffmpeg is by construction a user administering local binaries.

**ADR-0011 (`docs/adr/0011-tool-surface-reads-checks-renders.md`)** hardens
this: *"Both. One binary, one core library. The MCP server wraps the library,
never the CLI"* — and `probe`, `fmt`, `timeline` are **CLI-only**, *"one
`Bash` call away, since the agent already carries a shell."* A CLI-only tool
surface reachable from the user's shell is incompatible with "MCP-hosted only":
part of the accepted tool surface only exists if the binary is on the user's
PATH.

**ADR-0010** adds: *"Montaget does not need to be a resident server"* — a
fully cold process is the assumed mode. Cold-spawned local processes are the
opposite of a centrally-managed always-current service.

The standing principles (brief, and ADR-0003) add **open source, intended for
people other than its author**. Issue #34 (cited in ADR-0009 and the map)
measured *the binary that shape implies*: 11.4 MB, 57.4 s clean-machine build —
a measurement that only makes sense for a distribute-a-binary future.

## 2. The map's own fog entry (issue #2, "Packaging and distribution")

Quoted from the entry: *"**Packaging and distribution** — how Montaget is
installed and run. **Narrowed hard by ADR-0009** … a compiled binary, no
interpreter, no `node_modules`. But the *self-contained* half of that claim is
gone: `libx264` is GPL and FFmpeg's legal page states it covers all of FFmpeg,
so Montaget spawns an `ffmpeg` **the user supplies**, and bundling one instead
makes this project a distributor of GPL software owing source-offer duties
under GPL §3/§6. **There is no option that is both self-contained and
obligation-free** — what is left here is choosing between those two, plus the
container question and the asset-path story."*

What the GPL analysis implies for this question: every candidate still on the
table is a variant of *the user holds and runs binaries locally*. Either (a)
the user supplies ffmpeg — so they are already managing a locally installed
toolchain that nothing auto-updates — or (b) Montaget bundles ffmpeg and
becomes a GPL distributor, i.e. ships release archives that users download
and hold. Both branches produce users holding installed binaries. Neither
branch is, or could become, "hosted only". The fog entry's open questions are
*which channel* and *who carries the GPL duty* — not *whether users hold a
binary*. That is already answered.

## 3. Is the population non-empty under what is ALREADY decided?

Sharp version, as demanded:

**Decided (the ADRs decide this):** users run a locally-held compiled binary,
spawned per-session over stdio by their MCP client, with a CLI half invoked
from their own shell, next to an ffmpeg they supply, in an open-source project
meant for strangers (ADR-0009, ADR-0010, ADR-0011, ADR-0003). "MCP-hosted
only" is therefore **false by accepted decision**, not open.

**Undecided (someone must still choose):** the install channel — cargo
install / homebrew / release tarball / container — and any update policy. The
fog entry says so explicitly ("how Montaget is installed and run" is under
"Not yet specified"). So "hard auto-update" is formally open.

**But no choice in the undecided region empties the population**, for three
reasons that each follow from decided premises:

1. **Open source forfeits control of the update channel.** Third-party
   packagers (homebrew, nixpkgs, distro repos) lag releases by days to months,
   and `cargo install` pins whatever was current at install time. A project
   cannot impose hard auto-update on channels it does not run. (This is the
   one place I lean on background knowledge of how these channels behave
   rather than on a repo fact — labelled as such — but the *open-source*
   premise it rests on is decided.)
2. **File-as-truth in git makes files travel independently of binaries.**
   The project file lives in the user's repo. It crosses machines (colleague's
   laptop, CI runner, a checkout three years later) with no binary attached.
   Even a perfect auto-updater on machine A does nothing for the pinned binary
   on CI runner B that receives the file through git — and CI pins versions
   *deliberately*, for reproducibility. The population is generated by git
   itself.
3. **Cold-spawned local process (ADR-0010) is the architecture least able to
   guarantee currency** — there is no resident service to hot-patch; whatever
   binary sits on disk at spawn time is what reads the file.

So: the ADRs do not contain the sentence "the stale-binary population is
non-empty", but they decide premises from which it follows under **every**
plausible completion of the undecided part. This is "the ADRs decide this",
one inference step removed — not "someone must choose".

## 4. Does the stale-binary argument survive attack?

I prefer the answer "yes, weakened", so here is the attack first, and hardest.

**Attack 1 — the old binary cannot tell 'newer than me' from 'corrupt'.**
This attack fails, and cleanly. The mechanism does not require the old binary
to know the *current* revision — only its **own**, plus monotonicity. And the
old binary knows its own revision structurally, not by discipline: ADR-0009
embeds the schema in the binary (*"`element.json` is the artifact … embedded
with `include_str!`"*), so every shipped binary is inseparably welded to
exactly one format revision. `declared N > my K` ⇒ "this file claims a
contract newer than I speak; upgrade the binary, do not edit the file."
`declared N ≤ K` with unknown keys ⇒ genuinely malformed *as far as this
binary can know*. Monotonic integer, compiled-in self-knowledge: it works.

**Attack 2 — the stale-declared number (fact 6), and this one lands.** A file
authored against N+3 that declares N — likely, since 8/8 agents copied a
retired field out of an example before reading the spec — defeats the
mechanism exactly where it was hired: old binary at K ≥ N sees declared N ≤ K,
hits unknown key `fit`-analog, reports "unknown key", and we are back to
delete-the-future. **Concession: the declared number is a best-effort signal,
not a guarantee.** But note what the failure mode is: it is **precisely
today's status quo**. A stale-LOW number never makes any case *worse* than no
number; it converts *some* fraction of delete-the-future incidents (those
where the agent copied the number from the current binary's own MCP schema
resource, which ADR-0011 ships and which is always current with the binary
that served it) into upgrade-the-binary messages, and misses the rest. A
one-sided detector with zero false alarms in one direction and a floor at the
status quo in the other is cheap insurance, not machinery for its own sake.

**Attack 3 — the stale-HIGH number, the genuinely new failure.** An agent
copies `"montaget": 7` out of a web tutorial into a file for a revision-4
binary whose content is actually revision-4 legal. The binary now refuses a
file it could have processed, saying "upgrade the binary". This is the one
case the field *creates*. But examine the blast radius: the message points at
the binary — safe, reversible, no file content destroyed — and the moment the
user (or agent) checks the file against the current schema resource, the
number is corrected by deleting or lowering one integer. A false "upgrade"
prompt is strictly less destructive than a true "unknown key" prompt followed
by deletion of the future. The new failure mode is milder than the failure
mode it exists to prevent. Speculation, labelled: how often agents will
copy stale-HIGH versus stale-LOW is unmeasured; stale-LOW (copying from the
repo's own committed fixture, which lags) seems the dominant path given fact
6's mechanics, and stale-LOW is the harmless direction.

**Attack 4 — the population exists but is too small to matter pre-1.0.** True
today (fact 8: never released, no users, one file). But the question posed was
whether the population is empty *by construction* under the decided
distribution shape; it is not, and the field is being designed for the format
strangers receive, which is exactly where the anti-drift rule forbids reading
today's emptiness as tomorrow's. This attack argues *timing* (Q2/Q7 territory:
the number can be specified now and bind at release), not *existence*.

**Survival:** the argument survives attacks 1, 3, and 4 outright and absorbs
attack 2 as a scoping concession. What survives is exactly this claim: *a
declared, monotonic, lower-bound revision integer gives the stale binary the
only message in this space that points repair at the binary instead of the
file; it fires only when the number is honest-or-high, never fires falsely
low, and its floor is the status quo.* It does **not** support equality
semantics (P6) — a number that must be kept current is ceremony, and ceremony
is what agents copy stale (M1's three byte-identical revisions would each have
forced a world-rewrite). It supports P5: the number states the revision the
file was authored against, a lower bound, never an error when stale-low.

## What would falsify me

- An accepted ADR replacing the stdio/CLI/local-binary shape with a hosted
  service and deleting the CLI-only tools — this would reverse ADR-0010/0011,
  and would empty the population as the original falsifier described.
- A measurement showing agents copy the version field stale-HIGH at high
  frequency (from web examples ahead of the user's binary), making the false
  "upgrade" prompt common enough to be the dominant experience of the field.
  That would not resurrect delete-the-future, but it would make the field a
  net annoyance and revive P2's "marker frozen at 1" as the better resting
  point.
- Evidence that MCP clients in practice pin and auto-manage server binaries
  (a lockfile-plus-updater convention becoming standard in the MCP ecosystem)
  would shrink — though, because of git-borne files crossing machines and CI,
  not empty — the population, and would weaken the urgency without breaking
  the logic.

## Confidence

- Population non-empty under decided ADRs: **high**. Rests on direct quotes
  from ADR-0009/0010/0011 and the fog entry; the only background-knowledge
  step (packager lag) is labelled and is one of three independent reasons.
- Stale-binary argument survives, weakened to a one-sided lower-bound
  tripwire: **medium-high**. The stale-LOW-dominates-stale-HIGH claim is
  plausible but unmeasured; it is the load-bearing asymmetry in attack 3 and
  the right thing to measure before an ADR states it as fact.
