# Juror B1 — Issue #48 (`fit` vocabulary)

## Q1

**Decision:** `fit` is a derivation claim, not a render instruction. Its actual consumer is `validate` (and, by extension, the human/agent reading its output), never `render`.

**Why:** ADR-0013 settles that the declared `width`/`height` rect is authoritative at render — "the source is resampled to exactly the declared rect," full stop, regardless of what `fit` says. Once `width`/`height` are fixed, there is no residual decision left for `render` to make by consulting `fit`: it doesn't need to know whether the numbers came from `cover`, `contain`, or a typo, because the resample target is already resolved to two integers in the document. What `fit` actually does is retroactively describe *how those two integers were supposed to have been computed* — a provenance/intent tag on `width`/`height`. The only place that claim gets used is `validate`'s fit-deviation check (ADR-0013, "What `validate` checks"): it recomputes what the rule would produce from the probed source and diffs it against the declared value, using `fit` to pick which rule to apply and printing the note. `fit_rounding_scan.py` §5 is exactly this: it treats `fit:"cover"` as a claim to be checked against `images/06.png` on disk, not as an instruction the renderer executes.

**Strongest counter:** If a genuinely new fit value were admitted whose *rounding tiebreak itself* changed the drawn pixels in a way not fully captured by `width`/`height` alone (imagine a hypothetical value that also implies a sub-pixel sampling filter, not just an integer target), `render` could conceivably need to read `fit` after all. Nothing on the table today does that — `cover` and `contain` both fully resolve to `width`/`height` — but the claim "no consumer at render, ever" is slightly stronger than "no consumer at render, for the values this ADR admits."

## Q2

**Decision:** `bw`,`bh` = the element's `clip` rect's width/height (the aperture), never the element's own declared `width`/`height`. When `clip` is absent, there is no box to fit into, so a declared `fit` is unverifiable — it should be treated the same way ADR-0013 already treats an unprobeable source: `UNCHECKED`, not silently inert and not silently valid.

**Why:** `fit_rounding_scan.py`'s own `FIXTURE` table (§4) encodes each row as `(source w, h, aperture w, h)` — it feeds `cover_int` the **aperture** dimensions, not the declared rect. Hand-verifying `photo-06`: source `1536x2720`, `clip:[0,0,1080,1300]` → `bw=1080,bh=1300`. Cross-multiplication `bw*sh (2937600) >= bh*sw (1996800)` → width drives, taken verbatim as `1080` (matches declared `width`); slack axis `= 2720*1080 // 1536 = 1912` (matches declared `height`). This only works with `bw,bh = clip`'s dims. Using the declared rect itself as the box (`bw=1080,bh=1912`) is circular — you can't use the output as the input to derive the output — and it also silently *flips* the driving axis (`1080*2720=2937600 < 1912*1536=2937632`), landing on the right numbers by a coincidence of the arithmetic, not by a coherent rule. `handle-logo` is the instructive negative case the ticket points at: its `clip:[478,96,68,68]` is numerically identical to its declared rect, so it *can't* distinguish the two readings — the aperture happens to equal the drawn rect exactly there (no overscan, full circle, no Ken Burns). `photo-06` is the only element in the corpus where `clip != width/height`, and it's the one that proves `clip` is the box.

Absent `clip`: nothing in ADR-0012 or ADR-0013 defaults it (it's missing from ADR-0012's "everything else defaults" list, same as `width`/`height`), and a `cover` computation needs a target box that is smaller than or aspect-different from the declared rect to mean anything — without `clip` there is no second rect to compare against. Treating it as `UNCHECKED` (not `error`, not silently trusted) is the reading that's consistent with ADR-0013's own vocabulary for "the disk-agreement question is unanswerable."

**Strongest counter:** `UNCHECKED` for "fit with no clip" stretches a category ADR-0013 minted specifically for *unprobeable sources* (missing file, permission denied) to cover a *structurally absent field* instead — a different kind of unanswerable. A jury could reasonably want a distinct third bucket rather than reusing that one.

## Q3

**Decision:** `fit` is required on every image element.

**Why:** ADR-0006's rule, applied verbatim by ADR-0014 to the text box: *"an omitted field is indistinguishable from a decision not to check."* An omitted `fit` doesn't just mean "no claim" — it silently disables the fit-deviation note/check for that element, exactly the failure ADR-0014 refused to accept for `height` even though `height` was *derivable* and dead-on-arrival for 68% of elements. `fit` is a stronger case than `height` ever was: it's present on **8 of 8** image elements in the only real project file (vs. `height`'s 15/22 being merely reproducible from other fields), so requiring it costs nothing against the evidence and it is exactly what ADR-0014 called "required-and-computable," provided a tool (parallel to `measure`) can supply the value. It also blocks the tempting silent default ("no `fit` means assume `cover`," matching 8/8 today) — ADR-0012 already rejected silent-but-plausible defaults for `width`/`height` on the same logic ("a default is only safe where its wrong answer is loud"); a defaulted `cover` on a genuinely undecided element looks exactly as plausible as a correct one.

**Strongest counter:** Unlike `height`, `fit` (per Q1) has no independent render meaning — it does zero work if the file is never re-validated against source media. A juror could argue that making a field required purely to arm an *opt-in* check (`validate`), when ADR-0006 already concedes `validate` itself is not a structural chokepoint for the file-tools authoring path, is a weaker justification than ADR-0014's — text height at least bounds layout at authoring time even before any check runs; `fit` bounds nothing until someone runs `validate`.

## Q4

**Decision:** Closed set = `cover`, `contain`, and an escape value spelled `"declared"`. `cover`: driving axis takes the box dimension verbatim (exact by construction, `>=` on both axes after slack floors), slack axis floors — `s_slack * b_driving // s_driving`, preserving `computed >= box`. `contain`: computed dims `<=` box on both axes, and — per ADR-0013's own aside ("if `contain` is ever defined with the obvious semantics, only floor is safe there") — floor also, preserving `computed <= box` and keeping the one-rounding-operation-across-all-values property ADR-0013 already argued for. `"declared"` carries no inequality at all — it is explicitly the value that opts the element *out* of the fit-deviation check, i.e. "this rect is asserted, not derived; do not compute a rule and do not compare."

`contain` belongs in v1: the reference class is CapCut/Premiere (ADR-0003), both of which ship a letterbox/fit-within mode as a first-class sibling of crop-to-fill, and the fixture's 0/8 usage is — per ADR-0003's asymmetry — no evidence against it.

For the escape name: **`"none"` is disqualified** — CSS `object-fit: none` means "ignore the box, draw the source at its own natural size," which is close to the *opposite* of Montagent's escape ("trust the declared rect, don't derive or check it against anything"); an agent reasoning from CSS habit would misread it immediately. **`"fill"` is disqualified twice over** — it's already spent in this format as the shape/paint field (`fill`, CONTEXT.md), and CSS `object-fit: fill` additionally carries a specific non-uniform-stretch render semantic that doesn't match "no check applies" at all. `"box"` is disqualified as a resurrection of a term CONTEXT.md explicitly retired. `"declared"` is unspent and ties directly to the vocabulary ADR-0013 already uses for this exact concept ("the declared rect is authoritative at render") — it names the thing the value actually asserts rather than borrowing a foreign tool's crop/scale terminology.

**Strongest counter:** ADR-0014 shipped `gradient` as "unevidenced rather than rejected" and deferred it rather than admitting it on general-editor grounds alone — the same discipline could apply to `contain`: 0/8 usage, no ADR mentions it, and admitting it now is legislating a whole second rounding branch (even if the branch is "the same floor operation," it's still a second named value with its own inequality) for a capability nothing in this repo has yet needed. Shipping only `cover` + `"declared"` in v1 and opening `contain` as its own future ticket is the more conservative reading of "don't create a schema value by implication," which is this ADR-chain's most-repeated refusal.

## Q5

**Decision:** Retire `gravity` on images — schema error naming `origin` — completing the move ADR-0014 already made for text and shapes.

**Why:** ADR-0013's measurement (inert on 8/8) was handed here as a fact, not a verdict, but the structural argument behind it generalizes past the fixture: under Q2's settled model, `clip` is an *independent, absolute* frame-space rect, and the drawn content's position is *already* fully pinned by `x`/`y`/`origin` before `fit` or `clip` enter the picture. `cover`'s driving axis is taken verbatim and its slack axis is a deterministic floor — there is no "which side gets the extra content" choice left for `gravity` to resolve, because the extra content's position was never ambiguous: `clip` crops a rect whose origin is already nailed down. The same holds for `contain` (Q4): the resulting smaller rect's placement is still `x`/`y`/`origin`'s job, not a modifier on `fit`. So this isn't "gravity happens to be unused on these 8 elements," it's "gravity has no remaining degree of freedom to act on under the settled `clip`+`origin` model," which is a stronger and non-empirical basis for retirement than the measured fact alone, and it's the same shape of argument ADR-0014 already accepted for text/shape `gravity`.

**Cost to the fixture:** unlike ADR-0014's decisions (zero bytes changed), this one is not free — `gravity` is declared on all 8 image elements (`"top"` ×7, `"center"` ×1 on `handle-logo`), so retiring it is a mechanical one-field-per-element strip across the committed fixture plus a `migrate.py` correction, verifiable by the same byte-diff discipline ADR-0013 used elsewhere. That cost should be paid once and stated plainly, not glossed as free.

**Strongest counter:** The structural argument rests entirely on "the box is always `clip`." If a future fit value or a future element type (video, say) introduces a *different* kind of box — one not itself an independent absolute rect, but one derived relative to the element — `gravity` could regain exactly the job it's being stripped of here, and re-adding a retired, collision-recorded word is more expensive than never having removed it. ADR-0003's asymmetry cuts against acting on "inert today" too casually even when the argument is structural rather than empirical.

## Q6

**Decision:** Promote fit-deviation to `error`, now that Q4 supplies the legal escape (`"declared"`) the "Not settled here" section says this promotion was blocked on. Use the second, preferred shape: for `fit:"cover"` (or `"contain"`), `error` fires when the declared driving-axis dimension does not exactly equal the box dimension (zero grace), **or** the declared slack-axis dimension is not a member of `{floor(exact), ceil(exact)}`. An unprobeable source stays `UNCHECKED`, never `error`. `fit:"declared"` is exempt from the check entirely — that is the whole point of the escape.

**Why:** ADR-0013 explicitly names this predicate as the better of the two candidates (a step count is not scale-free — the same 2-step deviation is 0.105% on `photo-06` and 2.941% on `handle-logo`, a 28x spread) and explicitly says the only thing blocking it is the absence of a legal way to spell "don't check this," which Q4 now supplies. The stale-source case (§5 of the scan, 366 steps off, still covering) is exactly what this predicate is *for*: 1546 is nowhere near `{floor(1546.18)=1546... }` — wait, more precisely, on the *real* 1536x2200 source, declared 1912 is nowhere near `{floor(exact)=1546, ceil(exact)=1547}`, so it fires correctly where the current `note` lets it through.

**Fixture check, computed:** `photo-06` and its six siblings share one geometry — source `1536x2720` into box(clip) `1080x1300`: driving axis width `1080` matches declared `1080` exactly; slack exact `=2720*1080/1536=1912.5`, so `{floor,ceil}={1912,1913}`; declared height is `1912` — member, no error. `handle-logo`: source `800x800` into box `68x68`: driving axis (tie, width per `>=`) `68` matches declared `68`; slack exact `=800*68/800=68` exactly, `{floor,ceil}={68,68}`; declared height `68` — member, no error. **0 of 8 elements break**, matching ADR-0013's own claim that tightening later costs nothing on the committed file.

**Strongest counter:** Promoting to `error` now assumes every future author correctly reaches for `"declared"` the instant they want deliberate anisotropy or a stale-but-still-covering source, rather than leaving a legitimately-close-but-off file (e.g. a source re-encoded with a 1px trim from a different tool's rounding) unable to render at all until hand-fixed. ADR-0006's own noise-budget principle warns against exactly this kind of check tightening outrunning real-world authoring friction — `note` costing nothing today is a weaker but safer position until there's a corpus of files actually exercising the escape value.

## Anything the questions missed

**`fmt` and a pre-#48 file.** ADR-0014 forbids `fmt` from rewriting a declared extent or a colour because "the spelling is content." Every file written before this ticket lands either omits `fit` (now illegal under Q3) or lacks the `"declared"` escape spelling (now available under Q4). Nothing in the six questions says whether `fmt` may *backfill* a missing `fit` on an old file (a one-time migration convenience) or must refuse, the same way it must refuse to backfill a missing required `height` on text. Given ADR-0014's own precedent and the exact-string-replace argument that runs through every ADR in this chain, the consistent answer is `fmt` must not synthesize it either — that's a `migrate.py`-shaped operation, not a formatting one — but it's undecided territory this ticket opens and doesn't close.

**Video elements aren't addressed at all.** ADR-0003's general-editor scope commits Montagent to video clips eventually, and a video element will need the same source-dimensions-vs-declared-rect question `fit` answers for images. Nothing here is *wrong* for that future — the vocabulary this ticket settles (closed set, `clip` as box, required field, escape value) generalizes cleanly — but it's worth stating that this ADR should be written so `fit` is typed as a property of "elements with a probeable visual source," not of `type:"image"` specifically, so a future video ADR doesn't have to re-derive the same three decisions from scratch.
