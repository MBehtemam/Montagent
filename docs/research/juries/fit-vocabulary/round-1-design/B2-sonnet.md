# Juror B2 — Issue #48 (`fit` vocabulary)

## Q1

**Decision:** `fit` is a derivation claim, not a render instruction. It has zero effect on what `render` draws.

**Why:** ADR-0013 is unambiguous: "the source is resampled to exactly the declared rect" and the renderer "never silently samples at the exact isotropic factor and treats the declared integers as an approximate bound." Render takes `width`/`height` (and `clip`) and resamples to them — full stop. Nothing in that pipeline branches on the string `"cover"` vs `"contain"` vs anything else; a renderer that read `fit` to decide *how* to resample would be re-deriving the extent from the source at render time, which is exactly the defect ADR-0013 spent a whole section killing ("what is actually drawn is a number not in the file"). So `fit`'s actual consumers are (a) whoever computed `width`/`height` in the first place — a human or an agent, using the named rule as an algorithm — and (b) `validate`, which recomputes the rule from the source on disk and compares it to the declared numbers, emitting the fit-deviation note. `fit` is the field that lets that comparison exist at all: it names *which* algorithm the declared rect claims to be the output of. Say it plainly: `fit` is an assertion about how the author computed the extent, checked after the fact — not a layout mode consulted while drawing.

**Strongest counter:** A renderer implementation is free to *compute* `width`/`height` from `fit` at load time when they happen to be absent or need regenerating (e.g., a `montaget fix` / `measure`-style tool), and in that narrow authoring-time role `fit` does drive a real computation — just not inside `render`'s draw path. If a future tool auto-fills `width`/`height` from `fit` + source dims, "assertion checked after the fact" undersells it; it's more precisely "the formula the file claims its own numbers satisfy," which sounds like a layout mode right up until you ask who runs it and when.

## Q2

**Decision:** `bw x bh` is the `clip` rectangle's `width`/`height` — the aperture — not the element's own declared `width`/`height`. When `clip` is absent, `bw x bh` defaults to the element's own declared `width`/`height`, which makes a declared `fit` a no-op tautology in that case.

**Why:** Reconstructing ADR-0013's own worked arithmetic settles this. `photo-06`: source `1536x2720` (per ADR-0012's worked spill computation), declared `width:1080, height:1912`, `clip:[0,0,1080,1300]`. Plug `bw=1080, bh=1300` (the *clip* dimensions) into the published formula: driving axis by cross-mult, width drives (`1080*2720 >= 1300*1536`); slack axis `= 2720*1080 // 1536 = 1912` — exactly ADR-0013's own quoted arithmetic, and exactly the declared `height`. If `bw,bh` were instead the element's own `width,height` (1080,1912), the formula would be solving for its own output — circular. So the box the fit rule fits into is the aperture, and the declared `width`/`height` *are* the fitted-extent output, which is why ADR-0012 also derives the spill (`612.5 px` over the `1300`-tall clip) from this exact relationship. `handle-logo` confirms this differently, not identically: `clip:[478,96,68,68]` gives `bw=bh=68`, source is the 800x800 badge PNG (ADR-0014), and because source and clip are both square the fitted extent lands *exactly* on the box with no rounding — declared `width:68,height:68` equal to `bw,bh` on the nose. `photo-06` shows the box and the fitted extent *diverging* (1300 vs 1912, by design — that's what "cover" spilling means); `handle-logo` shows them *coinciding* (68=68, an aspect-locked degenerate case). Same rule, two different-looking outputs — that's the "instructive" difference the question points at: `bw,bh != width,height` in general, and elements can mislead a reader into conflating them when the aspect happens to match.

When `fit` is present but `clip` is absent, there is no other rectangle in the document to serve as `bw,bh`, so the box degenerates to the element's own `width,height`. Under that reading a declared `fit` with no `clip` asserts `width==bw` and `height==bh` trivially (the element's own numbers, compared to themselves) — the fit-deviation check becomes vacuous for that element, not wrong, just unable to say anything, structurally identical to ADR-0013's own `UNCHECKED` category for an unprobeable source.

**Strongest counter:** Defining `bw,bh` as "the clip, or the element's own rect if no clip" bakes two different geometric objects into one symbol name across two cases, which is exactly the kind of "sometimes a rect, sometimes something else" shape that got `box` retired in ADR-0012. A cleaner spelling might require `clip` whenever `fit` is anything other than the escape value, rather than letting the box silently degenerate.

## Q3

**Decision:** `fit` is required on every element that has a `source` (i.e., `image` and `video`), the same way the text box stayed required.

**Why:** ADR-0006's rule, restated by ADR-0014 for the text box: *"an omitted field is indistinguishable from a decision not to check."* Apply it here directly. If `fit` may be omitted, `validate` cannot tell "the author deliberately declared this rect with no coverage claim" from "the author forgot to think about fit at all" — and worse than the text-height case, an omitted `fit` doesn't just weaken one check, it removes the only anchor `validate` has for *which formula* to recompute and compare against. ADR-0014's text-box argument applies with more force here, not less: the text height at least has a documented *derivable default* (`ceil(size*line_height*line_count)`); `fit` has no analogous fallback — there is no "obvious" value to assume on omission, so omission there is pure information loss, not a redundant-but-armed check. The ADR-0006 opt-in objection — "an opt-in check on a command you might not run replaces real vigilance with false confidence" — applies letter for letter: an optional `fit` reintroduces exactly the `sequence`-label failure mode ADR-0006 was written to kill, one field over.

**Strongest counter:** Unlike text `height`, which is derivable from data already on the same element (`size`, `line_height`, the `\n` count — all local), `fit`'s value set is now closed to a small handful of named algorithms, and its escape value (Q4) makes "no coverage claim" legally spellable. A required field whose only two live options in the committed fixture are `cover` and the escape is close to boilerplate — arguably weaker grounds for *requiring* it than ADR-0014 had for `height`, where the check catches genuine, common, silent edits (adding a `\n`). One could reasonably default omitted `fit` to the escape value rather than erroring on absence, since "no claim" is a coherent, safe default the way `scale` defaults to `[1,1]`.

## Q4

**Decision:** The v1 closed set is `cover`, `contain`, and an escape value spelled `stretch`.

- **`cover`** (already settled by ADR-0013): inequality `width >= bw AND height >= bh` (the drawn rect fully covers the box, permitting overflow). Driving axis chosen by `bw*sh >= bh*sw`, takes the box dimension verbatim (exact). Slack axis `= (s_slack*b_driving)//s_driving`, **floors** — floor is a tiebreak here (both roundings satisfy `>=`), settled by ADR-0013 for non-geometric reasons (ceil is not additive; forward-consistency with `contain`; implementation entropy).
- **`contain`**: inequality `width <= bw AND height <= bh` (the drawn rect fits fully inside the box, permitting letterbox slack). Driving axis chosen by the flipped comparison `bw*sh <= bh*sw`, still takes the box dimension verbatim on the driving axis. Slack axis is the same integer-division formula and **must floor**, non-negotiably this time: ceiling the slack axis under `contain` can push it past `bh`/`bw` and violate the very inequality that defines the value — this is the case ADR-0013 flagged in tiebreak 2 ("if `contain` is ever defined with the obvious semantics, only floor is safe there"). Recommending it for v1 despite `cover` being 8/8 of the fixture: ADR-0003's asymmetry is explicit that fixture absence is never evidence against a capability, and `contain` is table-stakes in the stated reference class (CapCut/Premiere letterbox/fit-to-frame). Its rounding rule falls straight out of the same formula already published for `cover` — it costs one clause, not a new invariant, so defining it now doesn't create a value "by implication," it's the act this ticket exists to perform.
- **Escape — `stretch`**: inequality is equality on both axes, `width == bw AND height == bh`, unconditionally, regardless of source aspect. No rounding decision exists because `bw,bh` are already integers (they're the box's own declared or clip dimensions) — the cleanest member of the set for exactly that reason. This is "do not fit this, use my rect": it asserts nothing about the source's aspect ratio at all, so `validate`'s fit-deviation check has nothing to compare and is silently inapplicable (not `UNCHECKED` — the author explicitly opted out, which is different from an unprobeable source).

  Names already spent elsewhere and rejected: **`fill`** collides with the shape paint field `fill` (ADR-0014) — an agent grepping `"fill"` in a project with both `rect` and `image` elements would get false hits pointing at the wrong concept, the exact write-read/exact-string-replace hazard `CONTEXT.md` names for `center-center` and colour spellings. **`none`** collides with CSS `object-fit: none`, which means "don't resize at all, draw at natural size" — the opposite of what Montaget's escape does (it *does* resize, to exactly `bw x bh`, anisotropically if needed; that's CSS `object-fit: fill` semantics, not `none`). Naming it `none` would mislead an agent carrying CSS priors into expecting natural-size behavior Montaget doesn't have (there's no natural size in the document at all — ADR-0012 killed implicit `fill`-from-source). `stretch` avoids both collisions: it isn't a Montaget field name anywhere, and while colloquial, it isn't a reserved CSS `object-fit` keyword either, so it doesn't inherit false CSS semantics.

**Strongest counter:** Including `contain` now is a bet against ADR-0003's own explicit hedge — "general obliges primitives, not features... v1 implements what it implements" — and this ticket's own charter is narrowly "define what's needed to unblock the fit-deviation error," which only needs the escape value, not a third fit mode nobody has used. Shipping `contain` here risks exactly the "value created by implication" failure ADR-0013 refused to commit, just with better cover: nothing forces `contain`'s rounding logic to be exercised or verified against real data the way `cover`'s was against the 31M-combination sweep, so it ships unverified by the standard the rest of this vocabulary was held to.

## Q5

**Decision:** Retire `gravity` on images entirely — schema error naming `clip` (paired with `x`/`y`/`origin`) as the replacement, matching ADR-0014's identical treatment of `gravity` on text/shape (which names `origin`).

**Why:** ADR-0013 measured `gravity` inert on 8/8 image elements, but the stronger claim, confirmed by working through the geometry in Q2, is that it's *structurally* inert, not merely unexercised by this fixture (which would be an ADR-0003 violation to lean on alone). The element's `x`,`y`,`origin` position the *entire fitted rect* — the output of the `fit` computation, whatever its size — not some independent "visible window" that could slide within a fixed frame position. Under `cover`, the overflowing part of the picture is pinned by the same `x`,`y`,`origin` that already fully determine where the drawn rect (and hence its overflow) sits; under `contain`, any letterbox slack shows up *inside the element's own declared, smaller extent*, and where that sits in the frame is again fully pinned by `x`,`y`,`origin`. There is no leftover degree of freedom anywhere in this model for a "which part of the source is shown" keyword to consume — the aperture (`clip`) and the placement (`x`/`y`/`origin`) between them already exhaust the positioning question, on both `cover` and a hypothetical `contain`. This isn't a fact about the fixture; it falls out of the arithmetic itself, so ADR-0003's asymmetry doesn't block retiring it — this is the rare case where "inert on 8/8" is corroborated by mechanism, not just census.

**Cost to the fixture:** `gravity` appears on all 8 image elements (`top` x7, `center` x1 on `handle-logo`). Retiring it deletes 8 key/value pairs, requires a `migrate.py`/`verify.py` update (mirroring ADR-0013's own migrate-correction precedent), and is a pure subtraction — no rendered pixel changes, since the field was never consulted. That's the same "changes zero bytes of rendered output, corrects the document" shape ADR-0013's own `migrate.py` fix had.

**Strongest counter:** "Structurally inert under this element model" is an argument that the *model* left no room for gravity, not proof that no model should. A future aperture that isn't glued 1:1 to the element's own placement — e.g., a `clip` that can move independently within a larger fitted rect over time, which is exactly the open "is `clip` keyframable" question ADR-0012 left unsettled — would reopen a real degree of freedom gravity could occupy. Retiring the field now forecloses that future cheaply (a keyword is cheap to re-add, a schema error is not free to walk back once agents have learned "gravity is always an error"), and the ticket that would motivate it (#21, #13) hasn't run yet.

## Q6

**Decision:** Promote to `error`, using the second candidate shape — zero grace on the driving axis, membership in `{floor(exact), ceil(exact)}` on the slack axis — and gate it on `fit` no longer being omittable and `stretch` existing as the escape.

**Why:** ADR-0013 blocked promotion to `error` on exactly two things: a closed vocabulary (so the rule to check against is unambiguous) and a legal way to spell "don't check me" (so a deliberately anisotropic rect isn't forced into the false choice between silently failing a new error and polluting the `scale` animation channel, the 7/8-element collision ADR-0013 documented in detail). Both are now supplied: Q4 closes the vocabulary and Q3/Q4 make `stretch` the required, checked-free escape. With the escape available, there is no longer a legitimate authored file this error could wrongly refuse — anything that wants anisotropy just says so. The second predicate shape is the right one for the reason ADR-0013 already gave and the scan script demonstrates independently: a fixed step-count threshold isn't scale-invariant (the identical 2-step deviation is 0.105% on `photo-06`'s 1912-px axis and 2.941% on `handle-logo`'s 68-px axis, a 28x spread within one file), so a step-count error would be simultaneously too strict on large rects and too loose on small ones. `{floor(exact), ceil(exact)}` membership is scale-invariant by construction — it only ever admits the two "honestly rounded" answers regardless of magnitude — and zero grace on the driving axis is correct because the driving axis is *exact by construction* (an integer, not a rounding decision), so any deviation there can only be a typo or a stale-source drift, never a legitimate rounding choice.

I computed the predicate against the committed fixture rather than trusting the ADR's restated claim: for the 7 photo elements, driving axis (width) `1080 == bw(1080)` exactly, and slack axis (height) `1912 ∈ {floor(1912.5), ceil(1912.5)} = {1912, 1913}` — membership holds. For `handle-logo`, both axes are exact matches (`68 == 68` on both), trivially inside `{floor,ceil}` (which collapse to one value, 68, since the source is square and there's no rounding residue). **Result: 0 of 8 elements break**, matching the scan script's own assertion ("tightening later breaks 0 of 8 committed elements") and ADR-0013's claim — verified independently here rather than taken on faith.

**Strongest counter:** Promoting straight to `error` the same ticket that defines the vocabulary is aggressive sequencing — ADR-0013 explicitly reserved the severity decision for "this ticket" without mandating it happen in the *same* pass as defining the values, and shipping a new `error` at the same moment agents first learn the closed vocabulary and the `stretch` escape gives them zero grace period to discover and adopt the escape before their existing (currently `note`-only, non-blocking) files start refusing to render. A safer sequencing ships the vocabulary and `stretch` now, watches one release cycle of real usage of `stretch`, and promotes `note` to `error` in a follow-up ticket — which is also more consistent with ADR-0006's general caution about severity ("the level is never the finding," decided deliberately and slowly elsewhere in this project).

## Anything the questions missed

**`video` elements inherit this whole ticket by silence.** Every question and all the evidence in ADR-0013/#48 is scoped to the 8 `image` elements in the fixture, but `fit`, `clip`, and the cover/contain arithmetic are generic transform-layer concepts that ADR-0012 attaches to any element with a `source` — which per `CONTEXT.md`'s glossary includes `video`. Nothing here or in the ADRs says whether `video`'s *source range* (its own time-based dimension) interacts with `fit` differently, and ADR-0003's asymmetry cuts hard against assuming "the fixture has no video elements" means video doesn't need `fit`/`clip`/the escape value too — a general editor obliges the primitive to cover video the same way it obliges RTL text. This ticket's decisions should be stated as applying to "any element with a `source`," not "image elements," so the schema doesn't silently re-scope itself down to what the fixture happens to contain.
