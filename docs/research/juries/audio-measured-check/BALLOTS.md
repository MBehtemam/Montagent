# Ballots: the audio map's measured check, round 1

Packet: [`QUESTION-ROUND-1.md`](QUESTION-ROUND-1.md), sent blind and identical to three jurors
dispatched in parallel. Ticket: [#802](https://github.com/MBehtemam/Montagent/issues/802).
Ballots are verbatim.

## Juror 1 (Claude Opus 5.5)

🗳️ **Juror 1** (Claude Opus 5.5) — **Q1 VOTE: (c) both, and the build's test is a port of the prototype's evidence script (same metric, same fixture), not a separate artifact**

**Reasoning:** `verify` cannot attribute a number to one element's effect, because the file carries one mixed track and energy is per span. So it cannot be where an element-level capability (EQ cutoff, gate, de-ess, crossfade midpoint) proves itself. Only a fixed-fixture render can isolate the effect, and the fixture can be built so the effect is the only thing in the mix. `verify` is still the right witness for what the document itself declares at programme level (`master.target_lufs` / `ceiling_dbtp`). ADR-0172 already commits `verify` to reporting those, and they are the only measurements that mean anything on a user's file. The ADR evidence rule already requires a committed re-executable script that re-derives the number. If the CI test is a port of that same script (same metric, same fixture, same tolerance), the ADR's number and the shipped guarantee cannot drift apart. Two artifacts would be two places for the number to silently diverge.
**Trade-offs:** CI renders per capability cost wall time on three legs, and each fixture has to be built so the effect is isolatable. (a) alone cannot test element effects at all, and it pushes detection onto users after they have shipped. (b) alone leaves a declared master target with no witness on the real deliverable, which contradicts ADR-0172. Porting also ties the test to the prototype's fixture, which may be a little thin for regression. A capability can add cases, but the ported case stays the anchor.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q2 VOTE: (a) ffmpeg's own meters, with a narrow carve-out under (c) for band energy if needed**

**Reasoning:** `verify`'s whole premise is that the decoder is an independent witness. It uses `ffprobe`/`ffmpeg`, which the user already has, and it already runs `ebur128`. Using `ebur128=peak=true` and `astats` in both the CI test and `verify` means one measuring instrument across the prototype, the build test and the user's deliverable. Then a tolerance stated in an ADR means the same thing everywhere. The meters themselves (EBU R 128 gating, true-peak oversampling) are deterministic implementations of a standard. So the cross-build drift the research found in the effect filters (`afftdn`, `firequalizer`, and others) is a property of the thing being measured, not of the meter. Tolerances absorb it. Byte hashes cannot.
**Trade-offs:** The meter shares a build with the engine under test, so a regression in ffmpeg's `ebur128` would move both sides. That risk is small and is mitigated by cross-leg CI (three different ffmpeg builds). Band energy measured with an ffmpeg filter (for example `bandpass` then `astats`) inherits that filter's per-build float behaviour. If that proves noisy, a small Rust FFT inside the test is an acceptable carve-out for the band-energy metric only. Making (b) the general rule would bring in a second loudness implementation that `verify` does not use, and the two would disagree at the 0.1 LU level.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q3 VOTE: Loudness: ±1 LU two-sided, with the below-target side suppressed or downgraded to `note` when the headroom-under-6-dB review already fired. True peak: review when above ceiling + 0.5 dB codec allowance (measured on the decoded AAC)**

**Reasoning:** One gain then `alimiter` is not a closed-loop normaliser. ±0.5 LU is a mastering-house tolerance that a single measured gain plus a limiter, then AAC, will miss routinely, and the result would be noise reviews. ±1 LU is a cited outside standard (R 128 short-form / ATSC A/85), so under ADR-0061 it is correctly a `review` threshold. Two-sided, because "too loud" is also a miss. The known legitimate under-shoot from heavy limiting is already predicted by the headroom review, so it should not raise a second review for the same cause. For true peak, AAC at 160k typically adds a few tenths of a dB of inter-sample overs after a sample-accurate limiter. Strictly above the ceiling would fire on correctly made files. A stated 0.5 dB allowance absorbs this, is easy to cite, and still catches a missing or misconfigured limiter, which shows up as several dB over.
**Trade-offs:** ±1 LU lets a 0.9 LU error pass silently. That is acceptable for a `review`-class check whose job is to catch broken stages, not to certify delivery. The 0.5 dB codec allowance is an engineering number rather than a standard one. Per the evidence rule, it needs its own committed measurement across the CI legs to justify it, and it should be revised if that data says 0.3 or 1.0. A one-sided loudness check would hide over-target files, which is the more harmful error.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q4 VOTE: Commit the script, inputs and `measurements.json`, plus the exact rendered clips the owner listened to, small and short; blind X/Y with a committed key; the verdict recorded in the ADR, quoting a committed verdict file next to the clips**

**Reasoning:** The evidence rule treats the owner's verdict as a qualitative claim, and it needs the artifact itself committed verbatim. The research says bytes are not reproducible across build and CPU for exactly the effects under audition (`afftdn`, EQ, pitch). So "regenerate from script" does not reproduce what the owner heard, and the clips must be committed. The script and inputs are committed too, so the numbers re-derive and the assertions exit non-zero. Blind X/Y with a key committed alongside (or revealed after the verdict) stops the ear from favouring the label "processed", and the loudness match removes the louder-sounds-better bias. The verdict file names the build, the CPU, the listener's choice and the date. The ADR quotes it and links to it.
**Trade-offs:** Committed audio grows the repo. Keeping clips to a few seconds each, as compressed AAC or Opus at a stated bitrate, keeps that to kilobytes per capability, and Git LFS is an option if it grows. A single listener with a single blind trial is weak statistics. The owner's ear is the stated decider, so blinding is there to keep the judgement honest, not to turn it into ABX-grade proof. Script-only would be lighter but would leave the verdict pointing at audio nobody can hear again.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q5 VOTE: A smoke check asserts a fixed set of properties: the render succeeds; output length, channels and rate are as expected; the output is not silent and not clipped; the effect measurably changed the signal against bypass; and a reproducible, coarse per-effect signature holds where one exists**

**Reasoning:** "No honest number" means no number that captures quality. It does not mean no number at all. The smoke check should prove the effect was wired in, ran, and did not break the programme. The assertions:
1. `render` exits 0 and `validate` passes.
2. Duration is within one frame or one AAC packet of expected. For reverb or echo, the tail is allowed to extend by the declared decay, and that extension is asserted.
3. 48 kHz stereo is preserved.
4. Integrated loudness is above the −70 LUFS silence gate, and nothing is NaN or Inf (`astats`).
5. Sample peak stays below 0 dBFS, with no clipping counts.
6. The processed output differs from the bypassed render by more than a stated residual or correlation threshold, so the effect is not a silent no-op.
7. A coarse direction check where the effect has one: pitch up shifts the spectral centroid or the fundamental in the declared direction by roughly the declared semitones, within a wide tolerance; reverb raises energy after an impulse's end (an RT-like tail is present); a voice changer shifts the centroid or formants in the expected direction.
8. Integrated loudness after the effect stays within a few LU of bypass, so the effect has not blown up or collapsed the gain.

**Trade-offs:** The directional assertions are borderline "numbers". They are loose and can pass a bad-sounding effect, but they catch the common regressions: no-op, inverted parameter, silence, explosion. Smoke-only (render succeeds, not silent) would not catch an effect that silently bypasses, which is the most likely bug for chains with cross-build byte drift. A stricter numeric check would pretend to a quality claim the packet says no honest number supports. The owner's ear stays the judge of quality.

## Juror 2 (Claude Sonnet 5.5)

🗳️ **Juror 2** (Claude Sonnet 5.5) — **Q1 VOTE: (c), with the qualification that (b) is the acceptance gate and (a) is limited to master-stage and other document-declared programme properties. The build test is a port of the prototype's ADR-evidence script (same metric, same fixture), not a separate artifact.**

**Reasoning:** `verify` measures one mixed track and the packet says it cannot attribute a number to one element's effect. A per-capability check such as an EQ band cutoff, a gate, or a crossfade midpoint therefore cannot run there. A repo test that renders a fixed fixture is the only place the effect can be isolated against a bypassed control. `verify` is already the right place for properties the document declares, namely `target_lufs` and `ceiling_dbtp`, and ADR-0172 already assigns those to it. Porting the prototype script keeps one metric and one fixture from ADR through to CI. That avoids drift between what the ADR claims and what the build asserts, and it satisfies the evidence rule that the number is re-derivable.

**Trade-offs:** It costs two measurement homes and some discipline to keep them from overlapping. A port couples the test to the prototype's fixture, so the fixture must be committed and stable. Option (a) alone cannot see per-element effects. Option (b) alone leaves a user's real deliverable unchecked for the master target. A separate artifact would risk the ADR number and the CI assertion silently diverging.

🗳️ **Juror 2** (Claude Sonnet 5.5) — **Q2 VOTE: (a) ffmpeg's own meters (`ebur128=peak=true`, `astats`, a filter plus `astats` or `aspectralstats`), with no Rust crates in the test.**

**Reasoning:** `verify` already uses ffmpeg's `ebur128` as an independent witness, and the render runs on the user's installed ffmpeg. Measuring with the same toolchain keeps one definition of LUFS and dBTP across the ADR script, the CI test and `verify`. It adds no dependencies, and the existing Python evidence script can already call ffmpeg. A crate would be a second implementation that could disagree on gating or true-peak oversampling, which would make a CI failure ambiguous.

**Trade-offs:** The measurement depends on the ffmpeg build under test. The tolerance has to absorb cross-build and SIMD differences, and the packet notes some filters change bytes across builds. Assertions must therefore be on metrics with a tolerance, never on byte hashes. A crate would give a build-independent reference, but it would add a dependency and a divergence risk, so it is not worth it. A crate could be reconsidered only if a band-energy measure proves too coarse with `astats`.

🗳️ **Juror 2** (Claude Sonnet 5.5) — **Q3 VOTE: Loudness is ±1 LU, one-sided in effect: a `review` is raised when the integrated loudness is more than 1 LU off `target_lufs` in either direction, and the finding message distinguishes "below target" (likely heavy limiting) from "above target". True peak is a `review` only when the measured dBTP exceeds `ceiling_dbtp` by more than a small codec allowance of 0.3 dB. It is never an `error`.**

**Reasoning:** The target is a delivery target, and this is short-form, TTS-over-music work. The ±1 LU allowance (R 128 live/short-form, ATSC A/85) is the cited borrowed threshold that fits, and borrowed thresholds yield `review` (ADR-0061). ±0.5 LU would fire on ordinary single-gain results, because there is no compensation after the limiter. The message should still separate the two directions, since the below-target miss is the expected, explainable one and should point at the headroom review. For true peak, AAC adds inter-sample peaks after a correct limiter, so a strict "above ceiling" test would raise false reviews on correctly built projects. A small allowance keeps the review meaningful.

**Trade-offs:** The 0.3 dB figure is my judgement, not a cited standard, so the ADR must either measure it from the fixture, with a committed script, or state it as an estimate. A wider ±1 LU band hides misses of up to 1 LU, but that is acceptable for a `review`. Strict peak would be simple and standard-aligned but noisy. A larger allowance, such as 1 dB, would mask real overs. A purely one-sided loudness check would miss genuinely too-loud output, which is the more harmful direction.

🗳️ **Juror 2** (Claude Sonnet 5.5) — **Q4 VOTE: Commit the script plus inputs so the clips regenerate, and commit `measurements.json`. Do not commit the audio clips, except that the specific clips the owner actually judged are committed verbatim, once, as the verdict artifact. Use labelled A/B for prototypes. Record the owner's verdict in a committed verdict file next to `measurements.json`, referenced from the ADR.**

**Reasoning:** The evidence rule says a numeric claim needs a re-executable check committed with its inputs, so the script, inputs and `measurements.json` with exit-non-zero assertions are mandatory. Regenerated clips may differ across builds and CPUs, as the determinism facts show for several filters. The qualitative rule says a verdict needs the artifact itself committed verbatim, so the exact clips the owner heard must be preserved at the moment of judgement. Regeneration is not enough for the verdict, because it may not reproduce the clip the owner judged. Labelled A/B is sufficient because the owner's ear is the decider, and a single owner is not a blinded study. The point is hearing the effect at matched loudness, not defeating bias. Blind X/Y adds ceremony and a key to manage.

**Trade-offs:** Committing the judged clips adds repository weight, so keep them short and use a compressed format. Not committing every iteration's clips avoids churn. Labelled A/B admits expectation bias, which blind would remove, but that is of little value for one owner. Blind could be reserved for a contested effect. Committing nothing would break the qualitative evidence rule.

🗳️ **Juror 2** (Claude Sonnet 5.5) — **Q5 VOTE: A smoke check is a structural, non-perceptual regression test. It asserts that the render succeeds and the effect actually did something, bounded by sanity limits. It makes no claim of correctness.**

**Reasoning:** Reverb, pitch and voice changers have no honest numeric target, so the check should only catch breakage. The assertions are:
1. The render exits 0, `validate` passes, and the output is a decodable file.
2. The output duration is within a stated tolerance of the expected duration (exactly equal for non-time-stretching effects, within a bound for others).
3. The sample rate and channel layout equal the pipeline's (48 kHz stereo).
4. There is no silence: integrated loudness is above the `verify` silence gate (−70 LUFS), and the signal is not all zero.
5. There is no clipping and no NaN: the true peak is at or below a sane bound.
6. The effect is not a no-op: the processed output differs from the bypassed render by more than a minimum amount, for example RMS of the difference or a spectral distance above a floor.
7. The effect is bounded: loudness change versus bypass is within a generous window, so a runaway gain fails.
8. The result is deterministic within the same build: the same fixture rendered twice gives identical bytes, which is a property that holds per the packet. Cross-build comparison is not asserted.

**Trade-offs:** It cannot detect that a reverb sounds bad or a pitch is wrong, so the owner's ear stays the real check and the ADR must say so. The no-op and bounds thresholds are arbitrary, so they should be generous and documented as sanity limits, not acceptance criteria. Asserting a particular pitch frequency for pitch shift would be a real number, but I reject that framing here. Pitch has an honest number (fundamental shift on a sine fixture), so the packet's "no honest number" claim is partly wrong for pitch. If the fixture is a pure tone, that one can be upgraded from a smoke check to a measured check, while reverb and voice changers stay smoke.

## Juror 3 (Claude Fable 5.1)

🗳️ **Juror 3** (Claude Fable 5.1) — **Q1 VOTE: (c) — (b) for every capability, (a) only for document-declared programme properties; the CI test is a port of the prototype's evidence script, same metric and same fixture, with the threshold loosened to a stated tolerance.**

**Reasoning:** The packet's own facts settle the split. `verify` is defined as a witness independent of the engine that measures one mixed track and cannot attribute a number to a single element's effect. A per-capability check (energy below a cutoff after a gate, an equal-power sum at a crossfade midpoint) needs a fixture built so the number is attributable: a document with one element, a known source, the effect on versus bypassed. That is only possible in a repo integration test, so (b) is forced for capabilities. Conversely, the only numbers the user's document declares are `master.target_lufs` and `ceiling_dbtp`, which are programme-level and already assigned to `verify` by ADR-0172, so (a) covers exactly that set and nothing more. On the port question: the ADR evidence rule wants a committed re-executable check with its input data. If the CI test uses a different metric or fixture from the prototype's script, the ADR cites one number and CI defends another, and drift between them is undetectable. One fixture, one metric, two runners (the evidence script at ADR time, the `cargo test` on every leg thereafter) is the only arrangement where "the number stops reproducing" is caught.

**Trade-offs:** (b) alone would leave `master` unverified on real deliverables, which ADR-0172 already promises, so it is a regression of a prior decision. (a) alone cannot measure a capability (it is per-span, one mixed track) and would also force `verify` to recognise effect semantics, breaking its "never reads what the engine established" independence. The cost of (c) is two places to maintain, and the cost of the port is that the CI test must assert at a tolerance rather than the prototype's exact figure, because byte hashes hold only per (build, CPU) and CI runs three builds. That is the picture precedent (SSIM at a threshold, never byte equality) applied to audio; a separate artifact would be cheaper to write but is a numeric claim without a committed re-derivation, which the repo rule forbids.

🗳️ **Juror 3** (Claude Fable 5.1) — **Q2 VOTE: (a) ffmpeg's own meters, for both the CI test and `verify`, with one stated caveat: a meter run through `ffmpeg` is on the same binary as the engine, so the test must pin which filter and which print options it reads, and the ADR must name the meter.**

**Reasoning:** The floor is ffmpeg 7.1 and the user's install is the engine; `verify` is already defined as decoding with `ffprobe`/`ffmpeg`, and the silence gate already runs `ebur128`. Using ffmpeg's meters keeps the number the ADR cites, the number CI asserts, and the number `verify` reports as the same quantity measured by the same instrument. That matters in the one place the packet flags as hard: inter-sample true peak after AAC. `ebur128=peak=true` is the EBU-defined true-peak meter (oversampled), which is what `ceiling_dbtp` means; a Rust `ebur128` crate can do it too, but then CI, `verify` and the ADR would disagree by the crates' and ffmpeg's differing oversampling and K-weighting implementations, and a miss could not be classified honestly. Band energy via a filter plus `astats` (or `aspectralstats`) is the same instrument the engine's EQ uses, so the measured band is the band the capability claims to touch. The existing research is already backed by a Python script driving ffmpeg, so (a) is the continuation of practice, not a new dependency.

**Trade-offs:** (a) measures with the thing under test. The packet's determinism fact mitigates this: within one build, output and meter are both byte-stable, and the meters named (`ebur128`, `astats`) are not on the list of filters that drift across builds, so a meter divergence across CI legs is far less likely than an engine divergence. It also means the test parses ffmpeg's text output, which is brittle to format changes; the test must pin the parse and fail loudly rather than silently. (b) buys independence and a typed API, at the price of a second loudness implementation in the repo whose disagreement with the engine's meter becomes a permanent source of false `review`s and an extra crate to maintain and license. (c) has nothing on offer in the packet. If the owner later wants an independent witness, it should be the second meter in the ADR evidence script only, not what CI asserts.

🗳️ **Juror 3** (Claude Fable 5.1) — **Q3 VOTE: Loudness ±1 LU two-sided for a plain miss; an undershoot of any size is suppressed when `verify` can see the heavy-limiting condition the headroom review already predicts, otherwise a one-sided overshoot above +1 LU and an undershoot below −1 LU are both `review`. True peak: `review` only above `ceiling_dbtp` + 0.5 dB, with the allowance cited as a codec inter-sample allowance and stated in the finding; never an `error`.**

**Reasoning:** ADR-0172 fixes the class (always `review`, never `error`) and ADR-0061 fixes that a borrowed threshold is cited and yields `review`. What remains is which borrowed number. ±0.5 LU is R 128's programme tolerance for a delivery file that was mastered by a human with a real meter in the loop; the Montagent master stage is one measured gain with no compensation, through a limiter, then AAC. The packet names two legitimate misses, and both push the deliverable below target or above ceiling by amounts that ±0.5 LU would flag on honest renders, producing noise the owner learns to ignore. ±1 LU is the R 128 short-form and A/85 allowance and is the loosest figure with a citation; it absorbs the single-gain estimate error while still catching a stage that did nothing. For true peak, AAC inter-sample peaks after a correctly applied limiter are a documented fact of the format, and a `ceiling_dbtp` above −1 is already a review for exactly this reason; a strict "above the ceiling" check would flag a correct render on every TTS-over-music project with a −1 ceiling. A 0.5 dB allowance is the conventional codec headroom figure; it should be cited, and the finding should print the measured dBTP, the ceiling, and the allowance so the owner's ear can overrule it.

**Trade-offs:** ±1 LU will miss a stage that is off by 0.8 LU; given the stage's design that is within its own estimate error and not a wrong render. One-sided only (flag overshoot) would ignore a real failure mode (gain never applied, loudness far below target), so I keep the undershoot but let the already-existing headroom review carry it when limiting is heavy, to avoid double-reporting. The codec allowance means a deliverable can measure up to 0.5 dB above the ceiling with no finding; the packet says `verify` always reports the number, so the owner sees it regardless. Any tolerance tighter than the engine's own stage can hold turns `review` into a permanent warning, which is worse than no check.

🗳️ **Juror 3** (Claude Fable 5.1) — **Q4 VOTE: Commit the script, the inputs, and `measurements.json`; do not commit the rendered clips. Produce the A/B blind (X/Y with a committed key file) for the listening, and record the owner's verdict verbatim in the ADR as a quoted block that names the key and the measurement file's hash.**

**Reasoning:** The repo's evidence rule has two halves and this question straddles both. The numeric half (loudness match achieved, delta within tolerance, effect-on versus bypassed) is a script that re-derives the number and exits non-zero; the packet says the existing ffmpeg research already works this way, so the clips are derived data and the script plus inputs are the primary artifact. The qualitative half (the owner's ear) must be committed verbatim: that is the verdict text, not the audio. The clips themselves cannot be the verbatim artifact because the determinism fact says several candidate filters change bytes across builds, so a committed clip is a snapshot of one (build, CPU) that no CI leg can reproduce byte-for-byte; `measurements.json` with the metric at a tolerance is what can be reproduced. Blind X/Y with a key is the only way the recorded verdict means anything beyond "the owner preferred the version labelled processed"; the key is small and should be committed so the verdict is auditable. The verdict lives in the ADR because that is where the rule says qualitative evidence lives, and the ADR is what names the measured check.

**Trade-offs:** Not committing clips means a reviewer who wants to listen must run the script against a local ffmpeg, which costs minutes and may produce slightly different bytes on their build; the metric in `measurements.json` is what they compare, and the ADR should say so. Committing clips would be convenient and small for a TTS-over-music fixture, but it bakes in one build's output and invites the mistaken belief that CI could hash it. Blind costs the owner a step (listen, then open the key); labelled is faster but makes the recorded ear worthless as evidence. Recording the verdict only in the issue or the jury folder would split the evidence from the ADR that cites it.

🗳️ **Juror 3** (Claude Fable 5.1) — **Q5 VOTE: A smoke check is the same fixture rendered through the real pipeline with these assertions: (1) render exits zero and the output decodes with `ffprobe`; (2) duration is within one frame of the bypassed render (within one hop for pitch, since the chain may resample); (3) the processed output is not silent (integrated loudness above the −70 LUFS gate) and not the bypassed output (sample-domain difference above a floor, measured with `astats` on the difference signal); (4) true peak does not exceed the bypassed render's peak by more than a stated headroom unless the effect declares it adds gain; (5) no NaN/inf/DC offset (`astats` reports clean). Nothing about quality.**

**Reasoning:** The packet says reverb, pitch and voice changers have no honest number, and that is correct: there is no scalar that says a reverb is right. What a smoke check can honestly claim is that the effect ran, changed the signal, did not break the container, did not blow the level, and did not alter the timeline. Each of those is a measurable yes/no with a defensible threshold that holds across builds, which matters because the pitch chain is on the list of filters that change bytes across builds, so byte or hash assertions are exactly what a smoke check must avoid. Assertion (3) is the one that catches the most common real failure, an effect silently bypassed by a bad filter-graph string; (2) catches the pitch chain's classic failure of stretching time; (4) catches a reverb that doubles level. The owner's ear remains the acceptance for quality, and the A/B of Q4 still happens; the smoke check only guards the pipeline.

**Trade-offs:** A smoke check passes a reverb that sounds terrible, by design; the alternative, inventing a number (a decay-time estimate, a pitch-detector's reported shift), would be a numeric ADR claim needing a re-executable check whose reproduction across builds the determinism fact says is not guaranteed, and it would be read as a quality guarantee it is not. The "not identical to bypass" floor must be picked with care so a very subtle effect at low mix does not fail; stating the floor and the fixture's mix setting in the ADR handles it. Skipping the smoke check entirely would leave these three capabilities with no CI coverage at all, which breaks the standing rule that every ADR names a check.

## The owner's ruling

The owner ruled with the Judge's read, in full:

- **Q1:** (c), unanimous. Every capability gets a repo integration test on a fixed fixture,
  ported from the prototype's evidence script (same metric, same fixture), asserted at a stated
  tolerance and never by hash. `verify` checks only what `master` declares.
- **Q2:** ffmpeg's own meters (`ebur128=peak=true`, `astats`, a filter plus `astats` or
  `aspectralstats`), unanimous. The ADR names the meter, and the test pins how it parses the
  output and fails loudly if parsing breaks (Juror 3). A Rust FFT in the test is allowed for
  band energy only, if an ffmpeg-filtered measurement proves noisy across legs (Juror 1).
- **Q3:** loudness ±1 LU in both directions, unanimous. The below-target miss is not suppressed;
  its message names heavy limiting and the headroom review as the likely cause (Juror 2). Keeping
  `verify` independent rules out reading the document's other findings. True peak: a `review` above
  `ceiling_dbtp` + 0.5 dB (Jurors 1 and 3), provisional until a committed script measures AAC
  160k overshoot after `alimiter`.
- **Q4:** commit the clips the owner judged (Jurors 1 and 2), stated as a record and not a
  reference to compare against. Use a blind X/Y listen with a committed key (Jurors 1 and 3). The
  verdict goes in a file next to the clips, and the ADR quotes it.
- **Q5:** the smoke check is the common core of all three ballots: it renders; its length is
  exact or within a stated bound; 48 kHz stereo is preserved; it is not silent; it has no
  NaN/Inf or clipping; it is not a no-op against bypass; its loudness stays within a generous
  window of bypass. Pitch shift moves from smoke to measured, as a fundamental shift on a sine
  fixture within a tolerance (Juror 2). Echo and reverb also assert their tail (Juror 1).
  Reverb and voice changers stay smoke.

# Ballots: round 2

Packet: [`QUESTION-ROUND-2.md`](QUESTION-ROUND-2.md), sent blind and identical to three jurors
dispatched in parallel. Ballots are verbatim.

## Juror 1 (Claude Opus 5.5)

🗳️ **Juror 1** (Claude Opus 5.5) — **Q6 VOTE: (c) Split by purpose. Synthetic lavfi signals for every numeric check; one shared, committed real fixture (TTS narration over a music bed) for the ear's A/B; licence and provenance in a sidecar file committed next to each fixture.**

**Reasoning:** Numeric claims need signals whose expected value can be worked out in advance: a sine for EQ gain at a frequency and for pitch, an impulse for reverb or echo tails, a sweep for band shape, seeded noise for gate and compressor thresholds. Lavfi generates all of these from a command line, so the "input data" the evidence rule asks for is the generator command itself, committed in the test, with no binary in the repo. The ear cannot judge sines. It needs material like the lead workflow, so one shared real fixture serves every A/B and keeps judgements comparable across capabilities. Restoration already waits for a recorded-voice fixture, and that file goes in the same shared folder under the same rules when it arrives. Each real fixture gets a sidecar committed next to it (for example `fixture.provenance.md` or `.json`) recording source, author or TTS engine and voice, licence, date, and how it was produced. The ADR cites that sidecar.
**Trade-offs:** Some binary audio in the repo (keep it short, a few seconds, and still committed verbatim). Synthetic signals can miss content-dependent behaviour such as pumping on speech. That is what the A/B is for. (a) alone leaves the ear nothing realistic to judge. (b) alone makes every number depend on a recording, so expected values cannot come from the filter's definition.
