(My answers assume Q1 is decided as "kept, but stating whose checks ran", with the header naming the checks that ran instead of printing a zero scoreboard for them. My ballots don't depend much on that choice.)

🗳️ **Juror 1** (Claude Opus 5.5) — **Q2 VOTE: B, with one change: the new field lists the finding classes whose checks ran (e.g. `checks_run: []`, `["layout"]`, or all six), and the text is generated from it.**

**Reasoning:** JSON is canonical, and agents mostly read the JSON over MCP. Under A, a JSON consumer still gets `summary: {error:0, review:0, …}` from `timeline`, and that can't be told apart from a clean validate. That is the exact false confidence from the incident, moved to the channel that matters most. A also breaks "nothing is assembled twice": the prose would state a fact ("checks not run") that the JSON doesn't have, worked out from a `tool`-name lookup table inside the renderer. Every new verb would then need that table updated, or it would silently tell the lie again. With a field, the report states its own scope, and the text only renders it. Keeping `summary`'s shape is right, because ADR-0011's "one thing to parse" means consumers shouldn't need a different schema for each verb. The zeros stay parseable, and the field next to them says which zeros mean anything.
**Trade-offs:** B changes the JSON schema, so the fixtures, snapshot tests and MCP contract all move, and every verb has to fill the field in correctly. A verb that reports the wrong list would lie in a more authoritative voice than today's. A is cheaper and fixes the prose symptom the agent actually hit, but it leaves the canonical form ambiguous. It also puts meaning in the renderer, which the architecture explicitly forbids. The cost of B is one field that every verb must get right. I'd accept that over a renderer that has to know every verb.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q3 VOTE: B. Name what ran, expressed as the set of classes checked. The three tiers then come out of the data (empty / subset / full) rather than being special-cased.**

**Reasoning:** Two tiers would mark `fmt` as "checked" while it prints `0 reviews, 0 notes` it never looked for. That is the incident's failure at smaller scale. An agent running `fmt` after a truncated validate would read "checked, 0 reviews" as confirmation, just as it read timeline's zeros. The table in the question already shows three kinds of zero: real, real for one class only, and meaningless. Two tiers merge the last two into the first. If the field is a list of classes, the header can print a count for each class that ran and mark the rest as not run (e.g. `3 layout — errors/reviews/notes/unchecked/drift not checked (validate runs them)`). No extra enum is needed, and the list works for any partial-check verb added later.
**Trade-offs:** The header gets longer and less uniform, and the rendering logic has to handle a partial set instead of a boolean. It also commits the project to keeping each verb's declared check set true as the checks change, and a stale subset list is a new way for the report to lie. Two tiers are simpler to render and to test. But their simplicity comes from folding the very ambiguity we're trying to remove back into the report, so I don't think it's worth the saving.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q4 VOTE: B, with the NOT CHECKED text generated from the same checks-run field. It shouldn't be a second sentence added by hand.**

**Reasoning:** ADR-0006 says the report "ends with its own scope, unconditionally". Today, timeline ends with *validate's* scope ("validate verifies that the file is internally legal"), so the closing statement is currently false for every non-validate verb. Fixing only the header leaves a report that contradicts itself between its first line and its last. The incident's mechanism also matters here: the agent's mistake was `tail`. Tail keeps the end of the output and drops the top, so the header is exactly the part a truncated read loses, and the NOT CHECKED block is the part it keeps. A statement that only appears at the top doesn't protect the reader the incident showed us. Generating both from one field keeps "nothing assembled twice" intact.
**Trade-offs:** NOT CHECKED stops being one fixed text. That makes it longer and changes it per verb, so tests that pin the exact wording will churn. There's also a mild risk of verbosity on verbs whose users never cared about validate. A (header only) is less churn and keeps a stable closing text, but it leaves the ADR-0006 closing scope wrong and puts the fix only where truncated reads don't reach. The sentence should be short and mechanical ("validate's checks were not run: <classes>. Run validate for them."), so the cost stays at one line.
