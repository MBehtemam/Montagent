# Juror: Sonnet

Given [BRIEF.md](./BRIEF.md) in isolation — no access to ADR-0039, no access to the other
jurors' ballots.

---

1. **What unit should the check range over?** `group` as-is cannot be the unit. The evidence is direct: measured against a real, correct, shipped file, every one of five groups — a photo card, three siblings, and an eight-element quiz group — trips the check. That's not an edge case, it's the modal case, and the project's own governing principle for `validate` is that a check firing on the overwhelming majority of correct files is worse than no check at all. The root cause is a category error: `group` was deliberately specified as a vocabulary/organizational label, explicitly render-inert, with nothing about timing derived from it. Using it as the range for a *motion-synchrony* check asks a label that was designed to carry no timing semantics to suddenly carry timing semantics. The check needs a narrower, opt-in unit — call it a "motion unit": an explicit, small set of elements (and, per point 2, specific properties on them) that an author declares are meant to move together. This could be a new optional field (e.g. `motionGroup` or `syncWith`, listing element/property pairs), separate from `group`. It must be opt-in because the hazard only exists where an author actually intended coupling — and intent is exactly what a bare shared `group` string does not carry.

2. **Should it be scoped per-property?** Yes, unambiguously. Evidence point 2 shows that a same-`t` reading across all properties breaks on a completely unremarkable file: a headshot animated on `scale` and a caption animated on `opacity` in the same group, on unrelated schedules, with no coupling ever intended between those two channels. There is no reason a `scale` timeline and an `opacity` timeline should agree — they're different visual behaviors. So the check must never compare `t` values across differing properties; it can only compare `t` values for the *same* property across the declared members of a motion unit (e.g., all `x` keyframes among the elements listed as moving together). This scoping should be expressed explicitly, not inferred: the motion-unit declaration itself should specify which property (or properties) are the coupled ones — e.g. `{"elements": ["bar1","text1"], "property": "x"}` — rather than leaving a reader or the validator to guess that "elements share a group" implies "their `x` and only their `x` must match." Discoverability comes from the declaration being data in the file, not convention: an author (or an agent generating the file) sees a field named for exactly what it does.

3. **How would a deliberate stagger be expressed?** The check as commissioned can't distinguish 35600/36300/36700 (an intentional staggered entrance) from a coupled-delta bug, because "keyframe `t`s disagree" is satisfied by both. The fix isn't a suppress-flag bolted onto an already-fired check (that still requires every author to pre-emptively know about and opt out of a check they may never have heard of, which the brief explicitly rules out as unacceptable). The fix is to change what the check asserts: instead of "all `t` values in the unit must be equal," it should assert "all `t` values in the unit must equal the *declared offsets* for this unit" — and the motion-unit declaration itself is the place a stagger gets expressed. If a motion unit carries no offsets, the default expectation is synchronous (delta 0) and the check fires on any disagreement. If it carries per-element offsets (e.g. `{"elements": [{"id":"bar1","offsetMs":0},{"id":"text1","offsetMs":700},{"id":"card1","offsetMs":1100}]}`), the check verifies actual deltas against *those* declared deltas, and a correct stagger — deliberately authored as such — never fires. This makes the check compare the document against the author's own stated intent rather than against a uniform assumption, which also satisfies the "never assert intent the document doesn't carry" principle: the check only ever reports that a declared relationship is violated, never that an undeclared one should have held.

4. **Is the cross-property hand-off case in scope?** No — and it shouldn't be forced into scope. Evidence point 4 shows a structurally different relationship: "property A's animation ends where property B's begins" is a *sequencing* constraint between two different property channels, not a *synchrony* constraint on one property across elements. Trying to make one check catch both would recreate exactly the problem in point 2 — conflating channels that have no inherent reason to be compared — except worse, since now it's cross-property by design rather than by accident. It's also a different shape of check entirely: sync-check compares `t` for the same property across a set index (elements), hand-off compares `t` (and matching endpoint values) for different properties, potentially within a single element or across elements. This belongs to a separate, distinctly-named check (a "hand-off" or "relay" constraint) with its own opt-in declaration expressing which two property/element endpoints are meant to meet, if the project decides that hazard is worth mitigating at all — it is not automatically in scope just because it was discovered while testing this one.

**Verdict: retract the check as commissioned from `validate` in its current group-wide, all-properties, no-offset form, and replace it with a narrow, opt-in "motion unit" declaration — an explicit list of `{element, property}` members plus optional per-member offsets — that `validate` checks for keyframe-`t`-versus-declared-offset disagreement only among a unit's declared members, reporting at `review` severity (never `error`, since a desync is a plausible-but-unconfirmed slip, not a self-evident illegality) something like "motion unit `lower-third-1`: `text1.x` keyframe at t=1200 does not match declared offset (+0ms from `bar1.x`, expected t=1000)".**

Reasoning: every one of the four failures traces to the same design error — using an ambient, render-inert vocabulary label (`group`) as a stand-in for author intent about motion, and assuming a single global rule ("all `t`s must match") captures that intent. `validate`'s own stated bar is that an opt-in check is worth nothing and a noisy check is worse than none; a check that fires on 5/5 real groups fails that bar outright regardless of how it's scoped afterward, because the underlying signal (shared `group`) is simply the wrong signal — it was never meant to carry timing information, so no amount of patching (per-property scoping, offset tolerance) rescues an approach anchored to it. The only way to keep the check both meaningful and quiet is to require the coupling to be stated by the author as data — property-scoped, with explicit offsets defaulting to zero — at which point the check stops guessing at intent (satisfying "must never assert intent the document doesn't carry") and instead verifies a stated relationship, which is exactly the kind of thing `validate` is built to do on a single document with no prior version. This also cleanly resolves the stagger problem (point 3) without requiring blanket author awareness, since the offset is supplied at the moment the stagger is authored, not discovered after the fact as an exception. The hand-off case (point 4) is correctly left out: it's a different relationship shape and deserves its own opt-in mechanism rather than being smuggled into this one and repeating the same over-broad-scope mistake at one remove. Nothing here needs `compare`'s before/after machinery — the coupling is either declared in the current document or it isn't, and checking a stated relationship against actual values is squarely single-document work; only detecting that an *undeclared*, historically-observed synchrony broke would need `compare`, and that is explicitly out of scope for what was commissioned here.
