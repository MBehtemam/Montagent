# Ballots: the transitions ticket, as an agent would work with it

Packet: [`QUESTION.md`](QUESTION.md), sent blind and identical to three jurors dispatched in
parallel. Ticket: [#803](https://github.com/MBehtemam/Montagent/issues/803). Ballots are verbatim,
grouped by juror. The owner ruled with the Judge's read (below the ballots); the ADR is
[ADR-0176](../../../adr/0176-a-transition-carries-the-audio-across-its-cut-in-one-field-and-an-audio-only-crossfade-is-a-transition-kind.md).

## Juror 1 (Claude Opus 5.5)

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-1 VOTE: (a) the transition carries the audio behaviour in one field**

**Reasoning:** The window already exists as two literals, `start` and `end`, on the transition. If a second element repeated it, the agent would have two strings to keep in step on every trim, and a whole class of drift errors would follow. ADR-0145 says a derived thing is changed through the literal that generates it, and the window comes from the overlap. With one field the edit is a single `"audio":"…"` string next to the window it uses. An agent reading the transition sees picture and sound together.
**Trade-offs:** Picture and sound windows can't differ (no J/L-cut style offset crossfade). That's acceptable for now: an offset audio crossfade can still be written with volume keyframes. Option (b) adds an element, a sync rule and new error codes only to repeat data the file already holds.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-2 VOTE: (b) two curves, key `audio`, values `"cut" | "constant_power" | "constant_gain"`; absent = `"cut"` (see Q-4); the value guidance recommends is `"constant_power"`**

**Reasoning:** Constant power holds level for uncorrelated material under `amix normalize=0`, so it is the right choice almost every time. Constant gain is the right choice for correlated material (the same source on both sides, such as a split clip), where constant power bumps about 3 dB. Both map exactly to `afade` `qsin`/`tri`, and an agent can tell them apart from a one-line description. Putting `"cut"` in the same closed vocabulary means one key covers "no crossfade" too, so turning the crossfade on or off is a one-string replace.
**Trade-offs:** Exponential is left out. It is a stylistic choice that agents can't pick reliably, and an exponential fade can already be approximated with eased volume keyframes. Adding it later is backward-compatible. A single fixed curve (c) would give a wrong level on correlated cuts with no literal to fix it.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-3 VOTE: (b) at the end of the element's own chain, after `volume` and `[pan]` and before `adelay`**

**Reasoning:** The crossfade is an edit-point gain, not part of the sound design. Putting it last means no `audio_effects` compressor or limiter can undo the fade, the same reason ADR-0169 puts effects before `volume`. Placed before `adelay`, its times are element-local and come straight from the transition window, so it stays sample-exact like volume (ADR-0175). Multiplying after `volume` also gives the simple product that Q-6 and Q-7 report.
**Trade-offs:** A reverb tail inside `audio_effects` is faded along with the dry signal rather than ringing past the cut. That is the conventional result. Option (a), before effects, would let dynamics processing flatten the fade.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-4 VOTE: (a) absent = hard cut (today's behaviour, byte-identical renders), plus a `review` finding when both bridged elements carry audio and `audio` is absent**

**Reasoning:** Changing the sound of existing projects silently is the worst outcome on the list. Option (b) does exactly that, and option (c) breaks every file. A review finding makes the gap visible without breaking anything. It should fire only when both sides have an audio stream and neither is a `volume: 0` remap. Its repair field gives both literals: write `"audio":"constant_power"`, or write `"audio":"cut"` to keep the hard cut on purpose. Writing either value clears the finding, so cuts the author chose don't keep flagging. An agent writing a brand-new transition copies the schema example and guidance, which show `"audio":"constant_power"`. If it forgets, `validate` points it to the field.
**Trade-offs:** Existing projects that use transitions get a new review finding: noise, but not a failure, and each one is a single edit to clear. The cost is that the default is not the "best-sounding" value, but defaults here must preserve existing renders.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-5 VOTE: (a) widen `transition` with `kind: "audio_crossfade"`; the same key `audio` selects the curve in both forms**

**Reasoning:** An agent already knows `from`/`to`/`start`/`end`, the window-equals-intersection rule, and the existing codes (`E-TRANSITION-RANGE`, `-NO-OVERLAP`, `-REF-SELF`). All of them carry over unchanged. Only the ref rule widens, and only for this kind: `audio` or audio-bearing `video` may be named, while the visual kinds still refuse audio-only refs with `E-TRANSITION-REF-MISSING`. With one key name, an agent that has learned it once can use it everywhere. For `audio_crossfade`, the `audio` key is required and `"cut"` is refused (an error with the repair "use constant_power or constant_gain, or delete the transition"). `direction`/`ease` are refused for this kind. Separate tracks and overlap are already required by the existing rules.
**Trade-offs:** The `transition` element gets one kind whose picture behaviour is "none", and that kind has its own required-key rule. A separate element type (b) would repeat every rule and code for no gain. Option (c) keeps the hand-keyframed approach, which can't be read back as a crossfade, and it means writing four or more literals that must be kept in step.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-6 VOTE: (b) a `review` finding when a bridged element's volume keyframes change level inside the window; a `review` (not an error) when the audio field has nothing to fade**

**Reasoning:** Stacking a crossfade on a manual fade or a duck is legitimate and the result is well defined (gains multiply), so an error would be wrong. Ignoring it (a), though, would let a double fade (one that drops to near silence) pass quietly. The review names the transition, the element and the keyframe times. Its repair is "delete the manual fade keyframes inside [start,end], or set `audio` to `cut`". If a bridged element has no audio stream (`N-NO-AUDIO-STREAM`) or is a remap with `volume: 0`, that side contributes silence. The other side still fades, which is audible and usually unintended: a fade-in from silence rather than a crossfade. That case gets a review finding naming the silent side, with the repair "set `audio` to `cut`, or remove the field". On `kind: "audio_crossfade"` where neither side has audio, it is an error, because the element has no effect at all.
**Trade-offs:** More review findings to read. An error class would block valid creative stacking, and silence (a) breaks the "loud with a repair" rule.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-7 VOTE: `query --at` resolved gains with their source, `timeline` showing the audio value on the transition row, and `compare` treating `audio` as a transition field. `shift` needs nothing new. Add no derived values to the file.**

**Reasoning:**
- **`query --at`:** at an instant inside the window, it lists each sounding element with its factors and the product: volume v, crossfade gain g from transition `t1` with its curve, and resolved v·g. This is the one place an agent can see why something is quiet, and it explains stacking (Q-6).
- **`timeline`:** the transition row shows `audio=constant_power` (or `cut`), so the agent can see the audio behaviour at a glance without opening the JSON.
- **`compare`:** it diffs `audio` like any other transition field, so a changed curve shows up as a transition change.
- **`shift`:** it already moves transition windows with their bridged elements, and the crossfade window *is* that window. No new consistency logic is needed. Its tests should simply cover the audio kind.

**Must NOT add:** a stored or written-back resolved gain or curve samples in the project file; a separate audio-crossfade row that duplicates the window in `timeline`; and any second copy of the window anywhere an agent might try to edit it.
**Trade-offs:** Agents need `query --at` to see the actual combined level, because `timeline` shows only the chosen curve. That is deliberate: it keeps `timeline` compact and the file free of derived values.

## Juror 2 (Sonnet 5.5)

🗳️ **Juror 2** (Sonnet 5.5) — **Q-1 VOTE: (a) the transition itself carries the audio behaviour in a field**

**Reasoning:** The window already exists on the transition and validate already forces it to equal the intersection of the two bridged elements. A second element would store the same window twice, which breaks the one-string-per-authored-choice rule (ADR-0145). Under exact-string replace, an agent that moves one copy and misses the other gets a mismatch error, and only after the fact. With a field on the transition, the window is moved once, through the elements.
**Trade-offs:** The transition element now covers both picture and sound. Splitting the two (for example, a dissolve with no audio blend) is done by omitting the field, so nothing is lost. Option (b) costs a double-write and an extra drift code, and gains nothing.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-2 VOTE: (a) all three, selectable. Key `audio_curve` with values `constant_power`, `constant_gain`, `exponential`. The default when the key is present is `constant_power`.**

**Reasoning:** It is a closed vocabulary, it maps one-to-one to `afade` curves (qsin, tri, exp), and it matches the Premiere precedent. Each choice is a single string an agent can swap. A fixed curve cannot fix the 3 dB dip in the correlated-signal case or the tail-heavy case, and an agent would then have to fall back on hand-written keyframes.
**Trade-offs:** Three values mean a bit more documentation and test surface than two. The cost is small, because all three are one ffmpeg parameter. The key name carries no unit because the curve is not a level (ADR-0170 only governs level keys). A bare `audio_curve` could be read as meaning that audio is crossfaded, so the on/off switch must be spelled out in Q-4.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-3 VOTE: (b) after `volume` (and pan), at the end of the element's own chain, just before `adelay`**

**Reasoning:** The crossfade is a property of the join and not of the source. It should multiply whatever the element would otherwise sound like, including the author's ducking and any compressor output. Putting it before `audio_effects` would let a compressor or limiter undo the fade shape. That is exactly the failure that ADR-0169 put effects before `volume` to prevent. Placing it after `volume`, at the end of the element's chain, keeps the fade shape exact and the sum under `amix normalize=0` predictable.
**Trade-offs:** The fade does not feed into the effects, so a reverb tail is not faded along with the clip. The fade timing is still sample-exact, and the gain is applied after the other stages. Placing it before `audio_effects` (option a) would be wrong because a compressor then reshapes the fade.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-4 VOTE: (a) absent means today's behaviour (a hard audio cut); guidance tells agents to write the field**

**Reasoning:** The no-silent-change rule decides this. Existing projects must render byte-identically, and (b) changes the sound of every project that uses transitions. Option (c) is a schema break that forces edits to every existing file. Absent-is-today is also the only choice that keeps the field a plain authored literal. The cost is one extra field on each new transition.
**Trade-offs:** An agent that forgets the field gets a hard audio cut under a soft picture dissolve, which is silent and wrong-sounding. To close that gap, `validate` should raise a `review` finding when a video→video transition has no audio field, with the repair "write `audio_curve`, or `none` to confirm the hard cut." A new transition would then be authored with `audio_curve: constant_power` as the normal default. Agent guidance and the schema examples should show that pattern, and `none` should be accepted as an explicit value so a deliberate hard cut can silence the finding.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-5 VOTE: (a) widen the `transition` element with a new `kind` `audio_crossfade`. Its `from`/`to` may name `audio` or audio-bearing `video` elements. The visual kinds keep refusing audio-only refs. The curve key is `audio_curve` in both places.**

**Reasoning:** The window, the overlap check and the `from`/`to` checks already exist and have an established code set. The audio-only form reuses them, and `shift`, `compare` and `timeline` already know how to handle transitions. One key name for both forms means an agent learns the vocabulary once. In the audio-only kind, `audio_curve` is required with no `none` value, because `none` would make the element meaningless. A new element type (b) would duplicate the entire transition machinery. Option (c) forces the agent to hand-build two keyframe ramps that must stay in step, which is the same drift problem as Q-1(b).
**Trade-offs:** The `transition` element now has a kind that makes no picture, so the kind list needs a clear note. The ref check for `from`/`to` becomes dependent on the kind: visual kinds refuse `audio` elements and the audio kind accepts them. `E-TRANSITION-REF-MISSING` needs a message that names the kind. A separate new type would avoid this, but that cost is lower than building a parallel validator.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-6 VOTE: (b) a `review` finding when a volume keyframe changes the level inside the window. For a bridged element with no audio stream, or a speed-ramped `video` carrying `volume: 0`, the finding is also a `review` (not an error), and the fade is skipped for that element.**

**Reasoning:** Stacking is legitimate, because an author may want a duck under a crossfade, so it should not be an error. It is also easy to do by accident, for example a manual fade plus a crossfade giving a double dip. A `review` finding is loud and carries a repair, and it still lets the project render. For an element with no audio stream (`N-NO-AUDIO-STREAM` already exists) or a ramped `video` at `volume: 0`, there is nothing to fade. Erroring would force the agent to remove the field just to pass validation, and the crossfade is meant to describe the join. So the finding says "this side is silent, the crossfade applies to the other side only".
**Trade-offs:** A review finding on every legitimate duck can be noise, so the finding should name the keyframe and the window and fire only when the level actually changes inside the window. Nothing at all (a) hides a real double-fade mistake. An error (c) blocks valid stacking and punishes intentional work.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-7 VOTE: Smallest set: `query --at` inside the window (sounding elements, resolved gain per element, and the transition id and curve that produced it) plus `timeline` showing the audio curve on the transition row. `shift` must move the window and the bridged elements together. `compare` treats `audio_curve` as part of the transition. Do NOT add a separate audio-crossfade report, a waveform or loudness estimate, or any second place to edit the curve.**

**Reasoning:** An agent is misled when it hears a dip or a hard cut and the tools show nothing about why. `query --at` is where an agent asks "what do I hear at this instant", so it must show the crossfade gain as a separate factor from `volume`. That is how an agent tells a stacked double-fade from a single fade. `timeline` is where the transition is discovered, so the curve (or "hard cut") should show there. `compare` already diffs transition fields, so a new field needs no special treatment, provided it is reported as a change to the transition. `shift` must keep window and bridged elements consistent, as it already does for transitions.
**Trade-offs:** Resolving the gain in `query --at` needs a small computation, but it is the same arithmetic the renderer uses. Adding a separate audio-crossfade view, or any derived value an agent could try to edit, would break the exact-string-replace rule and create two sources of truth.

## Juror 3 (Fable 5.1)

🗳️ **Juror 3** (Fable 5.1) — **Q-1 VOTE: (a) the transition itself carries the audio behaviour in a field**

**Reasoning:** The window already exists and is already policed (`E-TRANSITION-RANGE` pins `start`/`end` to the intersection of the two bridged elements). An agent editing a dissolve should touch one element, one string. A single key on the transition (I will call it `audio` throughout) is discoverable by reading the transition schema, has a one-line edit footprint, and cannot drift from the picture window because there is no second copy. `shift`, `compare` and `timeline` already treat the transition as one row; a field on it inherits all of that for free.
**Trade-offs:** (b) makes the author write the same two integers twice and then adds a validator whose only job is to catch the drift it created; every `shift` must move three things instead of two; every `compare` shows two rows changing for one authored decision. The only thing (b) buys is independence of the audio window from the picture window (a J-cut or L-cut), and that is not a crossfade at all: it is authored today, correctly, as volume keyframes plus an offset, and Q-5 leaves that path open.

🗳️ **Juror 3** (Fable 5.1) — **Q-2 VOTE: (b) two curves, under one key `audio` with the closed vocabulary `cut | constant_power | constant_gain`; default (absent) is `cut`, and the curve an agent should reach for first is `constant_power`**

**Reasoning:** Two curves are genuinely different answers to a real question, not taste: under `amix normalize=0`, constant power holds level for two unrelated signals (the normal case: two different clips), while constant gain is the correct curve when the two sides are the same source (a cutaway back into the same take, or a re-used bed), where constant power bumps about +3 dB at the midpoint. An agent can be told that rule in one sentence. Folding on/off into the same key as the curve (`cut` is a value, not an absent key) means there is exactly one string to replace and `query` can always print a value; it also makes Q-4's default an explicit word rather than a silence.
**Trade-offs:** Dropping `exp` loses Premiere parity on paper, but exponential is a stylistic fade, not a correctness choice; it adds a third option for agents to pick between with no rule to pick by, and nothing in the planning map needs it. It can be added as a fourth value later without breaking a single existing project. (c) one fixed curve is tempting for simplicity but makes the same-source case audibly wrong with no repair other than ripping the transition out and hand-keyframing.

🗳️ **Juror 3** (Fable 5.1) — **Q-3 VOTE: (b) after `volume` and `pan`, at the end of the element's own chain (`… → volume → [pan] → transition gain → adelay → amix normalize=0`)**

**Reasoning:** The crossfade is a mix-time relationship between two elements, not part of either element's sound design. The whole point of a constant-power pair is that what reaches `amix` from the two sides sums to level; that is only guaranteed if nothing downstream of the fade can re-shape the level. ADR-0169 already put `audio_effects` before `volume` so a compressor cannot push a dip back up; the same argument applies with more force here, because here the dip is the entire feature. Placing it after `volume` also keeps the authored `volume` keyframes meaning what they mean today (ADR-0175: heard on the sample the instant names), and makes the Q-6 stacking finding a simple multiplication the validator can reason about.
**Trade-offs:** (a) before `audio_effects` lets a compressor or limiter undo the fade silently, which is exactly the failure that cannot be reported by `validate` from the file. Putting it after `adelay` (timeline time) would be an implementation convenience for `afade` since the window is in absolute ms, but that is a build-ticket detail; the decision here is only that it is outside and after the element's own chain and before summation.

🗳️ **Juror 3** (Fable 5.1) — **Q-4 VOTE: (a) absent means today's behaviour (`cut`), every existing project renders byte-identically; plus a `review` finding when a visual transition bridges two audio-bearing elements and `audio` is absent**

**Reasoning:** A silent change to the sound of every existing project with a dissolve is the one thing the judging rule forbids outright, so (b) is out. (c) breaks every existing file for a field most of them will set to the default anyway. (a) is the only option with zero silent change, but "absent" on its own is also silent in the other direction: a brand-new agent writing a dissolve will not know the key exists. So `validate` should say so: a `review` finding (e.g. `R-TRANSITION-AUDIO-UNSET`, repair: "add `\"audio\": \"constant_power\"` to crossfade the sound, or `\"audio\": \"cut\"` to keep the hard cut") fired only when both bridged elements actually carry an audio stream. It does not block render, it does not alter output, and once an agent writes either value it goes away forever. An agent writing a new transition under this choice writes `audio` explicitly every time (CONTEXT guidance plus the finding make it so), choosing `constant_power` unless both sides are the same source.
**Trade-offs:** Existing projects with transitions will light up with one review finding per transition on their next `validate`. That is noise once, with a one-string repair, and it is the honest price of a default that preserves old renders while still surfacing the new capability. Making `audio` required later (option c) remains possible after a deprecation window if the review finding proves insufficient.

🗳️ **Juror 3** (Fable 5.1) — **Q-5 VOTE: (a) widen `transition` with a new `kind: "audio_crossfade"`; one key name `audio` for both forms**

**Reasoning:** An audio-only crossfade has exactly the shape a `transition` already has: two refs, a window that must equal their intersection, two tracks, the same `E-TRANSITION-RANGE` / `-NO-OVERLAP` / `-REF-SELF` rules, the same `shift`/`compare`/`timeline` handling. A separate element type (b) would duplicate all of that and give agents two things to learn that behave identically. Per-kind rules keep it closed: visual kinds keep refusing audio-only refs (`E-TRANSITION-REF-MISSING` unchanged); `audio_crossfade` requires both refs to carry an audio stream (`audio` or `video`), refuses `direction`/`ease` as unknown keys for that kind, and requires `audio` to be present and not `cut` (an `audio_crossfade` with nothing to do is an error with repair "set `constant_power` or `constant_gain`, or delete the transition"). One key name, one vocabulary, one mental model: "a transition may carry sound across its window, and `audio_crossfade` is the one that carries only sound."
**Trade-offs:** The `audio` key has a different presence rule per kind (optional on visual kinds, required on `audio_crossfade`), which is a small irregularity an agent can hit once and repair from the finding. (c) stays available and is still the right answer for J/L-cuts and anything whose window is not the intersection; the curve shapes it cannot express (qsin vs. a lerp) are the reason to add the kind at all.

🗳️ **Juror 3** (Fable 5.1) — **Q-6 VOTE: (b) a `review` finding when a volume keyframe changes the level inside the window; missing audio stream is an `error` only on `audio_crossfade`; a constant `volume: 0` side is a `review`**

**Reasoning:** The stacking case has two very different authors. One wrote a manual fade before transitions could carry audio and is now double-fading by accident; the other is ducking a bed under narration that happens to span the cut and is doing it on purpose. `validate` cannot tell them apart from the file, so an error (c) would forbid a legitimate edit, while nothing (a) leaves the accidental double-fade silent. A review (`R-TRANSITION-VOLUME-STACK`, repair: "remove the keyframes inside `start`..`end` of this transition, or set `audio: cut` and keep your own fade") is loud, has a one-edit repair either way, and stops firing as soon as the author chooses. For a bridged element with no audio stream: on a visual kind this is fine (the other side still fades; `N-NO-AUDIO-STREAM` already says what there is to say), on `audio_crossfade` it is an error because the element exists to crossfade sound and one side has none. For a speed-ramped `video` carrying `volume: 0` (or any constant 0 volume): a review on both kinds (`R-TRANSITION-AUDIO-SILENT`, "this side is silent; the crossfade is a one-sided fade"), not an error, because `volume: 0` is an authored literal and `E-REMAP-AUDIBLE` already explains why it is there.
**Trade-offs:** The review will fire on intentional ducks until the author decides; that is one finding per intentional case, which is cheaper than an undetectable double fade in every accidental one. "Changes the level inside the window" must be defined as: any keyframe whose `t` lies strictly inside `(start, end)`, or a segment whose endpoints straddle the window with differing `v`; a flat constant volume across the window is not stacking.

🗳️ **Juror 3** (Fable 5.1) — **Q-7 VOTE: `query --at` reports each sounding element's resolved gain with its factors (volume, transition id + curve + its gain at that instant); `timeline` shows the `audio` value as one token on the transition row; `compare` and `shift` need nothing new**

**Reasoning:** The thing that would mislead an agent is hearing a level that no literal in the file explains. So `query --at t` inside the window must, for each element that is sounding, print the resolved gain and break it into its authored sources: `volume 1.0 (keyframe) × transition t1 constant_power 0.63 → 0.63`. When `audio` is absent it must print the resolved default by name (`transition t1 audio: cut (absent)`), which is what teaches the agent that absence means cut. `timeline` should carry the `audio` value on the transition row (`t1 crossfade v1→v2 1200–1800 audio=constant_power`) and nothing more; that is enough to spot a dissolve with a hard cut at a glance. `compare` already diffs fields of an element, so a changed `audio` value shows exactly like a changed `ease`; `shift` already moves a transition with its bridged elements because the window is bound to the intersection, and `audio` carries no time, so there is nothing to keep in step. That is the smallest set: one line per sounding element in `query`, one token in `timeline`.
**Trade-offs / must NOT be added:** Do not materialise the crossfade as derived volume keyframes on the bridged elements, in `query` output, in `compare`, or anywhere an agent might copy them back into the file; that would duplicate the authored literal and break "change the derived thing through the literal that generates it." Do not add a sampled gain table or curve plot to `timeline`; a row is a row. Do not add a separate "audio transitions" listing or tool; the transition list is the list. Do not have `query` report a resolved gain without naming the transition id it came from, since the id is the string the agent has to go and edit.

## The Judge's read and the owner's ruling

The Judge's read, after the ballots: Q-1, Q-3, Q-4, Q-5 and Q-7 are settled by all three jurors.
On Q-2 the Judge leaned to two curves under one `audio` key with `cut` as a value (Jurors 1 and 3),
not three under `audio_curve` (Juror 2), because exponential is a stylistic choice no rule picks
and adding a fourth value later breaks nothing. On Q-6 the one split is a one-sided
`audio_crossfade`; the Judge leaned to Juror 3's rule (an error if either side has no audio
stream), because a one-sided audio crossfade is a fade in disguise. The owner's ruling: "go with
the judge".
