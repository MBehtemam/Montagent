# Ballots: the ducking write tool

Packet: [`QUESTION.md`](QUESTION.md), sent blind and identical to three jurors dispatched in
parallel. Ticket: [#804](https://github.com/MBehtemam/Montagent/issues/804). Ballots are verbatim,
grouped by juror. The owner ruled with the Judge's read (below the ballots); the ADR is
[ADR-0177](../../../adr/0177-ducking-is-a-skill-script-that-writes-ordinary-volume-keyframes-and-the-format-stays-untouched.md).

## Juror 1 (Claude Opus 5.5)

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-1 VOTE: (b) A CLI-only verb in the binary, `montagent duck`. `captions.py` would call this verb instead of doing its own ducking. It should not be an MCP write tool.**

**Reasoning:** The lead workflow (TTS narration over a music bed) needs ducking all the time, so leaving it as an undocumented side feature of `captions.py` (d) means agents keep using code that is hard to find and has no tests. A script outside the binary (a) has a quieter problem: the format is closed and versioned, so a Python script that writes JSON can fall out of step with the schema without anyone noticing. A binary verb fixes that. It re-emits the file in canonical form, returns the new state's findings like every write path does, is tested by the Rust suite against the real schema, and its count is asserted, so adding it is a deliberate act, as ADR-0083 requires. Its output is still only ordinary `volume` keyframes, which is the door ADR-0055 named. An MCP tool (c) would need a bed id and a voice id, and the write-tool invariant forbids exactly that ("no tool takes ... an element id"). The only way to satisfy the invariant would be to pass the complete bed element and voice element as objects. That leaves the agent carrying a large blob that can go stale, all to get around a rule that exists for a good reason.
**Trade-offs:** An agent that only has MCP and no shell cannot duck. I accept that for now. The verb's output is plain keyframes, which the agent can also write by exact-string replace. This adds one verb to the CLI count. If usage over MCP proves high, it can be promoted later with a complete-element shape. (a) costs less to build, but it leaves the schema-drift and canonical-form risk in place.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-2 VOTE: (a) and (d) as one input: a spans file of `[{start,end}]` in ms (a words file already has this shape). No silence detection. With no timings, refuse loudly.**

**Reasoning:** A word-alignment file and a list of spans written by hand are the same data, so the verb should accept one format and ignore extra keys such as `word`. Word alignment is already external, and `compare` and `validate` already catch drift, so the duck reuses evidence the agent has and that it can check. Span times should be relative to the voice element and offset by its `start`, so that moving the voice element as a whole moves the duck correctly when the duck is rerun. Silence detection (c) brings thresholds, depends on the source audio, and produces results the agent cannot read back or check from the file alone. Using only `start`/`end` (b) has no pauses, which removes the whole point of `over`. When there are no timings, the verb exits with an error code and a repair telling the agent to run the aligner or pass spans. It does not quietly fall back to (b).
**Trade-offs:** The agent always needs an aligner step or spans written by hand. For TTS that is cheap, because most TTS engines can emit timings.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-3 VOTE: `--bed <id>` and `--voice <id>`, one bed per call (several voices are merged into one set of spans). Levels are linear (`under`, `over`, `end`). Times use `_ms` keys (`ramp_ms`, `lead_ms`, `join_ms`, `fade_ms`). The file only ever gets linear `volume` keyframes.**

**Reasoning:** These are arguments to a call, not keys in the file, so ADR-0170's dB rule for new file keys does not apply. What matters is the read-back. The agent checks the result with `query --at` and gets linear `volume` values. If `under: 0.18` goes in and 0.18 comes back, the comparison is trivial. A dB argument would force a conversion on every check, and 0.1778 would fail to match. The `_ms` suffix removes any doubt about the unit, as the rest of the format does. One bed per call keeps "which curve did this overwrite" unambiguous. For several beds, call it several times.
**Trade-offs:** Audio people think about depth in dB. The docs can give the equivalents next to the defaults (0.18 ≈ −15 dB).

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-4 VOTE: (c) Refuse when the bed already has keyframed `volume`, unless `--replace` is given. The duck owns the bed's whole curve, including an optional fade-in and fade-out (`fade_in_ms`, `fade_ms`, both off by default).**

**Reasoning:** A merge (b) has to decide where a hand-written fade ends and the duck begins, and nothing in the file says which is which. Every rerun after a retime would compound that guess. Replacing silently (a) destroys hand-written fades without telling anyone. Refusing with a repair ("bed has keyframed volume; pass --replace to regenerate") is loud and cannot be ignored by accident. Because a replace rewrites the whole curve, the fades have to be inputs to that same generation. Otherwise every rerun wipes them out. So the fade-out belongs to the duck verb, as an argument that is off by default.
**Trade-offs:** Unusual hand-made shapes on the bed cannot survive a rerun; the author has to fold them into the arguments or edit afterwards. Every refresh needs `--replace`, which is a small cost for knowing exactly what was overwritten.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-5 VOTE: (i) Keyframes only, no provenance record. (ii) Never emit equal-keyframe pairs that trigger `R-EASE-INERT`; a clean run must return zero reviews. (iii) Keep `R-TRANSITION-VOLUME-STACK` and do not skip ducking near transitions; the verb returns the review. Staleness is detected by `montagent duck ... --check`, which recomputes the curve and diffs it against the file.**

**Reasoning:** (i) A record that a duck was applied is recorded intent. It would be a second source of truth that goes stale with the voice, and the brief says the file never records it. (ii) A tool that triggers its own review on every run teaches agents to ignore reviews. A hold should be written however the format spells a constant segment without tripping the review: one keyframe per level change, at the start and end of each ramp, with the default ease on hold segments. If the review fires even on a correct hold, fix the review in the same change. Either way, a repo test asserts zero findings on a clean duck. (iii) Ducking less inside a transition window would leave music loud over speech without any warning. The review already tells the author that two level changes overlap, and the author decides. (Staleness) `--check` takes the same arguments plus the current spans. It exits nonzero with a finding that names the first instant that differs, and its repair is the same command with `--replace`. `compare`'s word-drift findings are the trigger to run it.
**Trade-offs:** Nothing in the file says it was ducked, so an agent only knows to check because of the workflow docs and a retime. I accept that cost to keep the file literal-only.

🗳️ **Juror 1** (Claude Opus 5.5) — **Q-6 VOTE: Measure both the written keyframes and the rendered PCM, in the repo's Rust render tests.**

**Reasoning:** Keyframes: `query --at` at named instants (inside speech, inside a pause of at least `join_ms`, inside a pause shorter than `join_ms`, after the last word, ramp start and end) must return exactly `under`, `over`, `under`, `end`, and the ramp endpoints. These are integer ms and literal values, so the tolerance is zero. PCM: render a steady-tone bed under a synthetic voice with known spans, then measure the bed's RMS in speech and in pauses against an unducked render. The ratio must be within ±0.25 dB of 20·log10(level). Ramp onset must fall on the sample its instant names, within ±1 sample at the project rate, as ADR-0175 requires. The tolerance comes from what is measured. The 0.25 dB allows for RMS windowing and float mix rounding on a steady tone. The sample bound comes directly from ADR-0175's guarantee, not from a byte hash. The tests live in the Rust suite because the verb lives in the binary (Q-1). The skill's CI only checks that `captions.py` calls the verb.
**Trade-offs:** The PCM test needs a render and is slower. Checking keyframes alone would miss chain-order regressions, such as an effect placed after `volume` pushing the duck back up (ADR-0169). Checking PCM alone would miss mistakes in the arguments that happen to sound plausible.

## Juror 2 (Sonnet 5.5)

🗳️ **Juror 2** (Sonnet 5.5) — **Q-1 VOTE: (a) a skill script, generalised out of `captions.py` into its own `duck.py` with the same shape; format untouched**

**Reasoning:** The duck is already shipped, works, and writes only ordinary `volume` keyframes. That is the exact residue ADR-0055 allowed. A script may take ids freely and sits outside both the MCP count (eleven) and the CLI-verb count, so nothing deliberate-to-add is triggered. Splitting it out fixes the real problem: ducking is buried inside a captions tool, so an agent doing narration plus a bed does not find it. The lead workflow's first wave is covered by a discoverable skill entry.
**Trade-offs:**
- (c) cannot satisfy the write-tool invariant. "No tool takes an element id" is exactly what a duck call needs (bed id, voice id), so it would need a schema-shaped complete element in and out, which is a worse `shift`.
- (b) adds a permanent binary verb and a test-asserted count change for something with no new evidence of cost.
- (d) leaves the discoverability gap. The script stays Python and stdlib-only, so the cost is that it is outside the binary's tests and relies on skill CI.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-2 VOTE: (a) external word-timings file as the primary source, plus (d) explicit spans as the alternative input. No silence detection, no coarse fallback. With no timings, fail loudly.**

**Reasoning:** The words file gives the pauses that decide `over` vs `under` and the join rule. Explicit spans (`[{start,end}]` in ms) cover voices with no aligner, such as a short TTS line where the author knows the span. Both reduce to the same internal span list, so the tool has one core. With neither input, the tool exits with an error naming both inputs and the shape of each. It does not guess.
**Trade-offs:**
- (b) writes a wrong duck silently, because there are no pauses. That is a silent misfire.
- (c) adds a heuristic with thresholds, a decoder dependency, and results that differ between runs. That is hard to explain and to repair.
- The cost is that the author must supply timings. That is acceptable because alignment is external anyway.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-3 VOTE: element ids for the bed and the voice; one bed per duck entry (a list of entries allows several beds); spec keys in dB and ms (`under_db`, `over_db`, `end_db`, `ramp_ms`, `lead_ms`, `join_ms`, `fade_ms`); the file always gets linear `volume` keyframes.**

**Reasoning:** ADR-0170 puts the unit in the key name for new level keys. The same logic applies to a new spec: a dB depth like -15 is how people and the skill's guidance think about ducking, and it needs no per-call linear arithmetic. The tool converts to linear once and rounds to a fixed number of decimals. The `_ms` suffixes remove the unit ambiguity of today's bare `ramp`, `lead` and `join`. The bed id is required. The voice is identified by the words or spans input, and the voice id is optional, used only to cross-check the voice's drawn range. Several beds are handled as several entries, each with its own levels, and are not a shared field. The bed id is checked against the project: it must be an existing audio element, or the tool gives a loud error with the list of audio ids.
**Trade-offs:**
- Two spellings exist (dB in the spec, linear in the file). The script prints the converted linear values it wrote, so the agent sees the mapping.
- The old `under: 0.18` keys can be accepted for one release with a deprecation warning.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-4 VOTE: (c) refuse when the bed already has a keyframed `volume`, unless told to replace (`replace: true`). The tool owns the whole curve in that case. The fade-out is an optional key of the same pass, on by default, not a separate tool.**

**Reasoning:** Merging (b) means guessing how a hand-made fade-in interacts with a ramp and where "inside the ducked stretch" ends. It is a source of silent, surprising curves and a hard-to-explain state. Replacing silently (a) destroys an author's hand work with no signal. Refusing is loud, has an obvious repair (add `replace`), and keeps existing projects unchanged. Once replaced, the tool writes the full curve: under, over, end, and a fade to 0 ending on the last drawn frame. A fade must be in the same pass because it is part of the single `volume` list, and two writers on one list would conflict. It can still be turned off with `fade_ms: 0` and then hand-edited by exact-string replace.
**Trade-offs:**
- One extra flag on the first re-run. Re-runs of the tool's own output also need `replace`, so the script should treat a `volume` that matches its own shape as replaceable, or the idempotent re-run becomes a nuisance.
- A hand-authored fade-in is lost on replace, so the agent must re-add it afterwards.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-5 VOTE: (i) keyframes only, no record of the duck; (ii) the tool emits held levels with no `ease` on equal pairs; (iii) leave `R-TRANSITION-VOLUME-STACK` alone, but have the script print the transition windows it overlaps. Staleness is found by re-running and diffing.**

**Reasoning:**
- (i) The format is closed, so a record would need a new schema key, and it would be a second source of truth that can disagree with the keyframes. "Never records that a duck was applied" is the settled pattern. The voice timings live in the external words file, and `compare` already catches voice drift. The documented loop is: retime the voice, re-align, re-run the script. The script has a `--check` mode that computes the keyframes, compares them with the bed's current `volume`, and exits non-zero with the differing instants. That is how an agent knows a duck is stale without a stored flag.
- (ii) `R-EASE-INERT` fires on an `ease` that does nothing. Held levels are two equal keys, and the tool should not set an `ease` on them. Whether that clears the review depends on how the validator treats a default ease. If the review still fires on equal pairs, the repair is in the validator's rule or accepted as a documented false positive, not hidden by the tool.
- (iii) A duck inside a transition window is a real overlap of two level changes, and the review is correct. Moving the duck to dodge it would change the audible result for the sake of a lint. The script prints a warning naming the transition and the window, and the author decides.

**Trade-offs:**
- With no record, a stale duck is found only by an agent that remembers to re-run. This is mitigated by the skill's retime checklist and `--check`.
- Noise from (ii) may remain until the validator rule is adjusted.

🗳️ **Juror 2** (Sonnet 5.5) — **Q-6 VOTE: both. A written-keyframe check (`query --at` at named instants) and a rendered-PCM check, run in the skill's CI in the style of `ci/test_prerender_still.py`. The rendered tolerance is 0.5 dB on level, with the ramp timing taken from ADR-0175.**

**Reasoning:**
- Keyframes: after the script runs on a fixture project and words file, `query --at` reads the bed's `volume` at the speech, pause, post-last-word and fade instants. These must equal the linear value of the dB spec within the rounding step (1e-3 absolute), plus the ramp start at `voice start - lead_ms`. This pins the script's logic exactly.
- PCM: render the fixture with a steady-tone bed. Measure RMS over windows well inside speech and inside a pause, against the same bed with no duck. The ratio must match `under_db` / `over_db` within 0.5 dB. The tolerance comes from two sources: the rounding of linear levels (about 0.05 dB at 0.18) and RMS window error on a steady tone. That is a measurement-noise allowance, not a hash.
- Ramp timing to the sample is already guaranteed by ADR-0175's Rust render test. The duck ADR cites that test, so the new check does not duplicate it and the script's test stays in the skill CI, where the script lives.

**Trade-offs:**
- The PCM check needs a render in skill CI, so it is slower. The Rust render tests are not the right home, since the script is not in the binary.
- If the render is skipped in some environment, the keyframe check alone still gates the script's logic.

## Juror 3 (Fable 5.1)

🗳️ **Juror 3** (Fable 5.1) — **Q-1 VOTE: (a) a standalone skill script, generalised out of `captions.py`, format untouched — with the door for (b) left explicitly open in the ADR**

**Reasoning:** The evidence ADR-0055 asked for has arrived in a narrow form: `captions.py` already ducks and agents use it, so hand-authoring was costly enough that a skill grew the feature. That is evidence for a script, not yet for a binary verb. The write-tool invariant ("No tool takes a field name or an element id") makes (c) structurally hostile to a duck: a duck is inherently *two ids plus parameters*, and the only invariant-compliant shape would be "the agent passes the complete bed element already carrying the keyframes it wants", which is the agent computing the duck itself, so the tool does nothing. A script can take ids freely, reads the words file the aligner already produced, and writes nothing the format does not already have. Extracting it from `captions.py` fixes the real defect: today a duck can only be refreshed by re-running caption generation, and a voice retime without a caption change has no refresh path. (d) leaves that coupling in place.
**Trade-offs:** A script is less discoverable than an MCP tool and has no `validate` findings in its return; the ADR should require the script to end by invoking `montagent validate` and printing its findings so the agent sees `R-EASE-INERT`/`R-TRANSITION-VOLUME-STACK` as the binary reports them. (b) would buy determinism-in-the-binary and a Rust test, at the cost of a tool-count change and a verb that needs the words-file format in the binary; defer it until two scripts need the same keyframe maths.

🗳️ **Juror 3** (Fable 5.1) — **Q-2 VOTE: (a) external word-timings file as the primary input, (d) explicit spans as an alternative input, same internal shape; (b) as the explicit fallback only when told `--coarse`; no (c)**

**Reasoning:** Word alignment is already external and already produced for captions; the duck should consume the same file so the two artefacts cannot disagree about where the voice is. Explicit spans are the same data type (a list of `{start,end}` ms) and cost nothing to accept; they serve the agent who has a script-level sense of the pauses but no aligner (e.g. per-sentence TTS clips whose boundaries it already knows). Silence detection would put a signal-analysis judgement inside the write path, which cannot be checked by `validate` from the file alone and would make the output depend on thresholds the file never records — a provenance gap the repo has consistently refused. When the voice has no timings the script must refuse loudly with a message naming the three ways to supply them, and must not silently fall back to the voice element's `start`/`end`: a coarse full-length dip is a different edit, so it is opted into, not defaulted.
**Trade-offs:** Refusing instead of falling back costs the agent one more round-trip in the simplest case. Accepting both files and spans means two input schemas to document. Silence detection would be the only option that survives with no external tool at all, and giving it up means the duck is only as good as the aligner.

🗳️ **Juror 3** (Fable 5.1) — **Q-3 VOTE: `bed` and `voice` are element ids; one bed per call, one voice per call; depth and levels in dB with the unit in the key (`under_db`, `over_db`, `end_db`), timing in `_ms` keys; the file gets linear `volume` keyframes rounded to a fixed precision**

**Reasoning:** ADR-0170 already decided that new level keys are dB with the unit in the name and `volume` stays the one linear level. The duck's parameters are new level keys, so they follow the rule; what is *written* follows the other rule, so it is linear `volume`. Agents reason about ducks in dB ("drop 15 dB under speech") and the footage skill's guidance can be restated as `under_db: -15`, `over_db: -7`, `end_db: -1.5` without losing anything. The call is one bed under one voice because that is what the keyframe maths is a function of; several voices are a loop in the caller, and several beds are several calls — nothing is gained by multiplexing inside one invocation, and the error messages stay one-dimensional. `_ms` suffixes for `ramp_ms`, `lead_ms`, `join_ms` match the document's absolute-millisecond convention and make the units unmistakable in a spec an agent types by hand. Written linear values should be rounded (say four decimals) so that `compare` and exact-string replace see stable strings across runs.
**Trade-offs:** Breaking from `captions.py`'s linear `under: 0.18` means its existing duck spec needs a migration note, or `captions.py` keeps its old keys and delegates. Rounding introduces a tiny difference between the dB the agent asked for and the level rendered; it is far below any acceptance tolerance.

🗳️ **Juror 3** (Fable 5.1) — **Q-4 VOTE: (c) refuse by default when the bed already has a keyframed `volume`; `--replace` replaces the whole curve, as `captions.py` does; no merge mode now; the final fade-out is a separate concern and is not written by the duck**

**Reasoning:** Merging keyframes is where silent damage lives: a hand-written fade-in that overlaps the first ducked stretch has no unique right answer (multiply? min? clip?), and whichever the tool picks is a derived value the file cannot show the origin of. Refusing with a finding-shaped message ("bed `music` already has 6 `volume` keyframes; pass `--replace` or move the fade to a separate element") is loud, costs one round-trip, and never changes a project without the agent having said so. Replace is deterministic and idempotent, which is what makes re-running after a voice retime safe. Taking the fade-out out of the duck decouples two concerns that are retimed by different events: the duck moves when the voice moves; the fade-out moves when the bed's end or the picture's last frame moves. With ADR-0176's audio crossfade on transitions already shipped, an outro fade has a native home that the duck should not duplicate.
**Trade-offs:** Refusing-by-default means the common case (bed has a manual fade-out, agent wants a duck) always needs `--replace` and loses the manual fade, which the agent must then re-express as a transition or a trailing element. That is a workflow cost, but a predictable one; a merge that sometimes keeps and sometimes clobbers would be worse for an agent recovering from an error. `captions.py`'s `fade` key should be kept as an opt-in for one release and marked deprecated.

🗳️ **Juror 3** (Fable 5.1) — **Q-5 VOTE: (i) keyframes only, no record in the file; provenance lives in the sidecar words file and the script's stdout; (ii) yes, avoid inert pairs by emitting one keyframe per level change with `ease` carrying the ramp, never two equal values; (iii) leave `R-TRANSITION-VOLUME-STACK` alone and do not special-case transitions; staleness is detected by `compare` against a dry-run, not by a file record**

**Reasoning:** (i) A record that a duck was applied is exactly the live relational field ADR-0055 refused, in disguise: the moment the file says "this `volume` came from voice `vo` with `under_db -15`", every reader must decide whether the keyframes and the record agree, and `validate` cannot check it from the file alone because the words are not in the file. ADR-0037/0086's pattern for derived instants is the same: keep the residue, keep the recipe outside. (ii) The inert pairs are an artefact of `captions.py` thinking in "hold then ramp" where the format thinks in "a keyframe is where the value is at t, eased from the previous one"; the generator should emit `{t: speechStart-lead, v: over}` then `{t: speechStart-lead+ramp, v: under}` and so on, with no doubled values, so a clean duck yields zero reviews. A tool that wrote a review into every project it touched would train agents to ignore that review. (iii) The stack review is correct when it fires: a duck crossing a transition's crossfade genuinely stacks two level changes, and that is the author's call (move the transition, retime the voice, or accept it). Having the script skip ducking inside the window would quietly leave the bed loud under speech, which is the one outcome the duck exists to prevent. Staleness: the script gets a `--check` / dry-run mode that computes the keyframes and diffs them against the bed's current `volume` without writing; the ADR should instruct the footage skill to run it whenever the voice element or its words file changes. The agent knows the duck is stale because the dry run says so, not because the file remembers.
**Trade-offs:** No in-file record means a project read cold cannot tell a hand-written dip from a generated one; that is already true of every keyframe in the format and is the price of ADR-0145. The dry-run check depends on the words file still being on disk; if it is lost, the only honest answer is "regenerate from the aligner", which is the same answer captions already live with.

🗳️ **Juror 3** (Fable 5.1) — **Q-6 VOTE: both measurements, split by what each build owns: the written keyframes checked via `query --at` in the skill's CI; the rendered PCM checked in the repo's Rust render tests against a fixture project that already carries the keyframes; tolerance ±0.5 dB on level, ±1 sample on ramp edges**

**Reasoning:** The two halves have different owners and different failure modes. The script's maths (does `under_db -15` at instant t become `volume` 0.1778 at t, does the ramp start `lead_ms` early, does a 500 ms pause stay down with `join_ms 600`) is a property of the Python and belongs in `ci/test_prerender_still.py`'s neighbour, read back through `montagent query --at` so the test exercises the real reader. The binary's job — that a keyframed `volume` is heard on the sample its instant names (ADR-0175) and that the effects list runs before `volume` (ADR-0169) — is already a Rust render test concern, and the duck ADR should add one fixture: a bed with a known duck curve and a tone source, measured as RMS over the speech window and the pause window relative to the unducked render, plus the first and last sample of a ramp. ±0.5 dB is the smallest difference the footage guidance treats as meaningful (it quotes level ranges 0.15–0.2, which is ~1.2 dB wide) and is comfortably above resampler and dither noise; ±1 sample on ramp edges is what ADR-0175 already promises. Neither test hashes bytes.
**Trade-offs:** Two tests in two languages is more surface than one, and the Rust side tests the format not the script, so a script bug that writes the wrong instants is caught only by the Python side. A single end-to-end PCM test driven from the script would be more honest but would make the repo's Rust CI depend on a skill script, which the repo has kept outside the binary on purpose.

## The Judge's read and the owner's ruling

The Judge's read, after the ballots: all three jurors rule out an MCP write tool (a duck needs two
element ids, which the write-tool invariant forbids); words file and explicit spans are one input,
with no silence detection; refuse when the bed already has keyframed `volume`, unless told to
replace; the file keeps only the keyframes, with a `--check` dry run for staleness;
`R-TRANSITION-VOLUME-STACK` is left alone; both the written keyframes and the rendered audio are
measured. The Judge took the skill script on Q-1 (2 to 1 over a CLI verb), dB in the spec on Q-3
(2 to 1 over linear), and the fade-out as an optional argument of the same pass, off by default, on
Q-4 (2 to 1; the Judge corrected Juror 3's claim that ADR-0176 gives an outro fade a native home,
because a fade to silence is not a crossfade between two elements). One point all three jurors
missed: Q-5 (ii) cannot be done as asked, because a held level needs two keyframes of equal `v`,
ADR-0038 requires an `ease` on each, and ADR-0052 fires `R-EASE-INERT` on any two consecutive equal
keyframes whatever the `ease` is. The Judge recommended accepting the review on a tool-written hold
and not amending ADR-0052 in this effort. The owner's ruling: "go with the judge".
